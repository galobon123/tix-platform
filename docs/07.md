## Épica 11: Testing de Carga con k6

**Objetivo de aprendizaje:** diseño de pruebas de carga realistas, modelo abierto vs. cerrado, *thresholds*, pruebas de corrección bajo concurrencia, k6 distribuido en Kubernetes e ingeniería del caos.

> Cumple el cuadro objetivo: *"Demostrar que el sistema tolera picos virales masivos de tráfico"*. Una prueba de carga sin métricas, trazas y logs (Épicas 09–10) solo dice **que** falló; con ellas dice **por qué**.

### HU 11.1 - Estrategia de Pruebas y Escenarios de Carga
`[NUEVA]`

**Descripción:** Como equipo, quiero escenarios k6 que reproduzcan el recorrido real de compra y los picos virales, para validar los SLOs antes de salir a producción.

**Tareas de Implementación:**
1. Definir los **tipos de prueba** y su propósito:

   | Tipo | Forma | Pregunta que responde |
   |---|---|---|
   | *Smoke* | 1–5 VUs, 30 s | ¿Funciona el script y el entorno? |
   | *Load* | carga nominal sostenida | ¿Cumple los SLOs con la carga esperada? |
   | *Stress* | rampa hasta degradación | ¿Dónde y cómo se degrada? |
   | *Spike* | salto brusco ×10 | ¿Resiste un pico viral? |
   | *Soak* | 60 % de capacidad, 4–8 h | ¿Hay fugas (memoria, conexiones)? |
   | *Breakpoint* | rampa hasta el fallo | ¿Cuál es la capacidad máxima? |

2. Usar el **modelo abierto** (`ramping-arrival-rate`: tasa de llegadas fija) para simular usuarios que llegan independientemente de la latencia; evita el *coordinated omission* del modelo cerrado (VUs que "esperan" y reducen la carga cuando el sistema se vuelve lento).
3. Recorrido de usuario: navegar → mapa → login → *hold* → orden → pago (**pasarela simulada**, nunca la real).
4. Mezcla de tráfico realista (p. ej. 90 % lectura / 10 % escritura) y *think time* con variación.
5. Datos de prueba: usuarios y tokens pre-generados (`SharedArray`), eventos y asientos sembrados; tokens de prueba emitidos por un endpoint **solo habilitado en *staging***.
6. Definir *thresholds* alineados a los SLOs (HU 09.3) y abortar automáticamente si se rompen.
7. Entorno de prueba con **dimensionamiento equivalente a producción** (o escalar los resultados con un modelo documentado).

**Referencia (`spike.js`):**

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';
import { SharedArray } from 'k6/data';
import { Counter } from 'k6/metrics';
import { uuidv4, randomIntBetween } from 'https://jslib.k6.io/k6-utils/1.4.0/index.js';

// Los 409/429 son respuestas esperadas del sistema, no fallos de red/servidor
http.setResponseCallback(http.expectedStatuses({ min: 200, max: 399 }, 409, 429));

const BASE = __ENV.BASE_URL, EVENT = __ENV.EVENT_ID;
const users = new SharedArray('users', () => JSON.parse(open('./data/users.json')));
const holds = new Counter('hold_ok');

export const options = {
  scenarios: {
    browse: {
      executor: 'ramping-arrival-rate', exec: 'browse',
      startRate: 100, timeUnit: '1s', preAllocatedVUs: 500, maxVUs: 5000,
      stages: [
        { target: 1000, duration: '2m' },
        { target: 5000, duration: '30s' },   // pico viral
        { target: 5000, duration: '5m' },
        { target: 200,  duration: '2m' },
      ],
    },
    buyers: {
      executor: 'ramping-arrival-rate', exec: 'buy',
      startRate: 1, timeUnit: '1s', preAllocatedVUs: 200, maxVUs: 2000,
      stages: [{ target: 300, duration: '1m' }, { target: 300, duration: '5m' }],
    },
  },
  thresholds: {
    // B-21: rate<0.001 (0,1 %), NO rate<0.01 (1 %).
    // La v2.0 ponía un umbral 10 veces más laxo que su propio criterio de aceptación
    // ("no hay errores 5xx inesperados < 0,1 %"), de modo que una prueba con 1 % de
    // 5xx pasaba el gate mientras el CA decía que debería fallar: el gate no garantizaba
    // nada. El umbral tiene que ser MÁS estricto que el CA, nunca más laxo.
    http_req_failed: ['rate<0.001'],
    'http_req_duration{endpoint:availability}': ['p(99)<300'],
    'http_req_duration{endpoint:hold}': [{ threshold: 'p(99)<200', abortOnFail: true, delayAbortEval: '1m' }],
    checks: ['rate>0.99'],
    dropped_iterations: ['count<100'],        // el generador/SUT sostiene la tasa pedida
  },
};

export function browse() {
  const r = http.get(`${BASE}/api/v1/events/${EVENT}/availability?section=A`,
                     { tags: { endpoint: 'availability' } });
  check(r, { 'availability 200': (res) => res.status === 200 });
  sleep(randomIntBetween(1, 3));
}

export function buy() {
  const u = users[(__VU - 1) % users.length];
  const h = { headers: { Authorization: `Bearer ${u.token}`, 'Content-Type': 'application/json' } };
  const seat = randomIntBetween(1, 2000);
  const r = http.post(`${BASE}/api/v1/events/${EVENT}/seats/${seat}/hold`, null,
                      { ...h, tags: { endpoint: 'hold' } });
  if (r.status === 201) {
    holds.add(1);
    http.post(`${BASE}/api/v1/orders`, JSON.stringify({ eventId: EVENT, seatIds: [seat], holdToken: r.json('token') }),
              { headers: { ...h.headers, 'Idempotency-Key': uuidv4() }, tags: { endpoint: 'order' } });
  }
}
```

**Criterios de Aceptación (CA):**
- Con la carga nominal, **todos** los *thresholds* pasan y el reporte se archiva en Confluence.
- En el pico ×10 el sistema degrada de forma controlada: `hold` mantiene p99 < 200 ms para tráfico admitido, la navegación puede recibir `429`/`503` y **no hay errores 5xx inesperados** (< 0.1 %).
- `dropped_iterations` ≈ 0 (el resultado no está limitado por el generador de carga).
- Cada ejecución queda correlacionada con paneles de Grafana por un `testid`.

**Casos de Uso:**
- **Happy Path:** El *spike* ×10 activa la sala de espera, el preescalado y el autoescalado; los SLOs de los usuarios admitidos se cumplen.
- **Failure Path:** El *threshold* de p99 de `hold` se rompe; la prueba aborta, el reporte señala el cuello de botella (p. ej. `cl_waiting` de PgBouncer) y se abre una acción de mejora.

### HU 11.2 - Prueba de Corrección: "Cero Sobreventa"
`[NUEVA]`

**Descripción:** Como responsable del producto, quiero demostrar con carga masiva que un asiento nunca se vende dos veces, para validar el invariante más importante del sistema.

**Tareas de Implementación:**
1. Escenario **un solo asiento, miles de compradores**: todos los VUs intentan reservar y comprar el mismo asiento a la vez:
   ```javascript
   export const options = {
     scenarios: { race: { executor: 'per-vu-iterations', vus: 5000, iterations: 1, maxDuration: '2m' } },
     thresholds: { won: ['count==1'] },          // exactamente 1 ganador
   };
   const won = new Counter('won');
   export default function () {
     const r = http.post(`${BASE}/api/v1/events/${EVENT}/seats/${SEAT}/hold`, null, authHeaders());
     if (r.status === 201) won.add(1);
   }
   ```
2. Escenario **muchos asientos, aleatorio**: 10 000 VUs sobre 1 000 asientos; ejecutar el flujo completo hasta `PAID` (`hold → order → payment → PAID → ticket`), porque la sobreventa también puede colarse por el camino del pago y no por el del *hold*.
3. **Verificación posterior en SQL** (automatizada al final de la prueba):
   ```sql
   -- 1) Ningún asiento con más de un ítem activo → 0 filas
   SELECT seat_id, count(*) FROM order_items WHERE released_at IS NULL GROUP BY seat_id HAVING count(*) > 1;
   -- 2) Todo asiento SOLD tiene exactamente un ítem activo → 0 filas
   SELECT s.id FROM seats s
     LEFT JOIN order_items oi ON oi.seat_id = s.id AND oi.released_at IS NULL
    WHERE s.status = 'SOLD' AND oi.id IS NULL;
   -- 3) Pagos aprobados sin orden PAID/REFUNDED → 0 filas
   SELECT p.id FROM payments p JOIN orders o ON o.id = p.order_id
    WHERE p.status = 'APPROVED' AND o.status NOT IN ('PAID','REFUNDED');
   -- 4) (B-05) Deriva entre Redis y la DB tras la prueba → 0 filas.
   --    Es la única que detecta un fallo REAL: la 1 y la 2 son imposibles por
   --    construcción (restricción parcial + UPDATE condicional), ver HU 09.4.
   --    Se apoya en las tablas del sondeo de deriva (drift_probe / drift_findings,
   --    DDL y consultas completas en HU 09.4), no en un snapshot de Redis.
   SELECT count(*) FROM drift_findings f
     JOIN drift_probe p ON p.probe_id = f.probe_id
     JOIN seats s ON s.seat_id = f.seat_id
    WHERE s.status = 'AVAILABLE'
      AND p.probe_at >= now() - interval '2 minutes';
   ```
4. Repetir la prueba **durante** un *failover* de Redis y durante un reinicio de PgBouncer (HU 11.4).
5. Ejecutarla de forma automática en la *pipeline* nocturna contra *staging* y como **puerta de promoción** a producción.

**Prueba de la prueba — *mutation testing* sobre el flujo completo (B-23).** La v2.0 solo mencionaba "desactivar a propósito el índice único parcial para comprobar que la prueba detecta la sobreventa", como *failure path* manual. Eso no funciona por dos razones, y por eso la v3.0 lo reemplaza:

- **Ese mutante no produce sobreventa.** El índice único parcial de `order_items` es una red de seguridad, pero **no es el mecanismo que decide**. Quien decide es el `UPDATE seats SET status='SOLD' WHERE seat_id=? AND status='AVAILABLE'` dentro de la transacción: si dos transacciones compiten, una recibe 0 filas y aborta. Soltar el índice deja el `UPDATE` condicional intacto, así que el sistema **sigue** sin sobrevender y la prueba no detecta nada. Se estaría "probando la prueba" con un mutante que no toca el *camino de compra*.
- **El endpoint de `hold` nunca toca `order_items`.** `order_items` se inserta al crear la orden, no al adquirir el *hold*. Ninguna mutación de esa tabla es alcanzable desde el escenario de *hold* de la v2.0.

La v3.0 define un **conjunto de mutantes nombrados**, cada uno con el detector que debe dispararse, ejecutado en un *namespace* efímero y en CI (no como ejercicio manual). La regla es: **un mutante que no es detectado es un hueco de cobertura, y la suite queda en rojo**.

| Mutante | Inyección | Detector que DEBE disparar |
|---|---|---|
| `M1-sin-arbitro` | Quitar el `AND status='AVAILABLE'` del `UPDATE` de `seats` | Consulta SQL 1 y 2 devuelven filas; `M2` también, por si acaso |
| `M2-sin-indice-parcial` | Quitar el `UNIQUE (seat_id) WHERE released_at IS NULL` | Consulta SQL 1 con `M1` activo (combinado); aislado, **no se detecta** y se documenta como tal |
| `M3-pago-sin-outbox` | El consumidor de pago no publica `order.paid` | Consulta SQL 3: hay `APPROVED` sin orden `PAID`; alerta `outbox_stuck` |
| `M4-refumbo-parcial` | El reembolso libera en Redis pero **no** marca `order_items.released_at` | Consulta SQL 4 y el asiento queda fantasma; alerta de deriva de B-05 |
| `M5-sin-idempotencia` | Ignorar la cabecera `Idempotency-Key` | Dos órdenes para el mismo *hold*; el umbral `won: count==1` falla |
| `M6-webhook-acepta-todo` | El webhook no valida la firma (ADR-014) | CA de HU 06.3: el webhook falsificado se rechaza y se registra `SECURITY` |
| `M7-hold-sin-precio-congelado` | El precio se lee del catálogo al confirmar, no del `holdprice:*` | CA de B-02: el precio pagado difiere del del *hold* |
| `M8-proyeector-apagado` | No arrancar el `availability-projector` | Consulta SQL 4 y `RedisMemoryPressure`/`seat_state_drift_current` de HU 09.4 |

`M1`, `M3`, `M4`, `M5` y `M8` deben ser detectables **de forma aislada**. `M2` está documentado como **no detectable aislado** y por eso `M1` y `M2` se ejecutan también en combinación: si alguien cambia el *árbitro* y olvida el índice, la combinación lo revela.

**Criterios de Aceptación (CA):**
- 5 000 intentos simultáneos sobre el mismo asiento producen **exactamente 1** `201` y el resto `409`.
- Las consultas de verificación devuelven **0 filas** tras cada ejecución, incluyendo las ejecutadas con fallos inducidos.
- **Los mutantes `M1`, `M3`, `M4`, `M5`, `M6`, `M7` y `M8` son detectados** por el detector indicado, cada uno en su propia ejecución, y la CI falla si alguno pasa inadvertido. `M2` se ejecuta combinado con `M1` y también debe detectarse.
- **La deriva entre Redis y la DB (consulta SQL 4, métrica `seat_state_drift_current`) es 0** al terminar la prueba, incluso tras *failover* de Redis. Este es el detector que de verdad importa: `M8` lo dispara y las consultas 1–3 no lo detectarían.
- La suite corre en la *pipeline* con `--seed` fijo para que un fallo sea reproducible, y con 3 semillas distintas en la corrida nocturna.

**Casos de Uso:**
- **Happy Path:** 5 000 compradores compiten; uno gana, 4 999 reciben `409` en menos de 200 ms.
- **Failure Path:** Se inyecta `M1-sin-arbitro` en *staging*; la prueba de la prueba **detecta** que el `UPDATE` perdió su condición, las consultas de verificación devuelven filas y la CI falla con el nombre del mutante, sin dejar ningún asiento vendido dos veces en el entorno real.

### HU 11.3 - Ejecución, Integración con CI y Reportes
`[NUEVA]`

**Descripción:** Como equipo, quiero ejecutar y comparar pruebas de carga de forma repetible, para detectar regresiones de rendimiento antes de producción.

**Tareas de Implementación:**
1. Tres niveles de ejecución, cada uno con su perfil y su presupuesto de tiempo:

   | Nivel | Perfil | Entorno | Cuándo | Qué valida |
   |---|---|---|---|---|
   | PR | `smoke` (5 VUs, 60 s) | Compose en el runner | cada PR | que el script corre, los *endpoints* existen, no hay errores tontos |
   | PR (opcional, etiqueta) | `load` corto (5 min, 200 VUs) | *staging* efímero | PR etiquetado `perf` | regresión grosera antes de fusionar |
   |-Nocturna | `load` (30 min) + `spike` | *staging* | cada noche | **gate de regresión de rendimiento** |
   | Pre-evento | `spike`, `soak`, `breakpoint` | *staging* equivalente | antes de un evento grande | capacidad y pico real |

2. **Gate de regresión de rendimiento (B-22), con su propia pipeline y su línea base.** La v2.0 decía: "un PR que degrada el p99 de `hold` más de un 20 % respecto de la línea base **falla** la verificación de rendimiento". Eso no se podía cumplir por tres razones, y las tres son la definición del hallazgo:
   - **La carga del PR no alcanza a medir un p99.** Un `smoke` de 5 VUs durante 30 s tiene unas decenas de muestras por endpoint. El p99 de 30 muestras es, literalmente, la muestra más lenta: **ruido puro**, con una variación de un orden de magnitud entre ejecuciones. Cualquier umbral puesto ahí no mide nada.
   - **El entorno del PR no es el de referencia.** Compose en el runner shares CPU con el resto de jobs, tiene otra versión de Postgres en modo local y otra de Redis sin *cluster*. Comparar su p99 con una línea base medida en *staging* condimensionamiento equivalente (HU 11.1) compara dos sistemas distintos, así que el "20 %" mide el entorno, no el código.
   - **Un umbral de 20 % sobre p99 no tiene en cuenta el ruido.** Entre dos ejecuciones idénticas hay diferencias del 5–15 % por ruido normal. Con un umbral del 20 % aparecen falsos positivos; con uno del 5 %, falsos negativos. El número se eligía sin datos.

   La v3.0 define el gate así, y lo mueve **fuera del PR**:
   - **Dónde:** en la pipeline de `staging` por PR (no en el PR), con el mismo perfil `load` de 5 min, ejecutándose siempre aunque el PR no toque las rutas calientes. El PR en sí conserva `smoke`.
   - **Contra qué:** contra una **línea base versionada** (`perf-baseline.json`, p99 por endpoint + RPS + `http_req_failed`), no contra la corrida anterior. Con la anterior, una regresión se "lava" sola en dos noches.
   - **Umbral:** **15 %** de empeoramiento en el p99 de `hold`, y el umbral se **calibra una vez** con ~10 corridas del mismo código en el mismo entorno: si la desviación típica entre corridas es 8 %, un umbral del 15 % da margen sin perder sensibilidad. El valor derivado queda escrito en el repo con su justificación; no es un número redondo inventado.
   - **Estadística, no comparación de dos números:** se comparan los **p99 con sus intervalos de confianza** (k6 `summary-trend-stats` con `p(99)`, `p(99.9)` y un bootstrap sobre los *thresholds* por VU). La regresión se declara solo si el empeoramiento es **estadísticamente significativo**, no si el número "parece" mayor.
   - **Fail-fast y no bloqueante a la vez:** una regresión > 15 % **falla** la pipeline y **bloquea el merge**; entre 10 % y 15 % **avisa** y queda registrada para revisión. Una prueba de carga ruidosa no puede dejar el repositorio bloqueado durante una semana.
   - **Guardas contra falsos positivos:** si `dropped_iterations > 0` o la variación entre VUs supera el 20 %, la ejecución se **descarta como inválida** y se repite una vez antes de decidir. Un resultado de una máquina sobrecargada no es una regresión de código.

3. Ejecución distribuida con el **k6 Operator** (`TestRun`) para generar más carga que un solo nodo:
   ```yaml
   apiVersion: k6.io/v1alpha1
   kind: TestRun
   metadata: { name: spike }
   spec:
     parallelism: 8
     script: { configMap: { name: k6-scripts, file: spike.js } }
   ```
4. Enviar los resultados a Prometheus con *remote write* (`--out experimental-prometheus-rw`; habilitar el receptor de *remote write* en Prometheus) y usar un *dashboard* de k6 en Grafana; etiquetar con `testid`.
5. Dimensionar el **generador de carga**: CPU < 80 %, red suficiente; vigilar `dropped_iterations`.
6. Plantilla de **reporte** en Confluence: objetivo, configuración, resultados (RPS, p50/p95/p99, tasa de error), cuellos de botella, acciones y comparación con la línea base.
7. **Salvaguardas:** prohibido ejecutar contra producción sin aprobación escrita; datos de prueba aislados; *kill switch* documentado; avisar al proveedor de nube/pasarela si aplica.
8. Obtener la **capacidad máxima sostenible** con una prueba *breakpoint* y usarla para fijar límites de HPA, cuotas de DB y tasa de admisión de la sala de espera.

**Criterios de Aceptación (CA):**
- **La regresión de p99 de `hold` > 15 % respecto de la línea base versionada falla la pipeline de *staging* y bloquea el merge** (B-22), y el caso se verifica con una ejecución artificial que inyecta un slowdown conocido (un *sleep* de 30 ms en el camino de `hold`), que **debe** ser detectado.
- Un PR normal (sin cambios en rutas calientes) **no** es bloqueado por el `smoke` de 60 s; y el PR etiquetado `perf` obtiene un resultado de regresión en < 15 min.
- El umbral de 15 % está justificado en el repo con la desviación típica medida entre 10 corridas equivalentes del mismo código.
- Una ejecución con `dropped_iterations > 0` se marca como inválida y no genera alarma de regresión.
- Cada reporte es reproducible: versión del código (SHA), configuración, *seed* de datos, línea base usada y dashboards enlazados.
- La prueba *breakpoint* documenta la capacidad máxima (RPS) y el primer recurso que se satura.

**Casos de Uso:**
- **Happy Path:** La ejecución nocturna pasa; el reporte se archiva y la tendencia semanal es estable.
- **Failure Path:** La ejecución nocturna falla por un aumento de latencia tras un cambio de índice; el reporte apunta a la consulta culpable vía trazas y se revierte.

### HU 11.4 - Pruebas de Caos y Resistencia (Soak) bajo Carga
`[NUEVA]`

**Descripción:** Como SRE, quiero inyectar fallos mientras el sistema está bajo carga, para verificar que la tolerancia a fallos funciona de verdad y no solo en el diseño.

**Tareas de Implementación:**
1. Método (por cada experimento): **hipótesis** → estado estable medible → fallo → observación → conclusión; definir radio de impacto y **condición de aborto**.
2. Catálogo de experimentos mientras corre k6:

   | # | Fallo | Hipótesis esperada |
   |---|---|---|
   | 1 | Eliminar 30 % de los pods de `api` | 0 pérdida de peticiones confirmadas; recuperación < 1 min |
   | 2 | Matar el primario de `redis-locks` | 503 breves (< 15 s), **0 ventas dobles**, reconciliación OK |
   | 3 | Matar 1 broker de Kafka | Producción continúa; sin pérdida; lag se recupera |
   | 4 | *Failover* de PostgreSQL (Multi-AZ) | Errores < 60 s; el *outbox* se recupera; sin datos perdidos |
   | 5 | +3 s de latencia en la pasarela (Toxiproxy) | *Breaker* abre; `checkout` degradado pero estable |
   | 6 | Pérdida de un nodo/AZ | Réplicas reprogramadas; SLO sostenido |
   | 7 | Saturar PgBouncer | *Load shedding* y 503 controlados; sin cascada |

3. Herramientas: Chaos Mesh o LitmusChaos (en K8s), AWS FIS (infraestructura), Toxiproxy (red), `kubectl delete`/`drain`.
4. **Soak test** de 4–8 h al 60 % de capacidad: vigilar crecimiento de heap (JFR/heap dumps), fugas de conexiones, estabilidad del *lag*, crecimiento de disco y volumen de logs.
5. Realizar un **GameDay** trimestral con el equipo y el runbook en mano (HU 12.3).

**Criterios de Aceptación (CA):**
- En **todos** los experimentos: `increase(seat_state_drift_total[1h]) == 0` (deriva entre Redis y la DB), ningún pago aprobado queda sin orden o reembolso tras la conciliación, y las consultas SQL 1–4 de HU 11.2 devuelven 0 filas. La métrica `invariant_double_sale_total` de la v2.0 se elimina: nunca podía disparar (B-05).
- Tiempo de recuperación de cada experimento dentro de lo declarado en su hipótesis, **sin intervención manual**.
- El *soak* no muestra crecimiento sostenido de memoria (> 5 % en 4 h tras estabilización) ni de conexiones.
- **Experimento 2 (matar el primario de `redis-locks`) deja `seat_state_drift_current == 0` al recuperar**, y la ejecución de reconciliación de HU 12.1 reconstruye `unavailable:*` completo desde la DB sin pérdida. Con `noeviction` (ADR-013) y réplicas, no se pierde ninguna escritura confirmada.

**Casos de Uso:**
- **Happy Path:** Se mata el primario de Redis en pleno pico; la alerta dispara, el clúster promueve la réplica y el sistema se recupera sola en segundos.
- **Failure Path:** El experimento revela que los *clients* no refrescan la topología y siguen apuntando al primario muerto; se corrige la configuración de Lettuce (HU 05.3) y se repite el experimento hasta pasar.
- **Failure Path (B-05):** El proyector de disponibilidad queda caído 30 min durante el experimento 1. Al volver, la deriva `sold_not_in_redis` salta, se congela la venta del evento afectado, se relanza el proyector desde el tópico de archivo (B-31) y la alerta se resuelve sin intervención manual en el camino crítico. Sin esta alerta (la de la v2.0) el retraso del proyector habría pasado **desapercibido**, porque la doble venta es imposible por construcción.

## Épica 12: Seguridad, Operación y Go-Live

**Objetivo de aprendizaje:** lo que separa un proyecto que funciona de un servicio en producción: respaldos, seguridad, procesos de incidentes, revisión de preparación y control de costos.

### HU 12.1 - Backups, Recuperación Puntual (PITR) y Recuperación ante Desastres
`[NUEVA]`

**Descripción:** Como responsable de la plataforma, quiero poder recuperar los datos y reconstruir el entorno tras un desastre, dentro de objetivos de RPO/RTO conocidos.

**Tareas de Implementación:**
1. **PostgreSQL (RDS):** *backups* automáticos con retención de 14 días, **PITR** habilitado, Multi-AZ, *snapshot* manual antes de migraciones riesgosas y copia de *snapshots* a otra región.
2. **Ensayo de restauración mensual:** restaurar a un instante concreto en una instancia nueva, ejecutar verificaciones de integridad (las consultas de HU 11.2) y medir el RTO real.
3. **Kafka:** RF = 3; los eventos son reproducibles desde el *outbox*/tópicos; evaluar MirrorMaker 2 para un DR entre regiones (opcional).
4. **Redis:** reconstruible por diseño: los conjuntos `unavailable:*` se regeneran desde la DB (HU 04.5) y, si hiciera falta, desde el tópico de archivo (B-31); la pérdida de la cola es aceptable con reingreso (HU 04.3). El procedimiento de reconciliación está en el runbook `redis-rebuild` (HU 12.3).
5. **Infraestructura como cattle:** reconstruir cluster + plataforma desde Terraform + ArgoCD (*bootstrap*) en ≤ 60 min; estado de Terraform versionado y respaldado.
6. Documentar un **runbook de DR** con tabla de RPO/RTO por componente:

   | Componente | RPO | RTO | Mecanismo |
   |---|---|---|---|
   | PostgreSQL | ≤ 5 min | ≤ 1 h | PITR / Multi-AZ |
   | Kafka | 0 (RF=3) / reproducible | ≤ 30 min | Réplicas + outbox |
   | Redis | n/a (reconstruible) | ≤ 15 min | Reconciliación |
   | Cluster K8s | n/a | ≤ 60 min | Terraform + GitOps |

**Criterios de Aceptación (CA):**
- El ensayo de restauración PITR a `T-5 min` finaliza con datos íntegros y un RTO medido ≤ 1 h; el resultado se archiva.
- Reconstruir un entorno *staging* desde cero con Terraform + ArgoCD funciona sin pasos manuales no documentados.
- Los *snapshots* y el estado de Terraform están cifrados y versionados.

**Casos de Uso:**
- **Happy Path:** Un `DELETE` accidental en producción se recupera restaurando a 2 minutos antes y reinsertando las filas afectadas.
- **Failure Path:** Se pierde una AZ completa; Multi-AZ promueve la réplica y el servicio vuelve en minutos; si se pierde la región, se ejecuta el runbook de DR.

### HU 12.2 - Seguridad Perimetral, de Cluster y de Datos
`[NUEVA]`

**Descripción:** Como responsable de seguridad, quiero defensa en profundidad desde el borde hasta los datos, para proteger a los usuarios y cumplir con las normativas aplicables.

**Tareas de Implementación:**
1. **Borde:** CDN + WAF con reglas administradas, control de bots y reglas de tasa; protección DDoS; TLS 1.2+ (preferir 1.3) y HSTS.
2. **Cifrado:** en tránsito (TLS interno hacia RDS, ElastiCache, Kafka) y en reposo (KMS en RDS, EBS, S3, ElastiCache).
3. **Kubernetes:** *Pod Security* `restricted`, `NetworkPolicies` *default-deny*, políticas de admisión (Kyverno/Gatekeeper): imágenes **firmadas** (cosign), sin `latest`, con `requests/limits` y sin *root*.
4. **IAM de mínimo privilegio** (IRSA por servicio), auditoría (CloudTrail, *audit logs* de K8s) y revisión periódica de accesos.
5. **Pruebas de seguridad:** DAST (OWASP ZAP *baseline*) contra *staging* en CI, revisión contra OWASP ASVS (nivel 2) y API Security Top 10, y *pentest* externo antes del lanzamiento.
6. **Datos personales:** inventario de datos, minimización, retención y acceso; endpoints de **exportación y eliminación de cuenta** (anonimizar datos personales conservando los registros fiscales/contables exigidos). Considerar la normativa aplicable (p. ej. Ley 25.326 de Protección de Datos Personales en Argentina; GDPR si hay usuarios en la UE) y **validarlo con asesoría legal**.
7. **PCI:** documentar el alcance (checkout alojado del proveedor → cuestionario SAQ A) y verificar que nunca se procesan datos de tarjeta.
8. Gestión de **vulnerabilidades**: Renovate/Dependabot, SLA de parcheo (CRITICAL ≤ 7 días), SBOM por release.

**Criterios de Aceptación (CA):**
- ZAP *baseline* sin hallazgos de severidad alta; el *pentest* no deja hallazgos críticos abiertos al momento del lanzamiento.
- Una imagen sin firma válida es **rechazada** por el *admission controller*.
- Un escaneo de puertos desde Internet no encuentra PostgreSQL, Redis, Kafka ni el puerto de gestión (8081) expuestos.
- El flujo de eliminación de cuenta anonimiza datos personales y conserva los registros financieros.

**Casos de Uso:**
- **Happy Path:** El WAF bloquea un barrido de bots antes de que llegue al Gateway.
- **Failure Path:** Se descubre una librería con CVE crítico; Renovate abre el PR, el pipeline lo valida y se despliega en < 24 h por el camino normal.

### HU 12.3 - Runbooks y Gestión de Incidentes
`[NUEVA]`

**Descripción:** Como equipo de guardia, quiero procedimientos escritos y un proceso de incidentes claro, para resolver problemas rápido y aprender de ellos.

**Tareas de Implementación:**
1. Plantilla de **runbook**: síntoma/alerta → impacto → diagnóstico (dashboards, consultas LogQL/PromQL/SQL) → mitigación paso a paso → escalamiento → verificación → seguimiento.
2. Runbooks iniciales: `hold-error-budget`, `pgbouncer-saturation`, `redis-failover`, **`redis-rebuild`**, `redis-memory-pressure`, `kafka-lag-dlt-reprocess`, `outbox-stuck`, **`seat-state-drift`** (era `double-sale-invariant` en la v2.0; ver B-05: el incidente real es la **deriva entre Redis y la DB**, no una doble venta imposible por construcción), `payment-provider-outage`, `rate-limit-false-positives`, `certificate-expiry`, `db-failover`, `rollback-release`, `pre-scaling-big-onsale`.
3. **Proceso de incidentes:** roles (comandante, comunicaciones, operaciones), severidades SEV1–SEV3 con objetivos de respuesta, canal dedicado, página de estado y plantillas de comunicación.
4. **Postmortem sin culpables** en ≤ 5 días hábiles para SEV1/SEV2, con acciones con responsable y fecha.
5. Rotación de guardia, traspasos documentados y matriz de escalamiento.
6. Medir **MTTA** y **MTTR**, y revisar la salud de la guardia (carga y fatiga).

**Criterios de Aceptación (CA):**
- Toda alerta *page* enlaza a un runbook existente; cada runbook fue **ejecutado por una persona que no lo escribió** en un GameDay.
- Cada incidente SEV1/SEV2 tiene postmortem publicado y acciones rastreadas.
- Existe un procedimiento verificado para el incidente `seat-state-drift` (congelar ventas del evento, relanzar el proyector, reconciliar `unavailable:*` desde la DB, reembolsar los afectados, comunicar). El antiguo `double-sale-invariant` no puede tener runbook porque no puede ocurrir: la doble venta la impide el `UPDATE` condicional más la restricción parcial. El runbook documenta **cómo se verifica que no ocurre** (consultas SQL 1–2 de HU 11.2, ejecutadas a demanda) y **qué hacer cuando lo que falla es la réplica de Redis**.

**Casos de Uso:**
- **Happy Path:** Un *page* a las 3 a. m. se resuelve en 15 min siguiendo el runbook, sin escalar.
- **Failure Path:** El runbook está desactualizado respecto del sistema; durante el postmortem se corrige y se agrega una verificación periódica.

### HU 12.4 - Production Readiness Review (PRR) y Plan de Lanzamiento
`[NUEVA]`

**Descripción:** Como equipo, quiero una revisión formal previa al lanzamiento y un plan gradual, para salir a producción con riesgos conocidos y controlados.

**Checklist de preparación (todos deben estar marcados o con excepción aprobada):**

- [ ] **Fiabilidad:** SLOs definidos y con paneles; alertas *page* con runbook; *breakers*, *timeouts* y *load shedding* verificados (HU 05.4).
- [ ] **Rendimiento:** prueba *spike* a **150 % del pico esperado** superada; *breakpoint* documentado (HU 11.x); preescalado ensayado.
- [ ] **Corrección:** prueba "cero sobreventa" verde, incluso bajo caos (HU 11.2, 11.4).
- [ ] **Datos:** backups y **restauración ensayada**; migraciones *expand/contract*; reconciliación operativa.
- [ ] **Despliegue:** *rollback* ensayado en < 5 min; *canary* con análisis automático; *feature flags*.
- [ ] **Seguridad:** *pentest* sin críticos; secretos rotables; sin puertos públicos indebidos; PCI/privacidad documentados.
- [ ] **Observabilidad:** métricas, trazas y logs correlacionados; tablero de lanzamiento listo.
- [ ] **Operación:** guardia asignada, escalamiento, página de estado, plantillas de comunicación.
- [ ] **Costos:** presupuestos y alertas activos; límites de autoescalado definidos.
- [ ] **Documentación:** ADRs, runbooks, diagramas y mapa de dependencias en Confluence.

**Plan de lanzamiento gradual:**
1. *Dark launch* interno (empleados) → 2. *Beta* por invitación → 3. Eventos pequeños reales → 4. Eventos medianos → 5. Primer evento de alta demanda con **sala de espera activa**.
- Congelar cambios no esenciales 48 h antes de una apertura grande; *war room* durante la apertura; plan de *rollback* y de comunicación acordado; *go/no-go* con criterios objetivos.

**Criterios de Aceptación (CA):**
- La PRR está firmada por al menos dos personas, con excepciones documentadas y con fecha de cierre.
- El ensayo general con k6 al 150 % del pico cumple los SLOs de los usuarios admitidos.
- El *rollback* completo se ejecuta en < 5 min en un ensayo cronometrado.

**Casos de Uso:**
- **Happy Path:** El primer evento grande se abre con sala de espera, preescalado y *war room*; los SLOs se cumplen y se cierra con un reporte.
- **Failure Path:** La PRR detecta que la restauración de backup nunca se ensayó; se posterga el lanzamiento hasta completarla.

### HU 12.5 - Costos (FinOps) y Limpieza de Entornos
`[NUEVA]`

**Descripción:** Como responsable del proyecto, quiero controlar el gasto cloud, para poder sostener el entorno de aprendizaje y de producción sin sorpresas.

**Tareas de Implementación:**
1. **Etiquetado obligatorio** (`project`, `env`, `owner`) con política de etiquetas y verificación (AWS Config/Terraform).
2. **Presupuestos y alertas** al 50 %, 80 % y 100 % del gasto mensual, con aviso al canal del equipo.
3. **Apagado programado de *staging*** (escala a cero fuera de horario) y entornos efímeros destruidos con `terraform destroy` al terminar cada práctica.
4. *Right-sizing* con las recomendaciones de VPA/Prometheus; instancias *spot* para `worker` y cargas tolerantes a interrupciones.
5. Revisar costos ocultos: NAT, transferencia entre AZ, retención de logs/trazas, *snapshots* e imágenes antiguas (políticas de ciclo de vida en ECR/S3).
6. Métrica de negocio: **costo por ticket vendido** y revisión mensual.

**Criterios de Aceptación (CA):**
- No existen recursos sin etiquetar en la cuenta (reporte semanal).
- El apagado programado de *staging* reduce su costo en **≥ 50 %**.
- Las alertas de presupuesto están activas y probadas.

**Casos de Uso:**
- **Happy Path:** Tras una práctica de *failover*, el entorno efímero se destruye y el costo vuelve a la línea base.
- **Failure Path:** Un NAT Gateway olvidado acumula costos; la alerta al 80 % lo detecta a mitad de mes.

### Anexo D — Glosario mínimo

- **ACID / MVCC:** propiedades transaccionales / control de concurrencia multiversión de PostgreSQL.
- **KRaft:** modo de Kafka con quórum Raft propio, sin ZooKeeper.
- **ISR:** *In-Sync Replicas*, réplicas al día que pueden aceptar un `acks=all`.
- **Outbox:** patrón que guarda el evento en la misma transacción que el cambio de negocio y lo publica después.
- **Idempotencia:** repetir una operación produce el mismo efecto que ejecutarla una vez.
- **SLI / SLO / presupuesto de error:** indicador medido / objetivo sobre él / margen de fallo permitido.
- **Burn rate:** velocidad con la que se consume el presupuesto de error.
- **Hash tag:** parte de la clave entre llaves `{}` que determina el *slot* en Redis Cluster.
- **Cache stampede:** avalancha de lecturas a la DB cuando expira una clave caliente.
- **Tail sampling:** decidir qué trazas conservar *después* de verlas completas.
- **Modelo abierto/cerrado (carga):** llegadas independientes de la latencia / usuarios que esperan la respuesta antes de reintentar.
