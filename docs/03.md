## Épica 03: Modelo de Datos, Persistencia e Índices

**Objetivo de aprendizaje:** modelado relacional, Flyway, MVCC, planes de ejecución, *index-only scans*, autovacuum y *connection pooling* con PgBouncer.

### HU 03.1 - Esquema SQL Relacional e Inmutabilidad de Precios
`[ORIGINAL · AMPLIADA]`

**Descripción:** Como arquitecto de datos, quiero definir tablas normalizadas, para asegurar integridad transaccional y registro histórico de precios.

**Tareas de Implementación:**
1. Crear scripts de migración con **Flyway** (`V1__core_schema.sql`, …) para `users`, `venues`, `events`, `price_tiers`, `seats`, `orders` y `order_items`. Las tablas `refresh_tokens` y `audit_log` se crean en HU 02.3 y 02.4 (`V2__`, `V3__`); `payments`, `idempotency_keys`, `outbox_events`, `processed_events` y `tickets` se agregan en las HU 06.x y 07.x con migraciones posteriores. **El orden de versiones de Flyway es fijo y no se reutiliza:** cada tabla nueva ocupa la siguiente versión.
2. Definir *Foreign Keys* y restricciones `NOT NULL`/`CHECK` (estados válidos, importes ≥ 0).
3. Configurar el guardado del `price_paid` en `order_items` de forma independiente al precio actual del catálogo, en **unidades menores** (`bigint`, p. ej. centavos) junto a `currency char(3)`; evitar `float`/`double`.
4. Hacer `price_paid` **inmutable a nivel de base de datos** mediante un *trigger* (no solo por convención de la aplicación).
5. Usar `timestamptz` para toda marca temporal y `uuid` (idealmente v7, ordenable) para identificadores expuestos públicamente.
6. Agregar un **índice único parcial** que impida que un mismo asiento tenga dos ítems de orden activos (última línea de defensa contra la sobreventa).
7. Probar las migraciones con **Testcontainers** (levantar PostgreSQL, aplicar Flyway, verificar restricciones) y ejecutar `flyway validate` en CI.

> **Decisión de modelado:** la tabla `seats` representa el **inventario por evento** (una fila por asiento por evento). La geometría para dibujar el mapa (coordenadas, SVG) es estática y se sirve como archivo versionado por CDN (HU 04.6), no se almacena en la tabla caliente. El estado `HELD` **no existe en la DB**: las retenciones temporales viven en Redis; la DB solo conoce `AVAILABLE`, `SOLD` y `BLOCKED`. Esto reduce drásticamente las escrituras sobre `seats`.

**Referencia (`V1__core_schema.sql`, extracto):**

```sql
CREATE EXTENSION IF NOT EXISTS citext;
CREATE TYPE seat_status AS ENUM ('AVAILABLE', 'SOLD', 'BLOCKED');

-- v2.0 la referenciaba como FK desde events pero nunca la creaba (B-37).
-- Sin esta tabla la migracion no corre: no hay de donde sembrar nada.
CREATE TABLE venues (
  id          uuid PRIMARY KEY DEFAULT uuid_generate_v7(),
  name        text   NOT NULL,
  address     text   NOT NULL,
  timezone    text   NOT NULL,                 -- IANA, p.ej. 'America/Argentina/Buenos_Aires'
  capacity    integer NOT NULL CHECK (capacity > 0),
  map_asset_url text,                          -- CDN; la geometria NO va en la DB (HU 04.6)
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE users (
  id             uuid PRIMARY KEY,
  email          citext NOT NULL UNIQUE,
  password_hash  text   NOT NULL,
  role           text   NOT NULL CHECK (role IN ('CUSTOMER','ORGANIZER','SUPPORT','ADMIN')),
  email_verified boolean NOT NULL DEFAULT false,
  created_at     timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE events (
  id             uuid PRIMARY KEY,
  venue_id       uuid NOT NULL REFERENCES venues(id),
  title          text NOT NULL,
  starts_at      timestamptz NOT NULL,
  sales_open_at  timestamptz NOT NULL,
  status         text NOT NULL CHECK (status IN ('DRAFT','ON_SALE','SOLD_OUT','CANCELLED','FINISHED')),
  currency       char(3) NOT NULL DEFAULT 'ARS'
);

CREATE TABLE price_tiers (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  event_id    uuid   NOT NULL REFERENCES events(id),
  name        text   NOT NULL,
  price_minor bigint NOT NULL CHECK (price_minor >= 0),
  UNIQUE (event_id, name)
);

CREATE TABLE seats (                       -- inventario por evento
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  event_id      uuid   NOT NULL REFERENCES events(id),
  price_tier_id bigint NOT NULL REFERENCES price_tiers(id),
  section       text   NOT NULL,
  seat_row      smallint NOT NULL,
  seat_column   smallint NOT NULL,
  status        seat_status NOT NULL DEFAULT 'AVAILABLE',
  version       integer NOT NULL DEFAULT 0,
  updated_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (event_id, section, seat_row, seat_column)
);

CREATE TABLE orders (
  id          uuid PRIMARY KEY,
  user_id     uuid NOT NULL REFERENCES users(id),
  event_id    uuid NOT NULL REFERENCES events(id),
  status      text NOT NULL CHECK (status IN
    ('PENDING_PAYMENT','PAID','FULFILLED','EXPIRED','CANCELLED','PAYMENT_FAILED','REFUNDED')),
  total_minor bigint NOT NULL CHECK (total_minor >= 0),
  currency    char(3) NOT NULL,
  expires_at  timestamptz NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id    uuid   NOT NULL REFERENCES orders(id),
  event_id    uuid   NOT NULL REFERENCES events(id),
  seat_id     bigint NOT NULL REFERENCES seats(id),
  price_paid  bigint NOT NULL CHECK (price_paid >= 0),   -- unidades menores, fijado al crear la orden
  currency    char(3) NOT NULL,
  released_at timestamptz                                -- NULL = ítem activo
);

-- Un asiento no puede tener dos ítems activos, pase lo que pase en Redis
CREATE UNIQUE INDEX ux_order_items_active_seat ON order_items (seat_id) WHERE released_at IS NULL;

-- Inmutabilidad del precio pagado
CREATE FUNCTION forbid_price_update() RETURNS trigger AS $$
BEGIN
  IF NEW.price_paid IS DISTINCT FROM OLD.price_paid
     OR NEW.currency IS DISTINCT FROM OLD.currency THEN
    RAISE EXCEPTION 'price_paid/currency son inmutables' USING ERRCODE = 'integrity_constraint_violation';
  END IF;
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_order_items_price_immutable
  BEFORE UPDATE ON order_items FOR EACH ROW EXECUTE FUNCTION forbid_price_update();
```

> **`venues` era una referencia colgante (B-37).** `events.venue_id` declara `REFERENCES venues(id)` desde la v1.0 del plan, pero ninguna HU creaba la tabla. PostgreSQL rechaza la migración, así que el hueco era visible en el primer `flyway migrate`; lo grave es que, si alguien lo "resolvía" improvisando, quedaba fuera del modelo de datos documentado. La tabla está arriba, con `timezone` explícito porque los eventos se venden por horario local y sin él el `starts_at` es ambiguo.
>
> **`price_minor` y `capacity`:** una sola moneda por evento y **2 decimales** fijos (ADR-015, B-41). El tipo sigue siendo `bigint` en unidades menores porque es lo correcto para dinero, pero el esquema **no** sirve para monedas sin subdivision decimal (JPY, KWD) sin una migración.

**Sobre la columna `version` de `seats` (B-09, B-38):**

La v2.0 la declaraba en el DDL, exigía `AND version = :v` en la tarea 2 de HU 04.2 y no la usaba en ninguna parte: el `UPDATE` real va solo por `status`, y con ADR-012 (Spring JDBC, sin ORM) `@Version` no existe. La v3.0 toma una decisión explícita en lugar de dejar la columna muerta:

- **La condición de `confirmSale` es el estado, no el versión.** `WHERE status = 'AVAILABLE'` ya es la comparación atómica que evita la sobreventa: si dos transacciones concurrentes leen el mismo asiento, solo una ve el `UPDATE` afectar una fila. Agregar `AND version = :v` obligaría a leer `version` antes, en otro round-trip, sin aportar nada.
- **`version` se queda** porque sirve para dos cosas reales: detectar escrituras fuera de banda durante la reconciliación de HU 04.5 (un `UPDATE` que no incrementa `version` es suspecto) y diagnosticar Lost Update en los logs. La tarea 2 de HU 04.2 se reescribe para reflejar esto.
- Si al implementar la reconciliación resulta que no aporta, se elimina con una migración `V…__drop_seats_version.sql` y el CA correspondente. Queda anotado como decisión a revisar, no como deuda invisible.

**Criterios de Aceptación (CA):**
- No se pueden insertar compras huérfanas (sin `user_id` o `event_id` válido): la inserción falla con SQLSTATE `23503`.
- Cambiar el precio de un evento (`price_tiers.price_minor`) no altera el valor registrado en compras pasadas; un `UPDATE order_items SET price_paid = ...` falla por el *trigger*.
- No pueden existir dos `order_items` activos (`released_at IS NULL`) para el mismo `seat_id` (violación `23505`).
- `flyway validate` pasa en CI y las migraciones aplicadas nunca se editan (los cambios van en versiones nuevas).
- Ningún importe se almacena como punto flotante.

**Casos de Uso:**
- **Happy Path:** Se procesa una orden y el asiento queda vinculado permanentemente al usuario y al precio del momento de compra.
- **Failure Path:** Intento de inserción de un `seat_id` inexistente provoca un *rollback* transaccional por violación de FK (`23503`) y la API responde `409`/`422` según el caso, sin dejar filas parciales.

**Hallazgos de la auditoría:** el modelo omitía `users`, `payments`, `tickets`, `outbox`, `idempotency_keys`; no definía el tipo del dinero ni garantizaba la inmutabilidad a nivel de DB; faltaba la defensa de unicidad por asiento. Escalado futuro: si `order_items` supera ~100 M de filas, evaluar particionado por rango temporal.

**Correcciones de la segunda auditoría (v3.0):**
- **B-37:** `venues` estaba referenciada como FK y no existía. DDL agregado. También se fija el orden de versiones de Flyway para que `refresh_tokens` (`V2`), `audit_log` (`V3`), `payments`/`idempotency_keys` (`V4`) y `outbox_events`/`processed_events` (`V5`) no colisionen.
- **B-09 / B-38:** la columna `version` y su condición `AND version = :v` quedan explicadas en lugar de contradictorias (ver nota arriba).
- **B-41:** se documenta explícitamente el supuesto de 2 decimales y por qué el esquema no sirve para JPY/KWD.
- **B-17:** ADR-012 fija Spring JDBC + Flyway, sin ORM; no hay `@Version` de JPA en ningún punto del plan.

### HU 03.2 - Índices Compuestos e Index-Only Scans
`[ORIGINAL · AMPLIADA]`

**Descripción:** Como DBA, quiero configurar índices estratégicos, para optimizar las consultas masivas de disponibilidad de asientos.

**Tareas de Implementación:**
1. Crear índice compuesto en la tabla `seats` **incluyendo todas las columnas que devuelve la consulta del mapa** (incluido `id`, necesario para reservar):
   ```sql
   CREATE INDEX idx_seats_event_status
     ON seats (event_id, status)
     INCLUDE (id, section, seat_row, seat_column);
   ```
   Si la consulta dominante es por sección, evaluar `(event_id, section, status)`.
2. Ejecutar `EXPLAIN (ANALYZE, BUFFERS)` sobre la consulta real y verificar `Index Only Scan` con `Heap Fetches: 0` (o muy cercano a 0).
3. Habilitar `pg_stat_statements` y registrar la latencia de la consulta.
4. Ajustar **autovacuum** de la tabla (el *visibility map* debe estar al día para que el *index-only scan* no vaya al *heap*):
   ```sql
   ALTER TABLE seats SET (autovacuum_vacuum_scale_factor = 0.02,
                          autovacuum_analyze_scale_factor = 0.02,
                          fillfactor = 90);
   ```
5. Tras cada carga masiva de asientos de un evento nuevo, ejecutar `VACUUM (ANALYZE) seats;` como paso del proceso de alta del evento (tarea de HU 13.1).
6. Incluir un test de integración que falla si el plan deja de ser *Index Only Scan* (regresión de rendimiento).
7. **Índice para la reconciliación (B-28).** El índice de arriba sirve para `WHERE event_id = $1 AND status = ...`, pero la reconciliación de HU 04.5 consulta `WHERE status = 'SOLD'` **sin** `event_id`: con `idx_seats_event_status (event_id, status, …)` eso es un *seq scan* de la tabla entera, que con millones de filas no termina. Índice parcial dedicado:
   ```sql
   CREATE INDEX idx_seats_sold_reconciliation
     ON seats (id, event_id)
     WHERE status = 'SOLD';
   ```
   Es pequeño (solo los vendidos, que además decrecen con el tiempo) y la reconciliación **siempre** se ejecuta acotada a un evento (`WHERE status = 'SOLD' AND event_id = $1`), lo que además evita que una sola corrida barra el histórico de todos los eventos.

**Consulta objetivo:**

```sql
SELECT id, section, seat_row, seat_column, status
FROM seats
WHERE event_id = $1 AND status = 'AVAILABLE';
```

**Criterios de Aceptación (CA):**
- Las consultas del frontend para renderizar el mapa de asientos de una **sección (≤ 2 000 asientos)** resuelven con un *Index-Only Scan*.
- El tiempo de respuesta de la base de datos es inferior a **10 ms (p99)** por consulta de sección, medido con `pg_stat_statements`.
- El mapa de **un evento completo** (decenas de miles de asientos) **no** se sirve desde PostgreSQL en el camino caliente: se resuelve desde CDN/Redis (HU 04.6).
- Tras una carga masiva y su `VACUUM`, `Heap Fetches` es < 1 % de las filas devueltas.
- La consulta de reconciliación `WHERE status='SOLD' AND event_id = $1` resuelve con el índice parcial `idx_seats_sold_reconciliation` y **no** con un *Seq Scan* (B-28). El test mide el nodo `Seq Scan` del `EXPLAIN` y falla si aparece.

**Casos de Uso:**
- **Happy Path:** Ráfagas de consultas de disponibilidad leen directamente del índice en memoria, liberando carga de I/O en disco.
- **Failure Path:** La falta de `VACUUM` (o estadísticas desactualizadas) degrada el rendimiento: con el *visibility map* incompleto aparecen *Heap Fetches* (el plan sigue siendo *Index Only Scan* pero lee la tabla) y, con estadísticas muy erróneas, el planificador puede elegir un *Sequential Scan*. Se corrige con `VACUUM (ANALYZE) seats;` y afinando autovacuum.

**Hallazgos de la auditoría:** (1) el índice no incluía `id` ni `section`, de modo que la consulta real **no** era *index-only* (A-08); (2) un *Index-Only Scan* depende de `VACUUM`, no solo del índice; (3) el CA de 10 ms era irreal para un estadio completo; (4) como `status` es columna indexada, sus actualizaciones no pueden ser *HOT* y generan *churn* en el índice: se tolera porque, al vivir los *holds* en Redis, cada asiento se actualiza **una sola vez** (a `SOLD`).

**Correcciones de la segunda auditoría (v3.0):**
- **B-28:** se agrega `idx_seats_sold_reconciliation`, índice parcial `(id, event_id) WHERE status='SOLD'`. El índice original no puede servir un filtro solo por `status` porque `event_id` es su primera columna: la reconciliación de HU 04.5 hacía *seq scan* de la tabla completa. Además la reconciliación se acota por evento.

### HU 03.3 - PgBouncer y Dimensionamiento de Conexiones
`[NUEVA]`

**Descripción:** Como DBA/SRE, quiero un pool de conexiones externo, para soportar miles de clientes concurrentes sin agotar `max_connections` de PostgreSQL.

**Tareas de Implementación:**
1. Desplegar PgBouncer (≥ 2 réplicas detrás de un `Service`) en modo **`transaction`**.
2. Configurar `pgbouncer.ini`:
   ```ini
   [databases]
   tickets = host=postgres port=5432 dbname=tickets

   [pgbouncer]
   pool_mode = transaction
   max_client_conn = 2000
   default_pool_size = 25
   reserve_pool_size = 5
   reserve_pool_timeout = 3
   query_wait_timeout = 5
   server_idle_timeout = 600
   max_prepared_statements = 200   ; PgBouncer >= 1.21
   auth_type = scram-sha-256
   ```
3. Dimensionar con la regla: `Σ(pools de PgBouncer) + conexiones directas (migraciones, admin, réplicas, Debezium) < max_connections`. Dejar ~10 % de margen.
4. En la app (HikariCP): `maximum-pool-size` **pequeño** (10–20 por pod), `connection-timeout` corto (2 s). Con hilos virtuales **no** escalar el pool al número de hilos: la DB es el recurso escaso; limitar concurrencia con un *semáforo/bulkhead*.
5. Compatibilidad con *transaction pooling*:
   - Prepared statements: con PgBouncer ≥ 1.21 y `max_prepared_statements > 0` se soportan; en versiones previas, `prepareThreshold=0` en el JDBC URL.
   - **No** usar `pg_advisory_lock` de sesión; usar `pg_advisory_xact_lock`.
   - **No** depender de `SET` de sesión ni de `LISTEN/NOTIFY` a través del pool.
6. Flyway y Debezium conectan **directo** a PostgreSQL (no a través de PgBouncer).
7. Exportar métricas con `pgbouncer_exporter` (`cl_waiting`, `sv_active`, `maxwait`, `avg_query_time`) y alertar sobre saturación.

**Criterios de Aceptación (CA):**
- Con 2 000 clientes concurrentes en un test de carga, las conexiones reales a PostgreSQL no superan el `default_pool_size` configurado (verificable con `SHOW POOLS;`).
- Con el pool saturado, la API devuelve `503` con `Retry-After` **antes** de superar el *timeout* del cliente y no se acumulan hilos bloqueados.
- Alerta `PgBouncerClientsWaiting` dispara cuando `cl_waiting > 0` sostenido por > 30 s.

**Casos de Uso:**
- **Happy Path:** 20 pods × 15 conexiones de Hikari = 300 conexiones cliente se multiplexan sobre ~25 conexiones reales a PostgreSQL.
- **Failure Path:** Una consulta lenta retiene conexiones del pool; `cl_waiting` crece y `query_wait_timeout` corta la espera. La app responde `503`, la alerta dispara y se investiga con `pg_stat_statements`/trazas.

## Épica 04: Motor de Reserva Atómica & Alta Concurrencia

**Objetivo de aprendizaje:** locks distribuidos y sus límites, Lua en Redis, Redis Cluster (*hash tags*), concurrencia optimista, control de admisión.

> **Principio rector:** *Redis decide rápido; PostgreSQL decide bien.* El lock en Redis es una optimización de rendimiento y experiencia (evita que miles de usuarios compitan por la DB). La **corrección** (no vender dos veces) la garantiza siempre la base de datos mediante restricciones y actualizaciones condicionales.

### HU 04.1 - Bloqueo Atómico de Asientos con Redis
`[ORIGINAL · AMPLIADA]`

**Descripción:** Como comprador, quiero bloquear mi asiento al seleccionarlo, para evitar que otro usuario lo compre simultáneamente.

**Tareas de Implementación:**
1. Implementar cliente Redis en el backend (**Lettuce**, con soporte de cluster) apuntando al cluster `redis-locks` (HU 05.3, ADR-013).
2. Diseñar las claves con **hash tags** para Redis Cluster: `hold:{<eventId>:<section>}:<seatId>`. Todo lo que está entre llaves determina el *slot*; así los asientos de una misma sección comparten slot y permiten scripts Lua atómicos multi-clave. Usar la **sección** (no el evento completo) como etiqueta distribuye el tráfico de un evento viral entre varios slots.
3. Ejecutar la reserva con **un único script Lua** (una sola ida y vuelta, atómico): verifica que el asiento no esté en el conjunto `unavailable:{evt:sec}` (vendidos **o bloqueados**), hace `SET ... NX PX 600000` (equivale a `NX EX 600`) con un **token de propiedad único**, congela el **precio** en `holdprice:{evt:sec}:{seat}` y registra el *hold* en un `ZSET` para poder listar los asientos retenidos (HU 04.6).
4. Liberar y extender el lock **siempre con *compare-and-delete*/*compare-and-expire*** en Lua (nunca `DEL` ciego).
5. Retornar confirmación de bloqueo (`201` con `token` y `expiresAt`) o error `409 Conflict` si la llave ya existe (`SEAT_ALREADY_HELD`) o el asiento ya está vendido o bloqueado (`SEAT_UNAVAILABLE`).
6. Limitar asientos por usuario/evento (p. ej. 6) para evitar acaparamiento.
7. Exigir **token de admisión** de la sala de espera (HU 04.3) en eventos con cola activa. Ese token es un JWT con `aud=waiting-room` (B-06) y **no** un *access token* de la API.
8. Instrumentar `seat.hold.latency` (histograma) y `seat.hold.total{result=ok|held|unavailable|error}`.

> **Por qué `unavailable:` y no `sold:` (B-01, crítico).** El enum `seat_status` tiene tres valores: `AVAILABLE`, `SOLD` y `BLOCKED`. La v2.0 solo consultaba `sold:{evt:sec}`, así que un asiento `BLOCKED` (reservado para producción, butacas de platea cortada, accessibility) se podía **retener y pagar**: el `hold` era exitoso, la orden se creaba, el pago se cobraba y recién al confirmar fallaba el `UPDATE ... WHERE status='AVAILABLE'`. El usuario pagaba y recibía un reembolso y un asiento que nunca podía tener. La corrección es mantener un solo conjunto `unavailable:{evt:sec}` que contiene tanto vendidos como bloqueados; el Lua pregunta por ese conjunto y no necesita distinguir el motivo.
>
> **Por qué el precio se congela en el hold (B-02, crítico).** El precio se leía al crear la orden, no al retener. Si el organizador cambia `price_tiers` entre el retain y el pago, el usuario ve un importe en el mapa y otro en la pantalla de pago, y paga el segundo. Congelar en el `hold` hace que el importe mostrado, el cobrado y el registrado en `order_items.price_paid` sean el mismo número, y que el cambio de precios solo afecte a retains nuevos.

**Referencia (`hold.lua`, v3.0):**

```lua
-- KEYS[1] = hold:{evt:sec}:<seat>          KEYS[2] = unavailable:{evt:sec}
-- KEYS[3] = holds:{evt:sec}                 KEYS[4] = holdprice:{evt:sec}:<seat>
-- ARGV[1] = seatId    ARGV[2] = token (userId:uuid)    ARGV[3] = ttlMs
-- ARGV[4] = expiresAtMs                     ARGV[5] = pricePaid (unidades menores)
--
-- Las cuatro KEYS comparten el mismo {hash tag}, asi que caen en el mismo slot
-- y el script es atomico en Redis Cluster.
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -1 end   -- vendido O bloqueado
if redis.call('SET', KEYS[1], ARGV[2], 'NX', 'PX', ARGV[3]) then
  redis.call('SET', KEYS[4], ARGV[5], 'PX', ARGV[3])                    -- B-02: precio congelado
  redis.call('ZADD', KEYS[3], ARGV[4], ARGV[1])
  return 1                                                               -- retenido por mi
end
return 0                                                                 -- retenido por otro
```

```lua
-- release.lua : KEYS[1]=hold key  KEYS[2]=holds zset  KEYS[3]=holdprice key
-- ARGV[1]=token  ARGV[2]=seatId
if redis.call('GET', KEYS[1]) == ARGV[1] then
  redis.call('ZREM', KEYS[2], ARGV[2])
  redis.call('DEL', KEYS[3])
  return redis.call('DEL', KEYS[1])
end
return 0
```

**Referencia (Java 21 / Spring):**

```java
@Service
class SeatHoldService {
    private static final Duration HOLD_TTL = Duration.ofMinutes(10);
    private final StringRedisTemplate redis;                 // conectado a redis-locks (ADR-013)
    private final RedisScript<Long> holdScript;              // carga lua/hold.lua

    // pricePaid llega congelado desde la consulta de catalogo; el hold lo persiste
    // en Redis para que la orden lo lea de ahi y no vuelva a leer price_tiers (B-02).
    HoldResult hold(UUID eventId, String section, long seatId, UUID userId, long pricePaid) {
        String tag   = "{" + eventId + ":" + section + "}";
        String token = userId + ":" + UUID.randomUUID();
        long expiresAt = Instant.now().plus(HOLD_TTL).toEpochMilli();
        Long r = redis.execute(holdScript,
            List.of("hold:" + tag + ":" + seatId,          // KEYS[1]
                    "unavailable:" + tag,                 // KEYS[2]  (SOLD + BLOCKED)
                    "holds:" + tag,                        // KEYS[3]
                    "holdprice:" + tag + ":" + seatId),    // KEYS[4]
            String.valueOf(seatId), token, String.valueOf(HOLD_TTL.toMillis()),
            String.valueOf(expiresAt), String.valueOf(pricePaid));
        return switch (r == null ? 0 : r.intValue()) {
            case 1  -> HoldResult.acquired(token, Instant.ofEpochMilli(expiresAt));
            case -1 -> HoldResult.unavailable();          // vendido o bloqueado
            default -> HoldResult.heldByOther();
        };
    }
}
```

**Criterios de Aceptación (CA):**
- El bloqueo es atómico: ante miles de peticiones simultáneas por el mismo asiento, **solo 1** obtiene respuesta exitosa y el resto recibe `409`. Verificado con un test de integración (1 000 hilos virtuales, `Executors.newVirtualThreadPerTaskExecutor()`) y con k6 a 10 000 VUs (HU 11.2).
- **Un asiento con `status='BLOCKED'` devuelve `409 SEAT_UNAVAILABLE` y nunca `201`** (B-01). El test siembra un asiento `BLOCKED` y hace `hold`; si el script regresara `1`, el CA falla. Este es el caso que la v2.0 no cubría.
- **El precio devuelto por el hold es el que la orden cobra** (B-02): test que (1) retiene con precio 10 000, (2) actualiza `price_tiers.price_minor` a 20 000, (3) crea la orden y verifica `order_items.price_paid = 10000`. La orden lee `holdprice:`; si leyera el catálogo, el CA falla con 20 000.
- El candado expira a los 10 minutos (600 s) con tolerancia de **±1 s** (verificado con TTL real en Testcontainers), y `holdprice:` expira con el mismo TTL.
- La operación de *hold* tiene **p99 < 5 ms** en Redis y p99 < 200 ms extremo a extremo.
- Liberar con un token ajeno **no** elimina el lock del dueño legítimo.
- Si Redis no está disponible, la API responde `503` rápido (*circuit breaker*, HU 05.4) y **nunca** concede asientos "a ciegas".
- Si el Lua recibe un `KEYS` fuera del `{hash tag}` compartido, Redis Cluster devuelve `CROSSSLOT` y el test de integración falla (protege contra el error B-07).

**Casos de Uso:**
- **Happy Path:** El usuario selecciona el asiento y tiene 10 minutos exclusivos para pagar.
- **Failure Path:** Dos usuarios envían la petición en el mismo milisegundo; Redis serializa los comandos: el primero bloquea la llave, el segundo recibe un error `409 Conflict`. Variante: el usuario no paga a tiempo; el TTL libera el asiento sin intervención.
- **Failure Path (failover):** el primario de `redis-locks` cae antes de replicar un lock; la réplica promovida no lo conoce y un segundo usuario lo adquiere. **No se vende dos veces** porque la creación de orden (índice único parcial, HU 03.1) y la confirmación (HU 04.2) rechazan al segundo.

**Hallazgos de la auditoría:** el comando original es correcto como primitiva, pero (a) faltaba el **token de propiedad** y la liberación segura (A-02); (b) Redis replica de forma asíncrona, por lo que un lock **puede perderse** en un failover: no se pretende que sea un lock de corrección (no se usa Redlock; para un recurso con árbitro final en la DB sería sobreingeniería); (c) con *Redis Cluster*, las claves deben pensar en *slots*; (d) mezclar cache y locks en el mismo Redis con *eviction* puede borrar locks (A-07, ver HU 05.3); (e) el TTL de Redis tiene precisión de milisegundos, no es "exacto" en sentido físico.

**Correcciones de la segunda auditoría (v3.0):**
- **B-01 (crítico):** `sold:{evt:sec}` → `unavailable:{evt:sec}` (SOLD ∪ BLOCKED), con CA dedicado. La v2.0 permitía comprar un asiento `BLOCKED`.
- **B-02 (crítico):** se agrega `holdprice:{evt:sec}:{seat}` y se congela el precio en el hold, con CA dedicado. La v2.0 podía cobrar un precio distinto del mostrado.
- **B-06 (crítico):** el token de admisión es un JWT con `aud=waiting-room`, no un *access token* de la API.
- **B-38:** la respuesta declara `token` (no `holdId`), que es lo que usan el código y los escenarios de k6.
- **B-15 / ADR-013:** el cluster es `redis-locks` con `noeviction`, no `redis-cache`.
- **B-38:** `release.lua` borra también `holdprice:`; si no, el precio congelado sobrevive al lock y la orden podría leer el precio de un hold ya liberado.

### HU 04.2 - Persistencia con Optimistic Locking
`[ORIGINAL · AMPLIADA]`

**Descripción:** Como motor backend, quiero validar el estado del registro en la base de datos al confirmar la venta, para mantener consistencia incluso ante fallos o pérdida de locks en la capa de caché.

**Tareas de Implementación:**
1. La columna `version` ya está en el DDL de HU 03.1 y se incrementa en cada `UPDATE`, pero **no es la condición de corrección** (B-09). Con ADR-012 (Spring JDBC, sin ORM) no hay `@Version` que la gestione: el arbitraje lo hace el estado. Ver la nota de la v3.0 en HU 03.1.
2. Confirmar la venta con un **`UPDATE` condicional por estado**:
   ```sql
   UPDATE seats
      SET status = 'SOLD', version = version + 1, updated_at = now()
    WHERE id = :id AND event_id = :eventId AND status = 'AVAILABLE';
   ```
   `status = 'AVAILABLE'` **es** la condición de exclusion mutua: PostgreSQL reevalúa el `WHERE` después de esperar el lock de fila, así que de N transacciones concurrentes sobre el mismo asiento exactamente una afecta una fila. Agregar `AND version = :v` obligaría a un `SELECT` previo del `version` sin impedir nada.
3. Para órdenes con varios asientos, hacer **todo o nada** en una única transacción: actualizar con `id = ANY(:ids)` y exigir que las filas afectadas sean exactamente `cardinality(:ids)`; si no, `ROLLBACK`.
4. **Ordenar los IDs** antes de actualizar para evitar *deadlocks* entre transacciones concurrentes.
5. Mapear `0 filas afectadas` a `409 Conflict`; **no** reintentar ciegamente (es un conflicto de negocio, no transitorio). Reintentar solo `40001` (*serialization_failure*) y `40P01` (*deadlock*) con límite y *jitter*.
6. Mantener `READ COMMITTED` (default): el `UPDATE ... WHERE status='AVAILABLE'` es atómico por fila y PostgreSQL re-evalúa la condición tras esperar el bloqueo de fila.
7. Tras confirmar, añadir el `seatId` al conjunto `unavailable:{evt:sec}` de Redis y emitir el evento `seat.sold` vía *outbox* (HU 07.2) en la **misma transacción**.

**Por qué la v2.0 se contradecía (B-09).** La tarea 2 exigía `AND version = :v` y el código de referencia no lo tenía; además el `SELECT` de `version` que esa condición requeriría no existía en ningún punto del flujo. Mantener las dos cosas como "opcional" deja el arbitraje indefinido. La v3.0 elige **estado**: es lo que PostgreSQL puede comprobar de forma atómica sin lectura previa, y expresa la invariante de negocio directamente ("solo vendo lo que está disponible"), mientras que `version` queda como instrumento de diagnóstico para la reconciliación.

**Referencia:**

```java
@Transactional
public void confirmSale(UUID orderId, UUID eventId, List<Long> seatIds) {
    var ids = seatIds.stream().sorted().toList();           // orden estable
    int updated = jdbc.update("""
        UPDATE seats SET status='SOLD', version=version+1, updated_at=now()
         WHERE id = ANY(?) AND event_id = ? AND status = 'AVAILABLE'
        """, ids.toArray(Long[]::new), eventId);
    if (updated != ids.size()) {
        throw new SeatConflictException(ids);               // rollback → 409 + compensación
    }
    orders.markPaid(orderId);
    outbox.append("seat.sold", eventId, ids);               // misma transacción
}
```

**Criterios de Aceptación (CA):**
- El *Update* devuelve **0 filas afectadas** si el asiento ya no está `AVAILABLE`; en ese caso la API responde `409`. El `version` no participa en la condición (B-09): el test lee `version` antes y después de una confirmación concurrente y verifica que **el `UPDATE` condicional por estado ya basta** — si el `WHERE` incluyera `version`, dos confirmaciones sobre el mismo asiento fallarían ambas en lugar de una.
- Se previenen las **actualizaciones perdidas** (*lost updates*) y la doble venta del mismo asiento: dos confirmaciones concurrentes sobre el mismo asiento resultan en exactamente 1 éxito (test con N hilos y Testcontainers).
- Para anomalías entre filas distintas (*write skew*), las invariantes críticas se protegen con restricciones (índice único parcial) o con `SERIALIZABLE` en la transacción que lo requiera.
- Una orden de varios asientos es atómica: si falla uno, no queda ninguno vendido.

**Casos de Uso:**
- **Happy Path:** El estado es `AVAILABLE`, la compra se confirma y `version` incrementa como efecto colateral.
- **Failure Path:** Una transacción intenta confirmar una reserva que otro proceso ya confirmó (p. ej. tras un failover de Redis); la base de datos rechaza la actualización por estado. La orden se cancela y, si el pago ya se capturó, se dispara el reembolso automático (HU 06.3).

**Hallazgos de la auditoría:** el CA original sostenía que se "previene estrictamente el *Write Skew*"; **es incorrecto**: el *optimistic locking* sobre una fila protege contra *lost updates*. El *write skew* involucra filas distintas y se previene con `SERIALIZABLE` o restricciones declarativas (A-03). Además, condicionar por **estado** (`status = 'AVAILABLE'`) es más expresivo que condicionar solo por versión.

**Correcciones de la segunda auditoría (v3.0):**
- **B-09:** se elimina la condición `AND version = :v` de la tarea y se explica por qué el estado es la condición de corrección. La columna `version` se conserva con un propósito declarado (diagnóstico de la reconciliación).
- **B-17:** desaparece `@Version` (JPA) y `ObjectOptimisticLockingFailureException`: con ADR-012 el acceso es JDBC puro y el código de error es el número de filas afectadas.

### HU 04.3 - Sala de Espera Virtual y Control de Admisión
`[NUEVA]`

**Descripción:** Como plataforma, quiero encolar a los usuarios cuando la demanda supera la capacidad, para admitirlos a un ritmo que el sistema pueda sostener y garantizar equidad.

**Tareas de Implementación:**
1. Implementar el servicio `waiting-room` (desplegable independiente, *stateless*, escala por separado).
2. Estructuras en `redis-locks`. **Particionado en K sub-colas desde el diseño (B-29), no como mitigación posterior:** `ZSET wr:{evt}:q{0..K-1}` (score = instante de llegada), donde `K = min(16, ceil(usuarios_esperados / 50 000))` y la sub-cola es `CRC16(userId) % K`. `ZADD NX` para no perder posición en reintentos, `ZRANK` para consultar posición.
3. **Por qué particionar desde el principio.** La v2.0 usaba **una sola** `ZSET wr:{evt}:queue` y dejaba "si excede la capacidad, particionar" como tarea 8. Eso contradice el principio que el propio plan aplica a los asientos (repartir el tráfico de un evento viral entre varios *slots*) y, con 200 000 usuarios, todas las operaciones de la cola —`ZADD`, `ZRANK`, `ZPOPMIN`— compiten por un único *slot* de un único nodo: un solo nodo caliente, y el `ZPOPMIN` del planificador es un punto de serialización inevitable. Con K sub-colas el planificador extrae de varias en paralelo y ninguna queda saturada. El coste es tener que calcular la posición global summing `ZRANK` en las K sub-colas, lo que se acepta.
4. **Equidad:** para quienes entran antes de la apertura, asignar *score* aleatorio dentro de una ventana (lotería), de modo que llegar un segundo antes no dé ventaja.
5. **Control de admisión:** un planificador admite `N` usuarios/segundo (`ZPOPMIN` sobre cada sub-cola, round-robin), donde `N` se deriva de la capacidad medida (p. ej. latencia p99 del *hold*, espera del pool de DB) y no de la demanda.
6. Emitir un **token de admisión** (JWT corto, `evt`, `sub`, `exp` ≈ 10 min) requerido por el endpoint de *hold*.
7. **El token de admisión es un JWT distinto al *access token* (B-06, crítico).** Claim `aud = "waiting-room"`, firmado con una **clave propia** (no la de los *access tokens*) y con `typ` propio. El endpoint de `hold` valida explícitamente `aud == "waiting-room"`. La v2.0 no definía `aud` para este token, con lo cual solo había dos resultados posibles y ambos malos: si el `api` lo aceptaba como *access token*, cualquier usuario de la fila podía saltarse la cola; si validaba `aud = "api"`, ningún token de admisión pasaba nunca y la sala de espera era un muro. Ver el detalle en la nota de abajo.
8. Informar la posición por SSE o *long-polling* con *jitter* en los reintentos del cliente; página estática servible por CDN mientras la cola está activa.
9. Mitigar bots: desafío tipo CAPTCHA/Turnstile al entrar, una entrada por cuenta, límite por IP/dispositivo.

> **B-06 en detalle.** El endpoint de `hold` es el único que exige el token de admisión, y no es autenticado: quien está en la cola todavía no tiene sesión. Por eso la separación no puede apoyarse en "estar autenticado". Con `aud` propio y clave propia, un token de admisión **no** sirve para llamar a ningún otro endpoint (todos exigen `aud = "api"`), y un *access token* **no** sirve para saltarse la cola (el `hold` exige `aud = "waiting-room"`). Ninguno de los dos tokens confunde al otro, que es exactamente el *confused deputy* que se quería evitar.

**Criterios de Aceptación (CA):**
- 200 000 usuarios en cola no degradan la latencia del `hold` de los usuarios admitidos (p99 < 200 ms durante la prueba).
- La tasa de admisión sigue el valor configurado (± 10 %) y se reduce automáticamente cuando el p99 supera el umbral.
- Un usuario no puede ocupar dos posiciones; reintentar `join` conserva su posición.
- Sin token de admisión válido, `hold` devuelve `403` en eventos con cola activa.
- **Un *access token* de la API usado como token de admisión devuelve `403` (B-06), y un token de admisión usado contra `/api/v1/orders` devuelve `401`.** Los dos tests son la prueba de que `aud` está realmente separado; sin ellos, un JWT sin `aud` (o con el `aud` equivocado) pasaría ambos y el CA no lo detectaría.
- Con K sub-colas activas, ninguna de ellas supera el 60 % del tamaño medio esperado: si una concentrates más, el reparto por `CRC16` está mal y el CA falla.

**Casos de Uso:**
- **Happy Path:** El usuario entra a la sala, ve su posición descender y recibe el token; reserva dentro de los 10 minutos.
- **Failure Path:** `redis-locks` falla y se pierde la cola; el servicio entra en modo degradado (ventana de re-entrada con nuevo sorteo) y se informa claramente al usuario en lugar de dejarlo en un estado inconsistente.

### HU 04.4 - Reserva Atómica de Múltiples Asientos
`[NUEVA]`

**Descripción:** Como comprador, quiero reservar varios asientos contiguos en una sola operación, para no quedarme con una selección incompleta.

**Tareas de Implementación:**
1. Script Lua `hold_many.lua`: recibe la lista de asientos de **una misma sección** (mismo *slot*), verifica que ninguno esté en `unavailable` ni retenido y recién entonces los retiene a todos con el mismo token y TTL; congela el precio de cada uno y registra los `ZADD`.
2. Límite de asientos por operación (p. ej. 8).
3. Respuesta en caso de conflicto: `409` con la lista de asientos conflictivos para que el front sugiera alternativas.
4. Órdenes que cruzan secciones: adquirir por sección en orden estable y **compensar** (liberar) si alguna falla.

**Referencia (`hold_many.lua`, v3.0):**

```lua
-- El script de la v2.0 tenía tres errores (B-07):
--   1) devolvía ARGV[2+i] en el conflicto, que es el TTL, no el seatId
--   2) nunca hacía el ZADD que la tarea 1 promete
--   3) no incluía el ZSET de retenciones en KEYS, así que no podía
--
-- KEYS[1]          = unavailable:{evt:sec}          (SOLD + BLOCKED)
-- KEYS[2]          = holds:{evt:sec}                 (ZSET de retenciones)
-- KEYS[3+i]        = hold:{evt:sec}:<seatId>         i = 0 .. nHold-1
-- KEYS[3+nHold+i]  = holdprice:{evt:sec}:<seatId>
--
-- ARGV[1]          = token
-- ARGV[2]          = ttlMs
-- ARGV[3]          = expiresAtMs
-- ARGV[4+i]        = seatId  (mismo orden que los KEYS de hold)
-- ARGV[4+nHold+i]  = pricePaid de ese asiento
--
-- Todas las claves comparten el {hash tag} {evt:sec}: mismo slot, script atomico.
local nHold = (#KEYS - 2) / 2

-- Fase 1: verificar TODO antes de escribir nada (todo o nada)
for i = 0, nHold - 1 do
  local seatId = ARGV[4 + i]
  if redis.call('SISMEMBER', KEYS[1], seatId) == 1 then
    return {-1, seatId}                             -- vendido o bloqueado
  end
  if redis.call('EXISTS', KEYS[3 + i]) == 1 then
    return {0, seatId}                              -- retenido por otro
  end
end

-- Fase 2: escribir. SET sin NX porque la fase 1 ya lo garantiza dentro de este
-- script atomico; si aun asi fallara, Redis aborta el script entero.
for i = 0, nHold - 1 do
  redis.call('SET',  KEYS[3 + i],        ARGV[1],              'PX', ARGV[2])
  redis.call('SET',  KEYS[3 + nHold + i], ARGV[4 + nHold + i], 'PX', ARGV[2])  -- B-02
  redis.call('ZADD', KEYS[2], ARGV[3], ARGV[4 + i])                             -- B-07
end
return {1}
```

**Criterios de Aceptación (CA):**
- Con 100 usuarios compitiendo por solapamientos de 4 asientos, ningún asiento queda retenido por dos usuarios y ninguna reserva queda "a medias".
- Un *hold* parcial nunca es observable desde fuera (todo o nada).
- **El segundo valor del retorno en conflicto es el `seatId` que lo provocó, no el TTL** (B-07). Test: `hold_many` sobre 3 asientos donde el segundo está retenido; el `409` trae el id del segundo. Si el script devolviera `ARGV[2+i]`, el id sería un número de milisegundos y el CA falla.
- **Tras un `hold_many` exitoso, `ZCARD holds:{evt:sec}` aumenta en exactamente N y `GET holdprice:{evt:sec}:<seat>` devuelve el precio** (B-07, B-02). Este es el CA que la v2.0 no tenía y que hacía el `ZADD` opcional en la práctica: si el `ZADD` falta, la lista de asientos retenidos de HU 04.6 queda vacía y el mapa miente.
- **Si el `ZSET` no está en `KEYS`, Redis Cluster falla con `CROSSSLOT`** y el test lo detecta (B-07). El test corre contra Redis Cluster real (Testcontainers), no contra un Redis único: en un Redis único el error `CROSSSLOT` no puede aparecer y el bug pasa inadvertido.

**Casos de Uso:**
- **Happy Path:** Reserva de 4 asientos contiguos en 1 ida y vuelta a Redis.
- **Failure Path:** Uno de los 4 asientos fue retenido un instante antes; la operación completa devuelve `409` indicando cuál, sin retener los otros tres.

**Correcciones de la segunda auditoría (v3.0):**
- **B-07 (alto):** el script de referencia no funcionaba. Devolvía el TTL en lugar del `seatId` en el conflicto, no escribía en el `ZSET` y no declaraba el `ZSET` en `KEYS` (con Redis Cluster eso además da `CROSSSLOT` en cuanto se use el `ZADD`). CA específicos para cada uno de los tres fallos.
- **B-01:** consulta `unavailable:` en lugar de `sold:`.
- **B-02:** congela el precio de cada asiento, igual que `hold.lua`.

### HU 04.5 - Expiración de Órdenes, Liberación y Reconciliación
`[NUEVA]`

**Descripción:** Como sistema, quiero expirar órdenes impagas y reconciliar Redis con la base de datos, para que ningún asiento quede inutilizable ni inconsistente.

**Tareas de Implementación:**
1. Job programado (con **ShedLock** para ejecución única entre pods) que expira órdenes vencidas:
   ```sql
   UPDATE orders SET status='EXPIRED', updated_at=now()
    WHERE status='PENDING_PAYMENT' AND expires_at < now()
   RETURNING id;
   ```
   y libera sus ítems (`UPDATE order_items SET released_at = now() ...`), emitiendo `order.expired` por *outbox*.
2. **No** usar *keyspace notifications* de Redis como mecanismo de expiración: son *fire-and-forget* y se pierden ante desconexiones o failovers.
3. Resolver la carrera *pago vs. expiración* con transiciones condicionales (`... WHERE status='PENDING_PAYMENT'`): gana quien llegue primero; si el pago llega tras expirar, se **reembolsa automáticamente** (HU 06.3).
4. **Reconciliación**: tarea que reconstruye `unavailable:{evt:sec}` desde PostgreSQL, **acotada a un evento** y usando el índice parcial `idx_seats_sold_reconciliation` (B-28). Se ejecuta al arrancar cada pod, tras un failover de Redis y bajo demanda:
   ```sql
   SELECT id, event_id FROM seats WHERE status = 'SOLD' AND event_id = $1;
   ```
   Sin el `event_id` el plan es un *Seq Scan* de la tabla entera; con el índice parcial es un *Index Only Scan* sobre los vendidos de ese evento (B-28).
5. Métrica `reconciliation.drift` (diferencias detectadas) con alerta si > 0.

> **B-03 (crítico): las dos expiraciones no pueden tener la misma marca de tiempo.**
> En la v2.0, `orders.expires_at` se fijaba **igual** al TTL del hold en Redis (600 s). Eso produce una ventana de entre 0 y ~60 s donde el hold **ya expiró** pero la orden sigue `PENDING_PAYMENT`:
>
> ```text
>   t = 600 s      el hold de Redis expira          → el mapa muestra el asiento LIBRE
>   t = 600..660   la orden sigue PENDING_PAYMENT     → el asiento sigue vendido en la DB
>                 otro usuario retiene y paga         → el índice único parcial rechaza su orden
>                                                        con 409 DESPUÉS de una reserva exitosa
> ```
>
> El sistema no sobrevende (la DB lo impide), pero el usuario ve un asiento disponible, lo compra, y la compra falla. La corrección es **desacoplar las dos marcas**:
>
> ```sql
> -- El hold vive 600 s; la orden caduca 90 s ANTES de que el hold muera.
> hold_expires_at = now() + interval '600 seconds'
> orders.expires_at = hold_expires_at - interval '90 seconds'
> ```
>
> El orden es siempre `orders.expires_at < hold_expires_at`, y el job de expiración corre **antes** de que el hold desaparezca. Con eso, cuando la orden se declara `EXPIRED` y libera `order_items`, el asiento todavía está retenido en Redis: nadie más puede tomarlo, y cuando el hold muera 90 s después el asiento ya está limpio en la DB. La ventana de sobreventa aparente se cierra.
>
> **Consecuencia operativa:** el usuario tiene 510 s para pagar, no 600. Es un costo real, deliberado, y la constante (90 s) es un parámetro con nombre (`app.hold.settle-grace`) para poder ajustarla al comportamiento real del proveedor de pagos.
>
> **CA que lo verifica (corregido).** La v2.0 enunciaba este CA al revés y por eso era **imposible de pasar**: "tras `DELETE` de las claves `hold:*` de un asiento con una orden aún `PENDING_PAYMENT`, un nuevo `hold` sobre ese asiento **falla** con `409`". Con el modelo de `03.md` eso no puede ocurrir: el asiento está retenido por una clave de **precio** (`holdprice:{evt:sec}:{seatId}`) y por su entrada en `holds:{evt:sec}`, pero su `seat.status` en la DB sigue siendo `AVAILABLE` y **no está en `unavailable:{evt:sec}`** (solo lo están los `SOLD` y los `BLOCKED`). Un `hold` nuevo sí tiene éxito: devuelve `201`, y lo que falla después es la orden, con `409` al comprobar `status='AVAILABLE'`... que sigue siendo `AVAILABLE`. Es decir, la comprobación tardía se activaría en el momento **equivocado**, que es exactamente el fallo que B-01 y B-03 vienen a cerrar.
>
> El CA correcto, y el que sí discrimina, es el siguiente, y va en las dos direcciones:
> - **Con la orden aún `PENDING_PAYMENT` y su *hold* vivo**, un `hold` nuevo sobre el mismo asiento devuelve `409 SEAT_ALREADY_HELD`, en < 20 ms. Verifica que la retención está publicada mientras la orden existe.
> - **Tras la expiración de la orden** (`orders.expires_at` alcanzado, job ejecutado, `order_items.released_at` escrito) y **antes** de que expire el *hold*, un `hold` nuevo sigue devolviendo `409 SEAT_ALREADY_HELD`. Este es el caso que B-03 existe para cubrir: los 90 s de gracia se traducen en que el asiento no queda vendible durante la ventana en la que la orden ya está cerrada.
> - **Tras la expiración completa** (*hold* incluido, `order_items.released_at IS NULL`, `seat.status='AVAILABLE'`), un `hold` nuevo devuelve `201`. Verifica que el asiento no queda huérfano retenido para siempre, que era el riesgo real de esta corrección.
>
> Los tres casos van en el mismo test de integración, en ese orden, con el `seatId` del caso 1 como aserto del caso 2.

**Criterios de Aceptación (CA):**
- Una orden impaga pasa a `EXPIRED` dentro de los 60 s posteriores a su vencimiento y sus asientos vuelven a estar disponibles.
- **`orders.expires_at` es estrictamente menor que `hold_expires_at` por el margen configurado (90 s por defecto)** en el 100 % de las órdenes creadas (B-03). El test compara las columnas de todas las órdenes de una corrida de k6.
- **Nunca se crea una orden cuyo hold ya expiró**: la creación de la orden devuelve `409 SEAT_HOLD_EXPIRED` si el token no existe en Redis, en vez de crear una orden imposible de pagar.
- Tras borrar manualmente los conjuntos `unavailable:*` en Redis, la reconciliación los reconstruye y `reconciliation.drift` vuelve a 0 en < 2 min, **para el evento dado** (sin recorrer los demás).
- Dos pods ejecutando el job a la vez **no** procesan la misma orden dos veces.

**Casos de Uso:**
- **Happy Path:** El usuario abandona el pago; a los 510 s la orden expira y el asiento vuelve a estar disponible para otros 90 s después, cuando el hold se libera solo.
- **Failure Path:** El pago se aprueba en la pasarela 3 segundos después de que la orden expiró y el asiento ya se vendió a otra persona; el sistema detecta el estado, **reembolsa** automáticamente y notifica al usuario.

**Correcciones de la segunda auditoría (v3.0):**
- **B-03 (crítico):** se separa `orders.expires_at` del TTL del hold con 90 s de margen, se explica la ventana de sobreventa aparente que se cierra y se agregan dos CA.
- **B-28:** la reconciliación filtra por `event_id` y usa el índice parcial dedicado; antes hacía *Seq Scan*.
- **B-01:** reconstruye `unavailable:{evt:sec}` (SOLD ∪ BLOCKED), no `sold:{evt:sec}`. Con el nombre anterior, los asientos `BLOCKED` desaparecían del camino rápido después de cada reconciliación y quedaban retenibles y vendibles.

### HU 04.6 - Mapa de Asientos y Disponibilidad en Tiempo Casi Real
`[NUEVA]`

**Descripción:** Como comprador, quiero ver el mapa de asientos y su disponibilidad actualizada, para elegir rápidamente sin que el servicio se sature.

**Tareas de Implementación:**
1. `GET /api/v1/events/{id}/seatmap`: geometría **estática y versionada** (SVG/JSON), con `Cache-Control: public, max-age=31536000, immutable` y *ETag*; servida por CDN.
2. `GET /api/v1/events/{id}/availability?section=…`: devuelve solo los asientos **no disponibles** (`SOLD` ∪ `BLOCKED` ∪ retenidos) en formato compacto (lista de IDs o *bitmap* en base64). Fuente: `SMEMBERS unavailable:{evt:sec}` ∪ `ZRANGEBYSCORE holds:{evt:sec} (now +inf`; **no** usar `SCAN`.
3. Caché L1 (Caffeine, 1 s) delante de Redis para absorber ráfagas (*hot key*).
4. `GET /api/v1/events/{id}/availability/stream` (SSE) con *deltas* publicados desde el tópico `seats.events` (HU 07.x); límite de conexiones por pod y *backpressure*.
5. Fallback: *polling* cada 3–5 s con *jitter* si SSE no está disponible.
6. **Fan-out (B-14, ADR-017).** El SSE no puede leer Kafka directamente: Kafka reparte cada registro a un consumidor, y con `concurrency` menor que el número de particiones hay pods que nunca ven un delta. La cadena es: `seats.events` → **un** proyector consolidado → **Redis Pub/Sub** → cada pod se suscribe y reenvía a sus clientes SSE. Los deltas son naturalmente *broadcast*: a todos les interesa el mismo cambio, lo que es exactamente lo contrario de lo que Kafka hace bien (particionar la carga entre consumidores).

> **B-14 en detalle.** Es tentador que cada pod consuma `seats.events` con su propio grupo de consumidores: Kafka entrega cada mensaje a **un** miembro del grupo, así que con 12 pods y 6 particiones solo 6 ven cada delta, y el mapa de los otros 6 queda desactualizado. La alternativa —un consumidor por pod leyendo **todas** las particiones— obliga a `concurrency = particiones` en cada pod (con 24 particiones de `seats.events`, son 24 hilos por pod) y multiplica el consumo de la partición 24 veces. El fan-out explícito a través de Redis Pub/Sub cuesta un salto de red y resuelve el problema de una vez.

**Criterios de Aceptación (CA):**
- El mapa de un evento de 50 000 asientos se entrega con **p99 < 100 ms** y **0 consultas** a PostgreSQL en el camino caliente.
- Un asiento vendido aparece como no disponible en los clientes conectados en **< 2 s**.
- 10 000 conexiones SSE por pod no superan el presupuesto de memoria definido (medido en k6).
- **Todos** los pods conectados reciben el mismo delta (B-14): el test conecta SSE en 8 pods, vende un asiento y verifica que los 8 lo reciben en < 2 s. Con el esquema de la v2.0 (consumo directo por pod) este CA falla, porque solo los pods que consumieron esa partición lo verían.

**Casos de Uso:**
- **Happy Path:** El cliente carga el mapa desde CDN y refresca solo los *deltas* de disponibilidad.
- **Failure Path:** Redis no responde; se sirve la última disponibilidad conocida (con marca de antigüedad) y el `hold` sigue validando contra el árbitro final, evitando falsos positivos de venta.

**Correcciones de la segunda auditoría (v3.0):**
- **B-14 / ADR-017:** el SSE se alimenta de Redis Pub/Sub y no de un consumo directo de Kafka por pod; se agrega el CA de "los 8 pods reciben el delta".
- **B-01:** la disponibilidad combina `unavailable:{evt:sec}` (vendidos y bloqueados) con las retenciones, no solo `sold:`.
- **B-39:** rutas con prefijo `/api/v1`.

## Épica 13: Catálogo y Administración

**Objetivo de aprendizaje:** modelado de datos de referencia, carga masiva idempotente, `COPY` de PostgreSQL, ciclo de vida de una entidad, *seeding* reproducible.

> **Por qué esta épica existe (B-12).** La v2.0 tenía 50 HUs y ninguna podía **crear un evento**: `venues` estaba referenciada como FK y no existía, no había CRUD de `events` ni de `price_tiers`, la carga de asientos se daba por hecha y no había forma de pasar un evento a `SOLD_OUT`. Sin esta épica el sistema solo se puede probar con fixturessql escritos a mano, y el objetivo de aprendizaje —un ticket que se compra de principio a fin— no se puede alcanzar. **Se implementa justo después de la 03**, pero conserva el número 13 para no invalidar las referencias `NN.N` ya escritas en `01.md` §0.9, `05.md` y `07.md`.

**Dependencias:** HU 03.1 (esquema), HU 02.4 (RBAC: `ORGANIZER`/`ADMIN`), HU 03.2 (índices y `VACUUM`), HU 11.1 (k6 para el *seeding*).

### HU 13.1 - Venues y Carga Masiva de Asientos

`[NUEVA · B-12]`

**Descripción:** Como organizador, quiero registrar la sede y cargar el inventario de asientos de forma masiva e idempotente, para tener un evento listo para la venta sin escribir SQL a mano.

**Tareas de Implementación:**
1. `POST /api/v1/venues` (rol `ADMIN`): crea la sede con `name`, `address`, `timezone` (IANA), `capacity` y `map_asset_url`. El DDL de `venues` está en HU 03.1 (B-37).
2. `POST /api/v1/events/{id}/seats:bulk` (rol `ORGANIZER` del evento) que acepta un CSV y lo carga con **`COPY … FROM STDIN`** en lugar de un `INSERT` por fila. Para 50 000 asientos, `COPY` baja la carga de horas a segundos y no satura el WAL como una transacción de 50 000 `INSERT`.
3. **Idempotencia por contenido:** el `seats.upsert` se hace con `INSERT … ON CONFLICT (event_id, section, seat_row, seat_column) DO UPDATE SET price_tier_id = EXCLUDED.price_tier_id`. Recargar el mismo CSV **no** duplica filas ni pisa los asientos ya `SOLD`.
   ```sql
   INSERT INTO seats (event_id, price_tier_id, section, seat_row, seat_column, status)
   SELECT $1, pt.id, s.section, s.seat_row, s.seat_column, 'AVAILABLE'::seat_status
     FROM staging_seats s
     JOIN price_tiers pt ON pt.event_id = $1 AND pt.name = s.tier_name
   ON CONFLICT (event_id, section, seat_row, seat_column) DO UPDATE
     SET price_tier_id = EXCLUDED.price_tier_id
    WHERE seats.status = 'AVAILABLE';      -- nunca pisar un SOLD ni un BLOCKED
   ```
   El `WHERE` del `DO UPDATE` es lo que hace segura la recarga: sin él, una recarga del CSV después de iniciada la venta dejaría `SOLD` en `AVAILABLE` y **vendería el mismo asiento dos veces**.
4. **Valores por defecto del CSV** si falta `section`: snake_case, `row` y `column` como enteros. Formato de una línea por asiento, cabecera incluida.
5. **Transacción única** para toda la carga, más `VACUUM (ANALYZE) seats;` al finalizar (HU 03.2, tarea 5) para que el *index-only scan* del mapa funcione.
6. Endpoint `GET /api/v1/events/{id}/seats:import-status` para consultar el progreso (filas cargadas, errores) sin esperar el request.
7. Rechazar la carga si `len(asientos) ≠ venues.capacity` **o** si supera el límite (p. ej. 200 000 filas): es un error de datos, no un problema de performance.

**Criterios de Aceptación (CA):**
- Cargar 50 000 asientos por `COPY` tarda **< 60 s** en el entorno de referencia; el mismo CSV por `INSERT` individual tarda > 20 min (el CA documenta el motivo de la decisión).
- **Cargar el mismo CSV dos veces produce exactamente las mismas filas** (`COUNT(*)` idéntico, sin duplicados) y la segunda corrida deja los asientos ya `SOLD` intactos. Este es el CA que detectaría el error del punto 3 sin el `WHERE`.
- Tras la carga, `EXPLAIN` de la consulta del mapa muestra `Index Only Scan` con `Heap Fetches` < 1 % (HU 03.2).
- Una fila con `tier_name` inexistente se rechaza con un error que nombra la fila y el valor, y **toda** la carga se revierte.
- Un usuario sin rol `ORGANIZER` sobre ese evento recibe `404` (no `403`, por B-08 anti-IDOR).

**Casos de Uso:**
- **Happy Path:** El organizador sube el plano del estadio como CSV, el sistema crea 50 000 asientos en menos de un minuto y el evento queda listo para publicarse.
- **Failure Path:** El CSV tiene una fila con `tier_name: "VIP_PISO_99"` que no existe en `price_tiers`. La carga se revierte entera, el endpoint de estado reporta `1 error: fila 12 341, tier_name desconocido "VIP_PISO_99"`, y ningún asiento queda creado. Variante: el organizador sube el mismo archivo dos veces por una duda; no ocurre nada (idempotencia).

**Correcciones de la segunda auditoría (v3.0):**
- **B-12 (alto):** HU nueva. Cierra el hueco que hacía imposible sembrar el sistema.

### HU 13.2 - Catálogo de Eventos y Niveles de Precio

`[NUEVA · B-12]`

**Descripción:** Como organizador, quiero crear y publicar un evento con sus niveles de precio, para poder ponerlo a la venta y controlar su ciclo de vida.

**Tareas de Implementación:**
1. `POST /api/v1/events` (rol `ORGANIZER`): crea en estado `DRAFT` con `venue_id`, `title`, `starts_at`, `sales_open_at`, `currency`. Validar que `sales_open_at < starts_at` y que `capacity` del evento no exceda el de la sede.
2. `POST /api/v1/events/{id}/price-tiers` y `PATCH /api/v1/events/{id}/price-tiers/{tierId}`: crear y modificar niveles. Un `price_tier` **no** se borra si ya tiene asientos vendidos; se marca como no vendible.
3. **Transiciones de estado válidas** (`DRAFT → ON_SALE → SOLD_OUT → FINISHED`, más `DRAFT → CANCELLED` y `ON_SALE → CANCELLED`), implementadas con `UPDATE … WHERE status = :expected` para que una transición inválida no aplique:
   ```sql
   UPDATE events SET status = 'ON_SALE', updated_at = now()
    WHERE id = $1 AND status = 'DRAFT';
   ```
4. **Guardas de la transición:**
   - `DRAFT → ON_SALE` exige: al menos un asiento cargado (`COUNT(*) > 0`), al menos un `price_tier`, y `sales_open_at` alcanzable. Sin esto el evento se publica vacío.
   - `ON_SALE → SOLD_OUT` es **automático** cuando `COUNT(*) FILTER (WHERE status='SOLD')` alcanza el total de asientos `AVAILABLE`; también manual por el organizador.
   - `ON_SALE → CANCELLED` dispara `order.refund_requested` por *outbox* para cada orden `PAID` no reembolsada (HU 06.3) y deja los asientos `AVAILABLE`.
   - `→ FINISHED` es automático por un job cuando `starts_at` pasó, o manual.
5. **Modificar precios con retenciones vivas:** cambiar `price_tiers.price_minor` solo afecta a holds **nuevos**. Los retenimientos existentes conservan su `holdprice:` (B-02), de modo que un usuario que ya tiene el asiento no ve el precio cambiar bajo sus pies. Esta regla es parte del contrato y se documenta en el endpoint.
6. Listados paginados: `GET /api/v1/events?status=ON_SALE` y `GET /api/v1/events/{id}`, con filtro por `status` usando el índice que corresponda.

**Criterios de Aceptación (CA):**
- `DRAFT → ON_SALE` con **cero** asientos devuelve `422` con el motivo (`no_seats`), no publica un evento vacío.
- Una transición no permitida (`ON_SALE → DRAFT`) devuelve `409 INVALID_TRANSITION` y no modifica el estado. El test recorre **todas** las transiciones de la tabla y verifica que exactamente las válidas devuelven `200`.
- Cuando el último asiento `AVAILABLE` se vende, el evento pasa a `SOLD_OUT` en **< 5 s** sin intervención.
- Cancelar un evento con órdenes `PAID` genera un reembolso por cada una, y el conteo de `order.refunded` coincide con el de `orders` `PAID` (verificable con una query).
- Un usuario `CUSTOMER` no puede llamar a ningún endpoint de esta HU (recibe `404`); un `ORGANIZER` solo puede modificar eventos de los que es propietario.

**Casos de Uso:**
- **Happy Path:** El organizador crea el evento, carga 50 000 asientos, crea tres niveles de precio y lo publica. Minutos después aparece en el listado público y es comprable.
- **Failure Path:** El organizador intenta publicar el evento antes de cargar los asientos; recibe `422 no_seats` con un enlace a la pantalla de carga. Variante: intenta bajar el precio de un nivel mientras 200 usuarios tienen ese asiento retenido; los 200 conservan el precio original y los siguientes obtienen el nuevo (B-02 aplicado al catálogo).

**Correcciones de la segunda auditoría (v3.0):**
- **B-12 (alto):** HU nueva. La transición a `SOLD_OUT` no existía en ninguna parte del plan v2.0.

**Criterios de Aceptación (CA):**

**Casos de Uso:**
- **Happy Path:** Antes de una corrida de k6, el operador llama a `seed` una vez y a `tokens` dos veces, y el escenario arranca con 200 000 usuarios autenticados sin intervención manual.
- **Failure Path:** Alguien despliega en `prod` con el perfil equivocado. El test de *context load* del pipeline falla antes de que el pod reciba tráfico y el despliegue se detiene; no hay un token de prueba sirvible en producción.
