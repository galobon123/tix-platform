## Épica 05: Capa de Caching y Resiliencia

**Objetivo de aprendizaje:** estrategias de caché multinivel, *cache stampede*, *token bucket* distribuido, operación de Redis Cluster, *circuit breakers*, *bulkheads* y *load shedding*.

### HU 05.1 - Prevención de Cache Stampede (Singleflight)
`[ORIGINAL · AMPLIADA]`

**Descripción:** Como sistema, quiero consolidar las lecturas simultáneas cuando la caché de un evento expira, para proteger la base de datos tanto dentro de un pod como entre pods.

**Tareas de Implementación:**
1. **Nivel L1 (por proceso):** caché Caffeine con *coalescing* por clave. `LoadingCache.get(key)` ejecuta **una sola** carga por clave y bloquea a los demás llamadores de esa misma clave (con hilos virtuales el bloqueo es barato). Evitar un `synchronized` global: serializaría claves distintas. En Spring, `@Cacheable(sync = true)` aplica el mismo principio. *(En Go: `singleflight.Group`.)*
2. **Nivel L2 (compartido):** Redis `redis-cache`, con **TTL + jitter** (±10–20 %) para no expirar masivamente a la vez.
3. **Lock distribuido de reconstrucción** entre pods: `SET lock:evt:{id} <token> NX PX 5000`. Quien lo obtiene recarga desde PostgreSQL y repuebla L2; el resto no toca la DB.
4. **Stale-while-revalidate:** guardar el valor con expiración lógica (*soft TTL*) menor a la física; si el valor está vencido lógicamente pero existe, **devolverlo** y recargar en segundo plano.
5. Si no hay valor ni lock: esperar con *backoff* + *jitter* (3 intentos máx.) y, si sigue sin haber valor, reconstruir bajo *bulkhead*.
6. **Refresco probabilístico anticipado** (XFetch) para claves muy calientes: recalcular antes del vencimiento con probabilidad creciente.
7. **Caché negativa:** guardar `NOT_FOUND` 30–60 s para eventos inexistentes (evita *cache penetration*).
8. Métricas: `cache.hit{level}`, `cache.miss`, `cache.rebuild.duration`, `cache.rebuild.timeouts`.

**Referencia (L1 por clave):**

```java
LoadingCache<UUID, EventView> l1 = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofSeconds(2))
    .recordStats()
    .build(id -> l2OrDb.load(id));   // una sola carga por clave, aunque lleguen 10 000 hilos
```

**Criterios de Aceptación (CA):**
- Si 10 000 peticiones impactan un catálogo no cacheado simultáneamente, se registra **como máximo 1 consulta por pod** en PostgreSQL con L1 y **1 consulta total** (tolerancia ≤ 2) cuando además participa el lock distribuido (medido con `pg_stat_statements` en un test con ≥ 3 réplicas).
- Con el valor vencido lógicamente, el 100 % de las respuestas se sirven desde caché (sin esperar la recarga).
- Un `NOT_FOUND` repetido 100 000 veces genera ≤ 1 consulta por ventana de caché negativa.

**Casos de Uso:**
- **Happy Path:** El hilo líder consulta la DB, guarda en Redis y responde; los otros 9 999 hilos reciben la respuesta del líder sin tocar la base de datos.
- **Failure Path:** El hilo líder sufre un *timeout* contra la base de datos; el lock expira (5 s), el siguiente hilo asume el liderazgo para reintentar, y mientras tanto los demás reciben el valor *stale* o, si no existe, un `503` con `Retry-After` aleatorizado. El *circuit breaker* de DB evita que los reintentos se conviertan en una tormenta.

**Hallazgos de la auditoría:** el mutex en memoria solo coordina **dentro de un proceso**; con N pods habría hasta N consultas, no 1 (A-06). Tampoco cubría el *hot key* de un evento viral ni el caso del líder lento (A-29).

### HU 05.2 - Rate Limiting por API Gateway
`[ORIGINAL · AMPLIADA]`

**Descripción:** Como sistema, quiero limitar la cantidad de peticiones por identidad y por tipo de endpoint, para evitar *scraping* o ataques de denegación de servicio sin penalizar a usuarios legítimos.

**Tareas de Implementación:**
1. Capa 1 — **borde (CDN/WAF/Gateway API):** límites gruesos por IP y reglas anti-bot.
2. Capa 2 — **aplicación (autoritativa):** *Token Bucket* **distribuido en Redis** mediante script Lua atómico, con claves por `usuario` (autenticados), `IP` (anónimos) y `clase de endpoint`.
3. Definir **cuotas por clase** (ejemplo inicial, a calibrar con k6):

   | Clase | Clave | Capacidad / recarga |
   |---|---|---|
   | `login` | IP + cuenta | 10 / min por IP, 5 / min por cuenta |
   | `register` | IP | 5 / hora |
   | `availability` | usuario o IP | ráfaga 40, 20 req/s |
   | `hold` | usuario | ráfaga 5, 2 req/s |
   | `general` | IP | 100 / min |

4. Retornar `429 Too Many Requests` con `Retry-After` y cabeceras de política de límite.
5. **Orden real de los filtros (B-18).** La v2.0 pedía "colocar el filtro primero, antes de autenticación pesada", y a la vez keyeaba el bucket **por usuario autenticado**: las dos cosas son incompatibles, porque para conocer el usuario hay que autenticarse primero. El orden que sí funciona, y que es el que implementa el `SecurityFilterChain`, es:
   1. **Borde** (CDN/WAF): límites gruesos por IP, sin tocar la aplicación.
   2. **Autenticación ligera**: validar la firma del JWT. No descifrar nada, no ir a la base de datos, no cargar roles. Es la lectura de una firma, del orden de microsegundos, y no es "autenticación pesada".
   3. **Rate limit por usuario** para endpoints autenticados, ahora que el `sub` ya está disponible sin ir a la DB.
   4. **Rate limit por IP** para requests anónimos (`login`, `register`) y como segundo límite en paralelo para los autenticados.

   La consecuencia que hay que aceptar: un JWT con firma inválida **no** llega a consumeirse en el bucket por usuario (muere en el paso 2), así que un atacante que falsifique tokens no gasta cuota del usuario victim's. Eso es deseable. Lo que sí se defiende contra es el abuso con tokens **válidos** — un cliente que reuse su propio token — y ese es justamente el caso que limita la cuota por usuario.
6. Política ante caída de Redis: *fail-soft* — caer a un limitador **local** por pod (Bucket4j) con cuota `límite/réplicas`; en `login` y `register`, *fail-closed* más estricto.
7. Registrar `ratelimit.rejected{class}` y alertar sobre picos.

**Referencia (`token_bucket.lua`, v3.0):**

```lua
-- KEYS[1]=rl:<clave>   ARGV[1]=capacidad  ARGV[2]=recarga/seg  ARGV[3]=costo
local t   = redis.call('TIME')
local now = t[1] * 1000 + math.floor(t[2] / 1000)
local cap, rate, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])

-- B-32: la v2.0 dividia por rate sin comprobar que fuera > 0. Con rate = 0
-- (configuracion pendiente de calibrar, o una clase mal definida) esto es
-- division por cero y el script aborta con un error en vez de devolver un 429.
if cap == nil or rate == nil or cost == nil or cap <= 0 or rate <= 0 or cost <= 0 then
  return {-1, 0, 0}        -- error de configuracion: el servidor responde 503, no 429
end

local d = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens, ts = tonumber(d[1]), tonumber(d[2])
if tokens == nil then tokens, ts = cap, now end
tokens = math.min(cap, tokens + math.max(0, now - ts) / 1000 * rate)

local allowed, retry = 0, 0
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
else
  retry = math.ceil((cost - tokens) / rate * 1000)
end

redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
-- B-32: math.ceil devuelve un flotante y PEXPIRE espera un entero; en algunas
-- versiones de Redis el error de tipo hace fallar el comando entero.
redis.call('PEXPIRE', KEYS[1], math.floor(cap / rate * 1000) * 2 + 1000)
return { allowed, math.floor(tokens), retry }
```

> **Por qué `+ 1000` en el `PEXPIRE`:** el TTL debe ser el tiempo necesario para llenar el bucket desde cero con margen, y además **no** debe expirar mientras el bucket está activo: si expirara, el usuario recuperaría la cuota completa. `floor(cap/rate*1000)*2` ya le da el doble del tiempo de llenado; el segundo de más es holgura para el redondeo.
>
> **Qué hace el `-1` del principio:** una clase mal configurada (`rate = 0`) no debe devolver un `429` que sugiere "esperá y reintentá", cuando el problema es de configuración. El servidor lo traduce a `503`, que sí es reintentable y **alerta**.

**Criterios de Aceptación (CA):**
- Exceder el límite retorna inmediatamente un código HTTP `429 Too Many Requests` con `Retry-After` correcto (± 1 s).
- Una respuesta `429` tiene **p99 < 5 ms** y **0 consultas** a PostgreSQL/Kafka: el rechazo es el camino más barato del sistema.
- El límite es **global**: con 5 pods, 500 peticiones simultáneas de un mismo usuario consumen un único *bucket* (no 5).
- Usuarios distintos detrás de una misma IP no se afectan entre sí en endpoints autenticados.
- **`rate = 0` produce `503`, no un error 500 ni un `429`** (B-32). Test parametrizado que invoca el Lua con `rate=0` y `cap=0`; sin la guarda, Redis devuelve un error de script y el endpoint responde 500, que en un tablero parece un fallo del sistema y no un error de configuración.
- **Una petición anónimo a `login` consume cuota por IP; una autenticada a `hold` consume cuota por usuario** (B-18). Test que verifica las dos claves en Redis después de cada caso.

**Casos de Uso:**
- **Happy Path:** El usuario navega normalmente dentro de los límites de la cuota.
- **Failure Path:** Un bot intenta extraer datos del mapa de asientos ejecutando 500 requests en un minuto y es bloqueado temporalmente (`429`); un segundo bot con IP rotativa es frenado en la capa de aplicación por límite de cuenta/huella y en el borde por reglas de WAF.

**Hallazgos de la auditoría:** (1) el CA "las peticiones rechazadas no consumen recursos" es inalcanzable literalmente; se reformula como **costo mínimo y acotado** (A-12); (2) limitar solo por IP es ineficaz con NAT/botnets; (3) un limitador local por pod no respeta la cuota global.

**Correcciones de la segunda auditoría (v3.0):**
- **B-18 (alto):** la tarea 5 ("filtro primero, antes de autenticar") era imposible de cumplir con la tarea 2 (key por usuario autenticado). Se documenta el orden real de cuatro pasos y por qué.
- **B-32 (bajo):** `PEXPIRE` recibía `math.ceil` (flotante) y faltaba la guarda contra `rate = 0`, que dividía por cero. Ambos corregidos, con CA.

### HU 05.3 - Redis Cluster: Topología, Failover y Separación Cache/Locks
`[NUEVA]`

**Descripción:** Como SRE, quiero operar Redis en modo cluster con roles separados, para obtener alta disponibilidad sin que la caché pueda afectar a los locks.

**Tareas de Implementación:**
1. Desplegar **dos clusters** (3 primarios + 3 réplicas cada uno; ElastiCache con *cluster mode enabled* en producción), según **ADR-013**:
   - `redis-locks`: `unavailable:` (SOLD ∪ BLOCKED), `holds:`, `holdprice:`, la sala de espera y el *rate limiting*. **No** se mantiene `sold:` (B-01: `sold:` no incluía `BLOCKED`). `maxmemory-policy noeviction`, **AOF** (`appendonly yes`, `appendfsync everysec`).
   - `redis-cache`: catálogo y proyecciones. `maxmemory-policy allkeys-lru` (o `allkeys-lfu`).
   - **ADR-013, en una línea:** las claves de disponibilidad van en el cluster con `noeviction`. En `redis-cache` (`allkeys-lru`) un "vendido" puede ser *evictado* del camino rápido. La DB seguiría siendo el árbitro —no habría sobreventa— pero el `hold` haría trabajo inútil para un asiento ya vendido y el mapa mostraría disponibilidad inconsistente. Un tercer cluster es prohibitivo.
2. Parámetros clave: `cluster-node-timeout 5000`. **`min-replicas-to-write 1` es exclusivo de Redis autogestionado (B-25):** con ElastiCache en *cluster mode enabled* ese parámetro **no existe** y el módulo Terraform no lo acepta; ponerlo en la configuración de un cluster gestionado es un error que falla en el apply, no algo que se ignora en silencio. Las dos opciones reales:
   - **Producción gestionada (recomendada, ADR-011):** no se configura. Se acepta la pérdida de locks en el failover y se cubre con la reconciliación de HU 04.5, que es la red de seguridad que ya existe.
   - **Autogestionado en K8s (para aprender):** `min-replicas-to-write 1` + `min-replicas-max-lag 1`, aceptando que un primario sin réplica sana rechaza escrituras y el `hold` devuelve `503`.
   La v2.0 listaba el parametro sin indicar en cual aplica una u otra, que es la forma mas segura de terminar con un `terraform apply` roto.
3. **Dimensionamiento y alerta de memoria (ADR-013).** El `noeviction` convierte la memoria en un límite duro: cuando se llena, las escrituras **fallan** en lugar de perder datos. Eso es lo correcto para locks, pero significa que hay que dimensionar antes de que sea un incidente. Requisito: alerta cuando `used_memory / maxmemory > 0.70` en `redis-locks` (no 0.95: a 70 % todavía hay margen para absorber una ráfaga), con dimensionamiento a partir de la fórmula de HU 05.3 y revisión trimestral.
4. Cliente Lettuce con refresco de topología adaptativo y *timeouts* cortos:
   ```java
   var topology = ClusterTopologyRefreshOptions.builder()
       .enablePeriodicRefresh(Duration.ofSeconds(30))
       .enableAllAdaptiveRefreshTriggers().build();
   var options = ClusterClientOptions.builder()
       .topologyRefreshOptions(topology)
       .timeoutOptions(TimeoutOptions.enabled(Duration.ofMillis(100)))
       .build();
   ```
   Lecturas desde réplicas (`ReadFrom.REPLICA_PREFERRED`) **solo** para `redis-cache`; los locks leen y escriben siempre en el primario.
5. Documentar las reglas de diseño de claves: *hash tags* por evento/sección, nunca claves multi-slot en scripts, evitar `KEYS`/`SCAN` en el camino caliente.
6. Detectar y mitigar ***hot keys*** (evento viral): L1 local, repartir por sección, y particionar colas (HU 04.3).
7. Monitoreo con `redis_exporter`: memoria, `evicted_keys` (debe ser **0** en `redis-locks`), latencia, `connected_slaves`, `cluster_state`.
8. **Failover drill** programado: eliminar el primario de un shard y medir el impacto.

**Criterios de Aceptación (CA):**
- `evicted_keys` en `redis-locks` es **0** incluso con memoria al 100 % (las escrituras fallan con error, no se borran locks).
- Al eliminar un primario, el cluster recupera escritura en **< 15 s** (`node-timeout` + elección) y la app se recupera sin reinicio.
- Durante el failover **no se vende ningún asiento dos veces** (verificado con la consulta de unicidad de HU 11.2).
- El cliente no genera tormentas de conexiones al refrescar topología.
- **`terraform plan` con la configuración de ElastiCache no menciona `min-replicas-to-write`** (B-25); y el test de Terraform falla si alguien lo agrega al módulo gestionado.
- **La alerta de memoria de `redis-locks` dispara al 70 %**, no al 90 %, y el runbook indica qué hacer (dimensionar o drenar `redis-cache`).

**Casos de Uso:**
- **Happy Path:** Las operaciones de lock se reparten entre los 3 primarios según sección/evento con p99 < 5 ms.
- **Failure Path:** Falla un nodo primario; las operaciones sobre sus *slots* devuelven error durante unos segundos, el *circuit breaker* devuelve `503` y, tras la promoción de la réplica, el servicio se normaliza. Se ejecuta la **reconciliación** (HU 04.5).

> **Nota:** Valkey es una alternativa compatible con el protocolo de Redis y está disponible en servicios gestionados; las decisiones de este documento aplican a ambos.

### HU 05.4 - Resiliencia en Dependencias: Timeouts, Reintentos, Circuit Breaker y Load Shedding
`[NUEVA]`

**Descripción:** Como sistema, quiero degradar de forma controlada cuando una dependencia falla o se vuelve lenta, para evitar fallos en cascada.

**Tareas de Implementación:**
1. Definir un **presupuesto de *timeouts*** coherente: *timeout* del cliente > del Gateway > del servicio > de cada dependencia (p. ej. 5 s / 4 s / 3 s / 1–2 s). Nunca llamadas sin *timeout*.
2. **Reintentos** solo en operaciones idempotentes, con *backoff* exponencial y *jitter*, máximo 2–3 intentos y *retry budget* global.
3. **Circuit Breaker** por dependencia (pasarela de pagos, Redis, PostgreSQL de lectura, SMTP).
4. **Bulkheads** (semáforos) para aislar recursos: hashing de contraseñas, llamadas a la pasarela, consultas pesadas.
5. **Load shedding:** límite de peticiones en vuelo por pod; al superarlo, `503` con `Retry-After` inmediato, priorizando endpoints críticos (`hold`, `checkout`) sobre navegación.
6. Implementar con **Resilience4j** (verificar compatibilidad de su *starter* con la versión de Spring Boot en uso) o con las anotaciones nativas de resiliencia de Spring Framework 7 (`@Retryable`, `@ConcurrencyLimit`).
7. **Pruebas de fallo** con Toxiproxy (Testcontainers): latencia, cortes y *timeouts* sobre PostgreSQL, Redis y la pasarela.

**Referencia (configuración):**

```yaml
resilience4j:
  circuitbreaker:
    instances:
      payments:
        slidingWindowType: COUNT_BASED
        slidingWindowSize: 50
        failureRateThreshold: 50
        slowCallDurationThreshold: 2s
        slowCallRateThreshold: 50
        waitDurationInOpenState: 20s
        permittedNumberOfCallsInHalfOpenState: 5
  retry:
    instances:
      payments-read:
        maxAttempts: 3
        waitDuration: 200ms
        enableExponentialBackoff: true
        exponentialBackoffMultiplier: 2
        enableRandomizedWait: true
  bulkhead:
    instances:
      password-hashing: { maxConcurrentCalls: 16, maxWaitDuration: 0 }
```

**Criterios de Aceptación (CA):**
- Con la pasarela respondiendo con 5 s de latencia, el *circuit breaker* abre y `checkout` responde en **< 500 ms** con un error controlado; el resto del sistema no se degrada.
- Con PostgreSQL a 100 % de saturación inducida, el *load shedding* mantiene `hold` operativo para tráfico ya admitido y rechaza navegación con `503`.
- No existe ninguna llamada de red sin *timeout* (verificado por revisión + prueba arquitectónica con ArchUnit).

**Casos de Uso:**
- **Happy Path:** Una falla transitoria de la pasarela se absorbe con 1 reintento y el usuario no percibe error.
- **Failure Path:** La pasarela cae por completo; el *breaker* abre, los usuarios ven "pago no disponible, tus asientos siguen reservados" mientras dura el TTL, y al recuperarse el servicio el *breaker* cierra gradualmente (*half-open*).

### HU 06.1 - Orden y Checkout con Máquina de Estados
`[NUEVA]`

**Descripción:** Como comprador, quiero convertir mis asientos retenidos en una orden pagable, para completar la compra dentro del tiempo de reserva.

**Máquina de estados de la orden:**

| Desde | Hacia | Disparador |
|---|---|---|
| — | `PENDING_PAYMENT` | `POST /api/v1/orders` válido |
| `PENDING_PAYMENT` | `PAID` | pago aprobado + `confirmSale` OK (HU 04.2) |
| `PENDING_PAYMENT` | `EXPIRED` | vence `expires_at` (HU 04.5) |
| `PENDING_PAYMENT` | `CANCELLED` | cancelación del usuario |
| `PENDING_PAYMENT` | `PAYMENT_FAILED` | rechazo definitivo del pago |
| `PAID` | `FULFILLED` | tickets emitidos (HU 06.4) |
| `PAID` | `REFUNDED` | reembolso (conflicto, cancelación del evento) |

**Tareas de Implementación:**
1. `POST /api/v1/orders` con cabecera obligatoria `Idempotency-Key` (HU 06.2) y cuerpo `{eventId, seatIds, holdToken}`.
2. Validar: usuario verificado, **propiedad de los *holds*** (el token coincide en Redis), límite de asientos y que el evento esté `ON_SALE`.
3. **Calcular precios en el servidor** desde `price_tiers`; nunca aceptar importes del cliente.
4. En **una transacción**: insertar `orders` + `order_items` (con `price_paid` fijado) y el evento `order.created` en el *outbox*. El índice único parcial (HU 03.1) rechaza duplicados.
5. `expires_at` = vencimiento del *hold* más próximo (nunca después).
6. Transiciones con `UPDATE orders SET status = :nuevo WHERE id = :id AND status = :esperado` (concurrencia segura).
7. Documentar la **saga** del checkout (coreografía por eventos): `hold → order.created → payment.created → payment.approved → seats.sold → tickets.issued`, con compensaciones (`release holds`, `refund`).

**Criterios de Aceptación (CA):**
- El total de la orden es exactamente `Σ price_paid`; un cliente que envíe un precio distinto lo ve ignorado.
- Una transición ilegal (p. ej. `EXPIRED → PAID` sin reembolso) es imposible: test parametrizado de la tabla completa.
- Crear una orden con un asiento ya incluido en otra orden activa devuelve `409` (índice único) aunque Redis haya perdido el lock.
- Todo cambio de estado publica su evento en el *outbox* en la misma transacción.

**Casos de Uso:**
- **Happy Path:** El usuario retiene 2 asientos, crea la orden, paga y recibe sus tickets en menos de 10 minutos.
- **Failure Path:** Tras `hold`, el usuario envía la orden con un `holdToken` ajeno; el servicio responde `403` sin crear nada.

### HU 06.2 - Idempotencia de Peticiones
`[NUEVA]`

**Descripción:** Como cliente (o su navegador/red), quiero poder reintentar una petición sin crear efectos duplicados, para que un *timeout* no resulte en doble orden o doble cobro.

**Tareas de Implementación:**
1. Tabla de claves de idempotencia:
   ```sql
   CREATE TABLE idempotency_keys (
     user_id         uuid NOT NULL,
     key             text NOT NULL,
     request_hash    text NOT NULL,
     status          text NOT NULL CHECK (status IN ('IN_PROGRESS','COMPLETED')),
     response_status int,
     response_body   jsonb,
     created_at      timestamptz NOT NULL DEFAULT now(),
     PRIMARY KEY (user_id, key)
   );
   ```
2. Algoritmo: `INSERT ... ON CONFLICT DO NOTHING`; si se inserta → ejecutar y guardar la respuesta **en la misma transacción** que el efecto; si existe con otro `request_hash` → `422`; si está `IN_PROGRESS` → `409` con `Retry-After`; si `COMPLETED` → **reproducir** la respuesta almacenada.
3. Aplicarlo a `POST /api/v1/orders`, creación de pagos y reembolsos.
4. TTL de 24 h con job de limpieza.
5. Documentar en OpenAPI que el cliente genera un UUID por intento de compra.

**Criterios de Aceptación (CA):**
- 50 peticiones idénticas concurrentes con la misma clave producen **exactamente 1 orden** y 50 respuestas equivalentes (49 reproducidas o `409` transitorios).
- La misma clave con un cuerpo distinto devuelve `422`.
- Tras un *crash* del servidor a mitad de la petición, el reintento no genera duplicados.

**Casos de Uso:**
- **Happy Path:** El móvil pierde la señal tras enviar el pago, reintenta con la misma clave y recibe la misma orden.
- **Failure Path:** Un bug del cliente reutiliza la clave con otro carrito; el servidor responde `422` en lugar de devolver la orden equivocada.

### HU 06.3 - Integración con la Pasarela de Pagos y Webhooks Seguros
`[NUEVA]`

**Descripción:** Como negocio, quiero cobrar de forma segura y reconciliar cada pago con su orden, para que no existan cobros sin tickets ni tickets sin cobro.

**Tareas de Implementación:**
1. Definir un **puerto** `PaymentGateway` (crear pago, consultar, reembolsar) y un adaptador por proveedor (Mercado Pago o Stripe) — ADR-010.
2. **Alcance PCI mínimo:** usar *checkout* alojado o campos del proveedor; **nunca** recibir, registrar ni almacenar número de tarjeta ni CVV.
3. Tablas:
   ```sql
   CREATE TABLE payments (
     id                  uuid PRIMARY KEY,
     order_id            uuid NOT NULL REFERENCES orders(id),
     provider            text NOT NULL,
     provider_payment_id text,
     status              text NOT NULL CHECK (status IN
       ('CREATED','PENDING','APPROVED','REJECTED','REFUND_PENDING','REFUNDED','CHARGEBACK')),
     amount_minor        bigint NOT NULL,
     currency            char(3) NOT NULL,
     created_at          timestamptz NOT NULL DEFAULT now(),
     updated_at          timestamptz NOT NULL DEFAULT now(),
     UNIQUE (provider, provider_payment_id)
   );
   CREATE TABLE webhook_events (
     provider    text NOT NULL,
     event_id    text NOT NULL,
     received_at timestamptz NOT NULL DEFAULT now(),
     PRIMARY KEY (provider, event_id)
   );
   ```
4. **Webhook seguro y acotado (B-14, ADR-014).** El endpoint del webhook hace **tres** cosas y nada más:
   1. Verifica la firma HMAC del proveedor con comparación en tiempo constante y tolerancia de marca temporal. Firma inválida → `401`, sin tocar estado.
   2. Deduplica por `(provider, event_id)`: si la fila ya existe, responde `200` y no reprocesa.
   3. Inserta el evento en la tabla de entrada y **publica `payments.events`** (vía *outbox*), y responde `200`.

   **No** confirma la venta, **no** toca `orders` ni `seats`, **no** consulta al proveedor. La v2.0 mezclaba las dos cosas: la tarea decía "volver a consultar al proveedor" y "procesar de forma asíncrona" en la misma línea, sin decir cuál hacía el endpoint. Con la confirmación dentro del webhook, el CA de "< 500 ms" dependía de una transacción `confirmSale` completa —que bloquea filas de `seats`— y de la disponibilidad del *worker* que emite el evento: un pico de carga hacía que el proveedor empezara a dar timeouts y reintentara webhooks, que es exactamente la tormenta que el diseño asíncrono evita.

   Con **ADR-014**, la separación es explícita: **el webhook responde rápido y no sabe nada del dominio**; el `payments.events` → `worker` es quien decide. La consecuencia a aceptar es que la confirmación es **eventualmente** consistente, y eso se refleja en la UI: el estado del pago es `PENDING_PAYMENT` con un banner "confirmando pago" hasta que llega el evento, no un `PAID` inmediato. El pago ya fue cobrado por el proveedor; lo que el usuario espera es la confirmación, y el SLA de esa espera es un SLO medible (§0.7).
5. Enviar al proveedor su cabecera de idempotencia al crear pagos/reembolsos.
6. **Reembolso: semántica definida (B-04, ADR-016).** Ver la tabla de abajo. La v2.0 decía "reembolso automático" sin decir qué pasaba con `seats.status`, `order_items.released_at` ni `tickets.status`, y las tres opciones razonables rompen algo.
7. Conciliación diaria: comparar pagos del proveedor contra la DB; alertar divergencias.
8. Proteger las llamadas salientes con *timeout*, *circuit breaker* y *bulkhead* (HU 05.4).

**Semántica del reembolso (B-04, ADR-016):**

Un reembolso tiene que decidir tres cosas a la vez. Lo que no puede hacer es elegir solo una:

| Objeto | Qué hace el reembolso | Por qué |
|---|---|---|
| `seats.status` | `'SOLD'` → `'AVAILABLE'` | Si queda `SOLD` sin ítem activo, el asiento quema inventario y la verificación de sobreventa (HU 11.2) da falsos positivos para siempre. Si queda `AVAILABLE` **con** el ítem activo, el índice único parcial `ux_order_items_active_seat` lo deja impagable para siempre. |
| `order_items.released_at` | `NULL` → `now()` | Es lo que libera el índice único parcial. Sin esto, el asiento liberado queda bloqueado para siempre; con esto, se puede volver a vender. |
| `tickets.status` | `'VALID'` → `'VOID'` | El QR ya enviado por email debe dejar de validar. Si el evento **ya empezó**, el reembolso es solo de dinero y el asiento **no** vuelve al inventario: se registra como `attended_refund` y el `seats.status` permanece `'SOLD'`. Ver la nota siguiente. |
| Evento | `order.refunded` por *outbox* | Para que las proyecciones y el cliente se actualicen. |

**Atomicidad: PostgreSQL sí, Redis no (B-04).** La v2.0 (y el primer borrador de esta corrección) decía "todo eso en **una sola transacción**", sin distinguir qué transacciones son posibles. Eso es imposible y es un error de diseño, no de redacción: **Redis no participa en la transacción de PostgreSQL**. No hay `BEGIN` que abarque ambos, ni *commit* en dos fases, y `SADD`/`SREM` no se deshacen con un `ROLLBACK`. Cualquier esquema que prometa atomicidad entre la DB y Redis miente sobre una de las dos, y el fallo aparece en producción: la transacción hace `COMMIT` y la llamada a Redis falla (o al revés), y el estado queda partido.

La solución usa el patrón **outbox**, que ya es la base de este proyecto (HU 07.2):

| Paso | Sistema | Atomicidad | Qué garantiza |
|---|---|---|---|
| 1 | PostgreSQL | **Una sola transacción** | `orders.status='REFUNDED'`, `seats.status='AVAILABLE'`, `order_items.released_at=now()`, `tickets.status='VOID'` y **la fila en `outbox`** (`order.refunded`) se escriben juntos, con `WHERE orders.status='PAID'`. O pasa todo, o no pasa nada. |
| 2 | Redis | **Eventual, best-effort** | El proyector `availability-projector` de HU 07.4 consume `order.refunded` y hace `SREM unavailable:{evt:sec}` + `SREM holds:{evt:sec}`. |
| 3 | Redis (reconciliación) | **Periódica** | El job de reconciliación de HU 04.6 compara `unavailable:*` con la DB y corrige. Es la red de seguridad, no el camino normal. |

Por qué el orden importa: **la DB va primero**. Si la transacción se hace `COMMIT` y el `SREM` falla, el peor caso es que un asiento libre parezca ocupado en la caché durante unos segundos: el `hold` devuelve `409` y el usuario reintenta. Es unavailability *falsa*, que degrada la conversión. Si el orden fuera el inverso (`SREM` primero y luego `ROLLBACK` de la DB), el peor caso es el opuesto y mucho peor: **el asiento parece libre y se puede vender dos veces**, que es la sobreventa que todo el diseño evita.

Un reembolso parcial (asiento liberado, ticket no) es peor que no reembolsar: deja al usuario con un ticket válido para un asiento que ya es de otro. Por eso los pasos de la tabla van en **una sola transacción de DB**, no en varias.

**Nota sobre el evento ya iniciado (`attended_refund`).** La regla es: si `event.starts_at <= now()`, el reembolso **no** libera el asiento y **no** invalida el ticket; solo mueve el dinero y escribe `attended_refund` en el reporte. La razón es operativa y es la misma que impide dar el asiento a otro: si el evento ya empezó, el asiento está siendo usado por alguien en la sala, y "devolverlo al inventario" significaría vender una butaca que ya está ocupada. En esa situación:
- `seats.status` **permanece** `'SOLD'`.
- `tickets.status` **permanece** `'VALID'` (el asistente conserva su entrada; la política de refunds en el curto es del negocio, no del sistema).
- El reporte de BS asienta el importe como gasto de compensación, sin implicar inventario.

Esto es una decisión de negocio, no una consecuencia técnica, así que se deja explícita y con su CA (abajo). Si el negocio quiere lo contrario, se cambia la tabla y no el código.

**Criterios de Aceptación (CA):**
- Un webhook con firma inválida devuelve `401` y no altera estado; un webhook duplicado se procesa **una sola vez**.
- **El webhook no ejecuta ninguna escritura de dominio:** un test afirma que tras el `200` la orden sigue `PENDING_PAYMENT` (B-14). Sin este CA, alguien puede "optimizar" siguiendo la lectura intuitiva del código y reintroducir el acoplamiento.
- **El webhook responde en < 200 ms p99** y su latencia **no** depende de la latencia de PostgreSQL: el `200` se emite tras insertar el evento en la cola local y **sin** esperar al *outbox* de PostgreSQL (ADR-014). La prueba inyecta 3 s de latencia en la DB y verifica que el p99 del webhook no se mueve.
- Ningún pago `APPROVED` queda sin orden `PAID`, `REFUNDED` o cola de reembolso al cierre de la conciliación (0 divergencias).
- Ningún dato de tarjeta aparece en logs, base de datos ni trazas (revisión automatizada de logs en CI).
- **Reembolso: el asiento vuelve a venderse (B-04).** Test end-to-end: comprar → `PAID` → reembolsar → el `seatId` vuelve a estar `AVAILABLE`, `order_items.released_at` no es `NULL`, `tickets.status = 'VOID'`, y **un segundo usuario puede comprar el mismo asiento y su `confirmSale` tiene éxito**. Ese último paso es el que la v2.0 no verificaba y es donde se rompía el índice único.
- **Reembolso de un asiento ya revendido:** el segundo comprador conserva su ticket y el primero recibe el reembolso. Verificable con una query de conteo.
- **Atomicidad real, no declarada (B-04).** Test de fallo inyectado que mata la conexión **entre** el `COMMIT` de PostgreSQL y el `SREM` de Redis (`TOXIPROXY` o un *proxy* conmutado en ese punto): el resultado exigido es que la DB queda coherente (los 4 campos actualizados, con `order.refunded` en el *outbox*), el asiento **parece** ocupado en la caché durante un máximo de 5 s, y la reconciliación lo corrige. Lo que el test **no** permite es el caso inverso: nunca un asiento libre en la DB y libre en Redis con el reembolso a medias, que sería sobreventa.
- **Reembolso con el evento ya iniciado:** el test fija `event.starts_at` en el pasado, reembolsa y verifica que `seats.status` sigue `'SOLD'`, `tickets.status` sigue `'VALID'`, el dinero se devuelve y el reporte registra `attended_refund`. Y el caso espejo (evento futuro) verifica el camino normal de la tabla.

**Casos de Uso:**
- **Happy Path:** El usuario paga; el webhook llega, responde `200` en milisegundos, y 200 ms después el `worker` confirma la orden y emite los tickets. La UI muestra "confirmando pago" durante ese intervalo.
- **Failure Path:** El pago se aprueba después de que la orden expiró; el worker detecta que la orden no está `PENDING_PAYMENT`, la marca `REFUND_PENDING`, reembolsa con clave de idempotencia y notifica. Variante: el webhook llega dos veces y desordenado respecto del estado actual; la segunda entrega se descarta por deduplicación y la regla de transición condicional.

### HU 06.4 - Emisión de Tickets y Validación de QR en Puerta
`[NUEVA]`

**Descripción:** Como asistente, quiero recibir un ticket con QR verificable, y como personal de puerta quiero validarlo una única vez, para impedir fraudes y reutilización.

**Tareas de Implementación:**
1. Consumidor de `order.paid` (HU 07.3) que emite un ticket por `order_item`, **idempotente** por `UNIQUE (order_item_id)`:
   ```sql
   CREATE TABLE tickets (
     id            uuid PRIMARY KEY,
     order_item_id bigint NOT NULL UNIQUE REFERENCES order_items(id),
     event_id      uuid NOT NULL REFERENCES events(id),
     status        text NOT NULL CHECK (status IN ('VALID','USED','VOID')),
     issued_at     timestamptz NOT NULL DEFAULT now(),
     used_at       timestamptz
   );
   ```
2. QR con `ticketId` + firma (Ed25519) sobre `(ticketId, eventId)`; el escáner verifica la firma sin conexión con la clave pública.
3. `POST /api/v1/tickets/validate` con transición atómica de un solo uso:
   ```sql
   UPDATE tickets SET status = 'USED', used_at = now()
    WHERE id = :id AND status = 'VALID' RETURNING id;
   ```
4. Respuestas diferenciadas: válido, ya usado (con hora del primer uso), anulado, firma inválida, otro evento.
5. Modo *offline* del escáner: lista local + sincronización posterior con resolución de duplicados.
6. Notificación por email con el ticket adjunto (consumidor de Kafka, HU 07.4).

**Criterios de Aceptación (CA):**
- Dos escaneos concurrentes del mismo ticket: exactamente **uno** resulta válido.
- Un QR con firma alterada o de otro evento es rechazado en < 50 ms sin consultar la DB.
- Reprocesar `order.paid` 10 veces genera exactamente 1 ticket por asiento.

**Casos de Uso:**
- **Happy Path:** El asistente muestra el QR, se valida y la puerta se abre en < 1 s.
- **Failure Path:** Una captura de pantalla del QR se usa en otra puerta; el segundo escaneo informa "ya utilizado a las HH:MM" y alerta al personal.

**Correcciones de la segunda auditoría (v3.0):**
- **B-04 (crítico):** el reembolsado ahora define las tres decisiones (ADR-016) y tiene un CA end-to-end que prueba que el asiento vuelve a venderse.
- **B-39:** rutas con prefijo `/api/v1` (`/api/v1/tickets/validate`).
