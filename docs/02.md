### HU 01.1 - Entorno de Desarrollo Local Contenerizado
`[ORIGINAL · AMPLIADA]`

**Descripción:** Como desarrollador, quiero disponer de un entorno local con `docker-compose.yml`, para ejecutar y probar la aplicación sin instalar servicios manualmente, con paridad razonable respecto de producción (PostgreSQL detrás de PgBouncer, Redis, Kafka en modo KRaft y, opcionalmente, el stack de observabilidad).

**Tareas de Implementación:**
1. Crear `docker-compose.yml` incluyendo PostgreSQL, **PgBouncer**, Redis y Kafka (**modo KRaft, sin ZooKeeper**), cada uno con `healthcheck`.
2. Configurar volúmenes con nombre para persistencia de datos de PostgreSQL y Redis (`pgdata`, `redisdata`).
3. Exponer puertos estándar (5432, 6432 para PgBouncer, 6379, 9092) mapeados al `localhost`, **parametrizados por variables** (`${POSTGRES_PORT:-5432}`) en un archivo `.env`.
4. Definir **perfiles de Compose**: por defecto solo infraestructura base; `--profile cluster` (Redis Cluster de 6 nodos), `--profile obs` (Prometheus, Grafana, Loki, Alloy, Jaeger/OTel Collector) y `--profile full` (incluye la app).
5. Agregar un `Makefile` (o `justfile`) con `up`, `down`, `reset` (borra volúmenes), `logs`, `psql`.
6. Documentar los comandos de inicialización y la resolución de problemas comunes en el `README.md`.

**Referencia (`docker-compose.yml`, servicios base):**

```yaml
services:
  postgres:
    image: postgres:17
    environment:
      POSTGRES_DB: tickets
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?definir en .env}
    ports: ["${POSTGRES_PORT:-5432}:5432"]
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d tickets"]
      interval: 5s
      timeout: 3s
      retries: 10

  pgbouncer:
    image: edoburu/pgbouncer:latest   # fijar una versión concreta en uso real
    environment:
      DATABASE_URL: postgres://app:${POSTGRES_PASSWORD}@postgres:5432/tickets
      POOL_MODE: transaction
      MAX_CLIENT_CONN: 1000
      DEFAULT_POOL_SIZE: 20
    ports: ["${PGBOUNCER_PORT:-6432}:5432"]
    depends_on:
      postgres: { condition: service_healthy }

  redis:
    image: redis:7
    command: ["redis-server", "--appendonly", "yes"]
    ports: ["${REDIS_PORT:-6379}:6379"]
    volumes: [redisdata:/data]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      retries: 10

  kafka:
    image: apache/kafka:latest        # fijar versión (4.x usa KRaft por defecto)
    ports: ["${KAFKA_PORT:-9092}:9092"]
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
      KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS: 0
    healthcheck:
      test: ["CMD-SHELL", "/opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server localhost:9092 >/dev/null 2>&1"]
      interval: 10s
      retries: 10

volumes: { pgdata: {}, redisdata: {} }
```

> **Nota Kafka local:** con un único `ADVERTISED_LISTENERS` a `localhost`, la app corriendo **fuera** de Docker conecta bien; una app **dentro** de la red de Compose necesita un segundo *listener* (p. ej. `INTERNAL://kafka:29092`). Resolverlo en el perfil `full`.

> **Nota Redis Cluster local:** el modo cluster anuncia IPs internas; por eso se levanta en un perfil aparte, con un job de inicialización (`redis-cli --cluster create ... --cluster-yes`) y la app dentro de la misma red de Compose.

**Criterios de Aceptación (CA):**
- `docker compose up -d --wait` termina con **exit code 0** y todos los contenedores en estado *healthy*.
- Los datos de la base de datos sobreviven a un `docker compose down` y posterior `up` (y **no** sobreviven a `make reset`).
- Con las imágenes ya descargadas, un entorno limpio queda operativo en **menos de 2 minutos**; el README documenta el tiempo esperado en la primera ejecución (descarga de imágenes).
- `psql` contra PgBouncer (6432) y contra PostgreSQL directo (5432) funcionan; las migraciones usan el directo.
- Ningún secreto está versionado: `.env` está en `.gitignore` y existe un `.env.example`.

**Casos de Uso:**
- **Happy Path:** Un desarrollador clona el repo, copia `.env.example` a `.env`, ejecuta `make up` y accede a la base de datos localmente en menos de 2 minutos (imágenes ya descargadas).
- **Failure Path:** El puerto 5432 está ocupado por un servicio local; Docker aborta con `Bind for 0.0.0.0:5432 failed: port is already allocated`. El desarrollador cambia `POSTGRES_PORT` en `.env` y relanza sin editar el compose.

**Hallazgos de la auditoría:** faltaban PgBouncer, *healthchecks* (sin ellos "healthy" no significa nada), Kafka en KRaft, perfiles y paridad con el cluster de Redis; el criterio "<2 min" ignoraba la descarga de imágenes; los puertos estaban fijos. Evitar imágenes de Bitnami para nuevos proyectos: el catálogo gratuito fue reducido y movido a repositorios *legacy*.

### HU 01.2 - Provisión de Infraestructura con Terraform
`[ORIGINAL · AMPLIADA]`

**Descripción:** Como DevOps Engineer, quiero gestionar la infraestructura cloud mediante código, para garantizar entornos repetibles, auditables y con credenciales efímeras.

**Tareas de Implementación:**
1. Estructurar el repo `infra/` con **módulos reutilizables** y **entornos separados**:
   ```text
   infra/
   ├── modules/
   │   ├── network/        # VPC, subnets públicas/privadas, NAT, SGs
   │   ├── edge/           # B-13: CloudFront + WAF + ACM + Route 53 (borde gestionado)
   │   ├── eks/            # clúster, node groups / Karpenter, OIDC provider (IRSA)
   │   ├── rds/            # PostgreSQL Multi-AZ, parameter group, backups/PITR
   │   ├── elasticache/    # 2 clusters Redis (locks, cache)
   │   └── registry/       # ECR + políticas de ciclo de vida
   └── envs/
       ├── staging/        # main.tf + staging.tfvars
       └── prod/           # main.tf + prod.tfvars
   ```
2. Escribir módulos Terraform (`.tf`) para VPC, Subnets y Security Groups (mínimo privilegio: la DB solo acepta tráfico desde el SG de los nodos/PgBouncer).
3. Definir el clúster de Kubernetes (**EKS** como referencia; GKE equivalente) y las bases de datos gestionadas (RDS PostgreSQL, ElastiCache).
4. Configurar un **backend remoto** en S3 con **cifrado, versionado y bloqueo de estado** (`use_lockfile = true`, Terraform ≥ 1.10, sin DynamoDB), creado una única vez por un módulo `bootstrap`.
5. Autenticar GitHub Actions contra AWS con **OIDC** (rol asumido por *workflow*), **sin claves de acceso estáticas**.
6. Integrar análisis estático: `terraform fmt -check`, `terraform validate`, `tflint` y un escáner de configuración (Trivy config/Checkov) en el CI.
7. Pipeline de infra: `plan` automático en PR (comentado en el PR), `apply` solo desde `main` con **aprobación manual** (GitHub Environments).
8. Configurar **alertas de presupuesto** (AWS Budgets) y etiquetado obligatorio (`project`, `env`, `owner`).

**Módulo `edge/` — CDN, WAF y certificados de borde (B-13).** La v2.0 dibujaba un `CloudFront → WAF → ALB → EKS` en el diagrama y HU 12.2 exigía "CDN + WAF con reglas administradas, control de bots y reglas de tasa; protección DDoS; TLS y HSTS", pero **el árbol de módulos de Terraform no lo contenía**. El diagrama describía un recurso que nadie iba a crear, y los CA de seguridad de HU 12.2 (escaneo de puertos, DDoS, TLS 1.3) no tenían nada detrás. El módulo `edge/` crea:

| Recurso | Para qué | Nota de diseño |
|---|---|---|
| `aws_cloudfront_distribution` | CDN: cachea estáticos y absorbe el pico antes del Gateway | El origen es el `ALB`, **nunca** el `Service` de K8s |
| `aws_wafv2_web_acl` + `ip_set` + `rate_based_statement` | WAF administrado + control de bots + **rate limit en el borde** | Limita por IP **antes** de llegar a la API; el token bucket de HU 05.2 es la segunda capa, por usuario |
| `aws_acm_certificate` + `validation` | Certificado de borde | `us-east-1` para CloudFront; se replica a `us-east-2` |
| `aws_route53_record` + `aws_acm_certificate_validation` | DNS y validación del certificado | Alias `A`/`AAAA` al *distribution* |
| `aws_wafv2_web_acl_association` | Adjuntar la ACL al *distribution* | Sin esto la ACL existe pero no protege nada |
| Outputs | `edge_domain`, `waf_acl_arn` | Los consumen el `Gateway` de HU 08.2 y los CAs de HU 12.2 |

Y el orden de recursos en el *edge* es explícito, porque es donde se cometen los errores: **ACM (validación) → WAF → CloudFront → Route 53**. CloudFront no puede emitir un certificado sin Route 53 con el alias, y un certificado no valida sin el registro DNS.

Dos decisiones que se dejan escritas porque son fáciles de asumir al revés:
- **El rate limit del borde es por IP y el de la API es por usuario** (HU 05.2). No son redundantes: el borde para bots que ni autentican, la API para un usuario autenticado que abusa de su sesión. Si el borde usara reglas por usuario, tendría que autenticar, que es justo lo que no queremos en el borde.
- **El WAF no sustituye a los límites de la API.** `rate<0.001` (B-21) y los límites por usuario se siguen aplicando; el WAF es una capa de filtrado de tráfico, no de reglas de negocio.

**Referencia (backend y proveedor):**

```hcl
terraform {
  required_version = ">= 1.10"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
  backend "s3" {
    bucket       = "tix-tfstate-<account-id>"
    key          = "envs/staging/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true   # bloqueo nativo en S3
  }
}
```

**Criterios de Aceptación (CA):**
- `terraform plan` detalla los recursos exactos a modificar **sin aplicarlos**; el plan se adjunta al PR.
- La infraestructura completa se levanta exclusivamente mediante la CLI/pipeline, sin intervención manual en la consola (excepto el *bootstrap* inicial documentado del bucket de estado).
- Dos ejecuciones concurrentes de `apply` sobre el mismo entorno **no** se pisan (el segundo falla por *lock*).
- `terraform plan` inmediatamente posterior a un `apply` exitoso muestra **0 cambios** (sin *drift*).
- Ningún secreto ni clave de acceso aparece en el código ni en el estado en texto claro (usar Secrets Manager / `manage_master_user_password`).
- **`edge/` aplicado en `staging` y `prod` sin ningún recurso fuera del estado (B-13).** CA automático: `terraform plan` tras el `apply` muestra 0 cambios para CloudFront, WAF, ACM y Route 53, y los 4 *outputs* del módulo existen.
- **La ACL del WAF está *asociada* al *distribution*, no solo creada.** CA: un escaneo desde Internet que dispare la regla de *rate limit* es **bloqueado en el borde** (respuesta del WAF con 403, sin llegar al `ALB`); verificable comparando los `access logs` de CloudFront, que no deben contener esa petición. Con la ACL creada pero sin `association`, esta CA falla y el tráfico pasa.
- **`https://api.<dominio>/api/v1/...` sirve un TLS válido (cadena completa, sin aviso) y `http://` redirige a `https://` con HSTS.** CA: `openssl s_client -connect <dominio>:443 -servername <dominio>` valida la cadena contra ACM; `curl -I http://...` devuelve 301/308.

**Casos de Uso:**
- **Happy Path:** Se despliega un entorno réplica de *Staging* idéntico a Producción ajustando solo el archivo de variables (`staging.tfvars` vs `prod.tfvars`: tamaños de instancia, número de réplicas, Multi-AZ).
- **Failure Path:** El despliegue falla a la mitad por alcanzar el límite de cuota de IPs elásticas. Terraform **no revierte** lo ya creado: el estado refleja los recursos exitosos y el recurso fallido queda fuera del estado. Se solicita el aumento de cuota y se **re-ejecuta `apply`**, que converge. (Solo un recurso creado parcialmente —p. ej. falla un *provisioner*— queda marcado como *tainted*.)

**Hallazgos de la auditoría:** faltaban *state locking*, entornos, OIDC y análisis estático; el *failure path* describía incorrectamente el estado *tainted*. Costos: EKS + NAT + RDS Multi-AZ no son gratuitos; para aprender, desarrollar sobre `kind`/`k3d` local y levantar la nube en ventanas cortas con `terraform destroy` al terminar.

**Correcciones de la segunda auditoría (v3.0):**
- **B-13 (Alto):** añadido el módulo `edge/` de Terraform (CloudFront, WAF + *rate limit* + control de bots, ACM, Route 53) con su orden de recursos, sus dos decisiones explícitas y tres CA. El diagrama de la v2.0 prometía un borde que el árbol de módulos no contenía.

### HU 01.3 - Pipeline de Integración y Despliegue Continuo (CI/CD)
`[ORIGINAL · AMPLIADA]`

**Descripción:** Como equipo de ingeniería, quiero automatizar la validación y liberación del código con una cadena de suministro segura, para entregar nuevas funcionalidades de forma rápida y confiable.

**Tareas de Implementación:**
1. Configurar triggers en GitHub Actions para cada *Pull Request* hacia la rama principal (`main`, *trunk-based*) y proteger la rama (revisión obligatoria + *status checks* requeridos).
2. Implementar etapa de *Build* que compile el código y ejecute la suite de pruebas unitarias con **JUnit 5** y de integración con **Testcontainers** (PostgreSQL, Redis, Kafka reales).
3. Medir cobertura con **JaCoCo** y fallar el build bajo el umbral (≥ 80 % líneas en `domain`/`application`).
4. Añadir calidad y seguridad: formato/lint (Spotless/Checkstyle), **CodeQL** (SAST), análisis de dependencias (Dependabot/Renovate + OWASP Dependency-Check o Trivy), **gitleaks** para secretos.
5. Construir la imagen con `docker buildx` (multi-stage, ver HU 08.1), etiquetarla con el **SHA del commit** (nunca solo `latest`), publicarla en ECR/GHCR, **escanearla con Trivy**, generar **SBOM** y **firmarla con cosign** (*keyless*, OIDC).
6. Aplicar **GitOps con ArgoCD**: el pipeline *no* hace `kubectl apply`; actualiza el tag de imagen en un repo/carpeta de manifiestos (`gitops/`) mediante PR o commit automatizado, y ArgoCD sincroniza.
7. Definir `Application`/`ApplicationSet` de ArgoCD: *staging* con sync automático (`selfHeal`, `prune`) y *prod* con **promoción manual**.
8. Ejecutar las migraciones de Flyway como **Job *PreSync*** de ArgoCD (conexión directa a PostgreSQL, no por PgBouncer).
9. Documentar la estrategia de *rollback*: revertir el commit de GitOps (o `argocd app rollback`).

**Referencia (workflow mínimo):**

```yaml
name: ci
on:
  pull_request: { branches: [main] }
  push: { branches: [main] }
permissions: { contents: read }
jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: '21', cache: maven }
      - name: Build, tests y cobertura
        run: ./mvnw -B verify          # JUnit + Testcontainers + jacoco:check
      - uses: gitleaks/gitleaks-action@v2
  image:
    needs: build-test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write, id-token: write }
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with: { registry: ghcr.io, username: "${{ github.actor }}", password: "${{ secrets.GITHUB_TOKEN }}" }
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}/api:${{ github.sha }}
      - name: Escaneo de vulnerabilidades
        uses: aquasecurity/trivy-action@master   # fijar a un SHA/versión en uso real
        with:
          image-ref: ghcr.io/${{ github.repository }}/api:${{ github.sha }}
          severity: CRITICAL,HIGH
          exit-code: '1'
      - uses: sigstore/cosign-installer@v3
      - run: cosign sign --yes ghcr.io/${{ github.repository }}/api:${{ github.sha }}
```

> Fijar las *actions* por **SHA completo** en producción (mitiga ataques de cadena de suministro) y usar `permissions` mínimos por job.

**Criterios de Aceptación (CA):**
- Un *Pull Request* **no puede fusionarse** si falla alguna aserción de JUnit, cae la cobertura bajo el umbral de JaCoCo, `gitleaks` detecta un secreto o Trivy reporta vulnerabilidades CRITICAL/HIGH sin excepción documentada.
- Cada imagen en el registro es **trazable al commit** (tag = SHA), está **firmada** y tiene SBOM adjunto.
- El despliegue en producción se realiza **sin tiempo de inactividad** (*Rolling Update* con `maxUnavailable: 0`, *readiness probes*, *graceful shutdown* y `PodDisruptionBudget`; ver HU 08.2), verificado con una prueba de carga ligera durante el despliegue (0 errores 5xx).
- Tiempo de pipeline de PR (build + test) **< 10 min** p90 (cachés de Maven/Docker activos).
- *Rollback* a la versión anterior en **< 5 min** mediante revert de GitOps.

**Casos de Uso:**
- **Happy Path:** Código nuevo pasa linters y pruebas, se construye la imagen Docker, se escanea y firma, el pipeline abre el commit en `gitops/` y ArgoCD actualiza los pods automáticamente en *staging*; tras validar, se promueve a *prod*.
- **Failure Path:** Una prueba unitaria falla por un error de lógica; el pipeline se interrumpe y **bloquea** el merge y el despliegue a producción. Variante: la imagen despliega pero las sondas de *readiness* nunca pasan → el *rollout* no avanza, los pods viejos siguen sirviendo y ArgoCD marca la aplicación como *Degraded*.

**Hallazgos de la auditoría:** el pipeline no tenía seguridad de cadena de suministro, no definía qué pasa con migraciones ni cómo se promueve entre entornos, y "sin tiempo de inactividad" no estaba respaldado por la configuración necesaria (A-10, A-19).

### HU 01.4 - Configuración, Secretos y Entornos
`[NUEVA]`

**Descripción:** Como equipo de ingeniería, quiero una gestión de configuración y secretos consistente entre entornos, para que ninguna credencial viaje en el código ni en las imágenes y los despliegues sean reproducibles.

**Tareas de Implementación:**
1. Aplicar los principios *12-factor*: configuración por variables de entorno/`ConfigMap`, perfiles de Spring (`local`, `staging`, `prod`), la misma imagen en todos los entornos.
2. Gestionar secretos con **External Secrets Operator** + AWS Secrets Manager (alternativa: Sealed Secrets). Prohibido versionar secretos en texto claro.
3. Configurar `gitleaks` como *pre-commit hook* y en CI.
4. Validar la configuración al arranque (`@ConfigurationProperties` + `@Validated`): la app **falla rápido** si falta una variable crítica.
5. Definir rotación: contraseñas de DB y claves de firma JWT rotables sin *downtime* (ver HU 02.2).
6. Documentar el mapa de entornos (local, CI, staging, prod) y sus diferencias en Confluence.

**Criterios de Aceptación (CA):**
- Un escaneo del historial de git con `gitleaks` devuelve **0 hallazgos**.
- La app no inicia (exit ≠ 0) si falta `DB_URL`, `REDIS_LOCKS_URL` o la clave de firma, con mensaje claro en el log.
- Rotar la contraseña de la base de datos no requiere reconstruir imágenes (solo actualizar el secreto y reiniciar *rolling*).

**Casos de Uso:**
- **Happy Path:** Se crea un secreto nuevo en Secrets Manager; External Secrets lo sincroniza a un `Secret` de K8s y los pods lo consumen como variable de entorno sin cambios de código.
- **Failure Path:** Un desarrollador intenta *commitear* una clave de AWS; el *hook* `pre-commit` (o el job de CI) bloquea el cambio.

## Épica 02: Autenticación, Usuarios y Seguridad

**Objetivo de aprendizaje:** Spring Security, hashing de contraseñas, JWT/JWKS, rotación de refresh tokens, OWASP API Top 10.

### HU 02.1 - Registro de Clientes y Hashing Seguro
`[ORIGINAL · AMPLIADA]`

**Descripción:** Como cliente, quiero crear una cuenta de forma segura, para acceder a la compra de entradas.

**Tareas de Implementación:**
1. Crear endpoint de registro `POST /api/v1/users/register` (B-39) con contrato OpenAPI y errores en formato **RFC 9457** (`application/problem+json`).
2. Implementar validación de formato de email (normalizado a minúsculas) y **fortaleza de contraseña según NIST SP 800-63B**: longitud mínima 12 (permitir ≥ 64), sin reglas de composición forzadas, rechazo de contraseñas filtradas (API de *k-anonymity* de Have I Been Pwned o lista local) y de las más comunes.
3. Aplicar **Argon2id** (recomendado) o BCrypt para hashear la contraseña antes de guardarla en la DB:
   - Argon2id: mínimo OWASP ≈ 19 MiB de memoria, 2 iteraciones, paralelismo 1 (calibrar para ~100–250 ms en el hardware de producción).
   - BCrypt: *work factor* ≥ 10 (límite de 72 bytes de entrada).
   - Usar `DelegatingPasswordEncoder` de Spring Security para poder **migrar de algoritmo** sin invalidar hashes existentes (`{argon2}...`, `{bcrypt}...`).
4. Crear `users` con índice único sobre `lower(email)` (o tipo `citext`) y flujo de **verificación de email** (token aleatorio, almacenado como hash, TTL 24 h).
5. Proteger el endpoint con *rate limiting* (HU 05.2) y un *bulkhead* para el hashing (el hashing es intencionalmente costoso: limitar su concurrencia evita saturar CPU).
6. Registrar el evento `user.registered` vía *outbox* (HU 07.2) para el email de bienvenida/verificación.

**Referencia (Spring Security):**

```java
@Bean
PasswordEncoder passwordEncoder() {
    // Argon2id con los valores de OWASP, NO los defaults de Spring:
    // defaultsForSpringSecurity_v5_8() usa 16 MiB y la tarea exige >= 19 MiB (B-10)
    var argon2 = new Argon2PasswordEncoder(19 * 1024, 2, 1, 32, 256);
    return new DelegatingPasswordEncoder("argon2",
        Map.of("argon2", argon2, "bcrypt", new BCryptPasswordEncoder(12)));
}
```

> **B-10:** los parámetros van explícitos a propósito. Si se usa `Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()`, la memoria baja a 16 MiB y el hash queda por debajo del mínimo de OWASP que pide la tarea 3, sin que nada lo señale. Los valores viven en configuración (`app.security.argon2.*`) para poder recalibrar sin recompilar; el CA de 100–250 ms mide esa calibración.

**Criterios de Aceptación (CA):**
- La base de datos nunca almacena la contraseña en texto plano; el campo `password_hash` incluye el prefijo del algoritmo.
- Intentos de registro con un email existente (comparación sin distinguir mayúsculas) devuelven `409 Conflict`.
- Contraseñas por debajo del mínimo o presentes en la lista de filtradas devuelven `400 Bad Request` con detalle por campo.
- El hash tarda entre 100 y 250 ms en el entorno objetivo (medido en un test de integración que falla fuera de rango amplio).
- Un usuario no verificado **no puede** hacer *hold* ni comprar.

**Casos de Uso:**
- **Happy Path:** Usuario ingresa datos válidos, el sistema guarda el hash y devuelve `201 Created`; recibe un email con el enlace de verificación.
- **Failure Path:** Usuario ingresa una contraseña débil (ej. "1234"); la API la rechaza con `400 Bad Request` y un mensaje accionable. Variante: ráfaga de 5 000 registros/s (bot) → los *rate limits* y el *bulkhead* devuelven `429`/`503` sin saturar la CPU.

**Hallazgos de la auditoría:** parámetros de hashing no definidos, política de contraseñas ausente y riesgo de DoS por costo de CPU. El `409` permite *enumerar* emails registrados: se acepta por UX pero con *rate limiting* y CAPTCHA como mitigación (ADR-006); la alternativa es responder siempre `202 Accepted` y notificar por email.

**Correcciones de la segunda auditoría (v3.0):**
- **B-10:** el código de referencia usaba `Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()`, que baja la memoria a 16 MiB — por debajo del mínimo de ~19 MiB que exige la tarea 3. Los parámetros ahora son explícitos y configurables.
- **B-37:** el DDL de `users` y del token de verificación de email sigue en HU 03.1; esta HU solo lo referencia.
- **B-39:** el endpoint pasa a `/api/v1/users/register` y el contrato OpenAPI se versiona.

### HU 02.2 - Login y Emisión de JWT / OAuth2
`[ORIGINAL · AMPLIADA]`

**Descripción:** Como cliente, quiero autenticarme con email y contraseña, para obtener un token de acceso a la plataforma.

**Tareas de Implementación:**
1. Crear endpoint `POST /api/v1/users/login`.
2. Implementar comparación segura del hash de la contraseña, **en tiempo constante** respecto de la existencia del usuario: si el email no existe, verificar igual contra un hash ficticio para evitar *timing attacks*.
3. Generar *Access Token* (JWT) de corta duración (15 min) firmado con **clave asimétrica** (EdDSA o RS256), con `kid` en el encabezado, y publicar las claves públicas en un endpoint **JWKS** (`/.well-known/jwks.json`) para que los demás servicios validen sin compartir secretos.
4. Claims mínimos: `sub` (ID de usuario), `roles`, `iat`, `exp`, `iss`, `aud`, `jti`.
5. Generar el *Refresh Token* como valor **opaco aleatorio** (≥ 256 bits) entregado en cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth` (HU 02.3 cubre rotación).
6. Protección contra fuerza bruta: contadores en Redis por **cuenta** y por **IP**, con *backoff* progresivo (1 s, 2 s, 4 s… hasta un máximo) y respuesta `429` con `Retry-After`; CAPTCHA tras N fallos. Evitar el bloqueo permanente (vector de DoS contra cuentas ajenas).
7. Configurar los servicios como *OAuth2 Resource Server* (`spring-boot-starter-oauth2-resource-server`) validando firma, `iss`, `aud` y `exp`.
8. Documentar la rotación de claves: publicar la clave nueva en JWKS, firmar con ella y retirar la anterior tras `exp` máximo (15 min) + margen.
9. **Versionado de API (B-39).** Todas las rutas cuelgan de un prefijo `/api/v1` (`/api/v1/users/register`, `/api/v1/auth/refresh`, …). El contrato OpenAPI se publica desde el código y un test de contrato en CI falla si un cambio introduce un campo o cambia un tipo sin actual version. Los tópicos de Kafka ya están versionados por nombre (`orders.events.v1`); la API usa el mismo criterio.

**Referencia (cadena de filtros mínima):**

```java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        // B-08: NO se ignora CSRF en toda la API. /api/v1/auth/refresh y /api/v1/auth/logout
        // se invocan con cookie y sin header Authorization: si se ignoran, un sitio
        // un sitio third-party puede rotar la sesion del usuario. El CSRF token de
        // doble submit se exime solo en las rutas que usan exclusivamente Bearer.
        .csrf(csrf -> csrf
            .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
            .ignoringRequestMatchers("/api/v1/users/register", "/api/v1/users/login"))
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(a -> a
            // B-08: /api/v1/auth/refresh debe ser permitAll. Con el access token expirado
            // (que es exactamente cuando se usa) Spring responde 401 antes de llegar
            // al controlador, y el flujo de renovacion no funciona nunca.
            .requestMatchers(
                "/api/v1/users/register",
                "/api/v1/users/login",
                "/api/v1/auth/refresh",
                "/api/v1/auth/logout",
                "/.well-known/jwks.json",
                "/actuator/health/**").permitAll()
            .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .build();
}
```

> **B-08 (dos errores encadenados).** En la v2.0 el flujo de *refresh* era inalcanzable: el endpoint no estaba en `permitAll`, así que un cliente con el *access token* expirado —el único caso en que se refresca— recibía `401` en el filtro y nunca llegaba al controlador. Y la compensacion de ese problema, `csrf().ignoringRequestMatchers("/api/**")`, desactivaba la protección en **toda** la API, incluida la única ruta que sí usa cookie. La corrección es dejar CSRF activo y eximir solo las dos rutas que no dependen de cookie.

**Criterios de Aceptación (CA):**
- El JWT contiene el ID del usuario y su rol en los *claims* y se valida con JWKS (verificable con un test que firma con una clave desconocida y espera `401`).
- Las credenciales inválidas devuelven consistentemente `401 Unauthorized` **sin revelar** si el fallo fue el email o la contraseña; la diferencia de tiempo de respuesta entre "email inexistente" y "contraseña incorrecta" es **< 10 %**.
- Tras 5 intentos fallidos sobre la misma cuenta, el sexto devuelve `429` con `Retry-After`; el usuario legítimo puede volver a intentar tras el *backoff* y no queda bloqueado indefinidamente.
- El *refresh token* nunca es accesible desde JavaScript (`HttpOnly`) y viaja solo por HTTPS.
- `POST /api/v1/auth/refresh` con el *access token* **expirado** devuelve `200` con un par nuevo (no `401`): es el escenario real de uso y el que la v2.0 rompía.
- `POST /api/v1/auth/refresh` **sin** el header `X-XSRF-TOKEN` y **con** la cookie de *refresh* presente devuelve `403` (B-08). El test envía la cookie y omite el token a propósito.
- Un token de *access* usado contra `/api/v1/auth/refresh` devuelve `401`, no `200`.

**Casos de Uso:**
- **Happy Path:** Credenciales correctas generan los tokens y permiten acceso a rutas protegidas.
- **Failure Path:** Múltiples intentos fallidos (ej. >5) sobre una cuenta o desde una IP activan *backoff* progresivo y `429`, mitigando ataques de fuerza bruta **sin bloquear permanentemente** a usuarios detrás de una misma NAT.

**Hallazgos de la auditoría:** el plan bloqueaba la IP, lo cual penaliza redes compartidas y no detiene ataques distribuidos; no definía algoritmo, `kid`, JWKS, rotación de claves ni revocación (A-13, A-14). El título "JWT / OAuth2" mezclaba conceptos: aquí se implementa JWT con validación estilo OAuth2 Resource Server; el *flujo* OAuth2/OIDC completo (Keycloak) queda como alternativa en ADR-006.

**Correcciones de la segunda auditoría (v3.0):**
- **B-08 (crítico, dos fallos encadenados):** (1) `/api/v1/auth/refresh` no estaba en `permitAll`, de modo que el flujo de renovación devolvía `401` siempre que hacía falta — justo cuando el *access token* ya expiró; (2) el arreglo que la v2.0 daba a eso (`csrf().ignoringRequestMatchers("/api/**")`) desactivaba CSRF en toda la API, incluida la única ruta que usa cookie. El código nuevo mantiene CSRF activo con doble submit y exime solo las rutas que no dependen de cookie.
- **B-39:** las rutas llevan el prefijo `/api/v1` y hay tests de contrato en CI.

### HU 02.3 - Refresh Tokens con Rotación, Logout y Revocación
`[NUEVA]`

**Descripción:** Como cliente, quiero mantener mi sesión de forma segura y poder cerrarla en todos mis dispositivos, para que el robo de un token no comprometa mi cuenta indefinidamente.

**Tareas de Implementación:**
1. Crear la tabla `refresh_tokens` (DDL en §"Esquema" de esta HU, migración `V2__refresh_tokens.sql`); guardar **solo el hash** (SHA-256) del token.
2. `POST /api/v1/auth/refresh`: validar token, marcarlo como usado y emitir un **par nuevo** (rotación en cada uso) dentro de la misma `family_id`. Requiere CSRF activo (B-08) y `permitAll` (B-08).
3. **Detección de reutilización:** si llega un token ya usado, revocar **toda la familia** y exigir login (indicio de robo).
4. `POST /api/v1/auth/logout` (revoca la familia actual) y `POST /api/v1/auth/logout-all` (revoca todas las familias del usuario).
5. Para revocar *access tokens* antes de `exp` (baneo, cambio de contraseña), mantener un *denylist* de `jti` en Redis con TTL igual al tiempo restante.
6. Limpieza periódica de tokens expirados (job con ShedLock para ejecución única entre pods).

**Esquema (B-37):**

```sql
-- V2__refresh_tokens.sql
CREATE TABLE refresh_tokens (
    id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     uuid        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    family_id   uuid        NOT NULL,
    token_hash  bytea       NOT NULL,              -- SHA-256 del token opaco
    expires_at  timestamptz NOT NULL,
    used_at     timestamptz,
    revoked_at  timestamptz,
    created_at  timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT ck_refresh_tokens_expiry CHECK (expires_at > created_at)
);

-- La busqueda critica es "hash de este token -> fila", una sola por request.
CREATE UNIQUE INDEX ux_refresh_tokens_hash ON refresh_tokens (token_hash);
-- "familias activas de este usuario" para logout-all y para revocar por familia.
CREATE INDEX ix_refresh_tokens_user_active
    ON refresh_tokens (user_id, family_id)
    WHERE revoked_at IS NULL AND used_at IS NULL;
-- Purga periodica: solo mira tokens expirados.
CREATE INDEX ix_refresh_tokens_expires ON refresh_tokens (expires_at);
```

> **Por qué `token_hash` es `bytea` y no `text`:** 32 bytes de SHA-256 en binario ocupan la mitad y no dependen de la codificación. El token opaco se genera con 32 bytes de `SecureRandom` y se entrega en Base64URL; la DB nunca ve esa cadena.
>
> **Por qué un índice parcial y no un índice simple:** la consulta de `logout-all` y de revocación por familia siempre filtra por "tokens vivos de esta familia". El índice parcial cubre exactamente ese conjunto y no se ensucia con tokens ya usados, que son la mayoría tras unas horas.

**Criterios de Aceptación (CA):**
- Usar el mismo *refresh token* dos veces invalida la familia: el segundo uso devuelve `401` y el token "nuevo" legítimo deja de funcionar.
- `POST /api/v1/auth/refresh` con el *access token* expirado devuelve `200` con un par nuevo (B-08).
- `POST /api/v1/auth/refresh` con la cookie presente pero sin `X-XSRF-TOKEN` devuelve `403` (B-08).
- Tras `logout-all`, ningún *access token* del usuario es aceptado en **≤ 15 s** (propagación del denylist).
- Ningún *refresh token* en texto claro existe en la base de datos: un `SELECT` sobre `token_hash` devuelve 32 bytes binarios, no una cadena imprimible.

**Casos de Uso:**
- **Happy Path:** El cliente renueva silenciosamente su sesión cada 15 min; cada renovación entrega un refresh nuevo.
- **Failure Path:** Un atacante usa un refresh robado después de que el cliente ya lo rotó; el sistema detecta la reutilización, revoca la familia y fuerza un nuevo login.

### HU 02.4 - Autorización (RBAC), Aislamiento de Datos y Hardening de la API
`[NUEVA]`

**Descripción:** Como responsable de seguridad, quiero que cada endpoint aplique autorización por rol y por propiedad del recurso, para prevenir accesos indebidos (OWASP API Top 10).

**Tareas de Implementación:**
1. Definir roles: `CUSTOMER`, `ORGANIZER`, `SUPPORT`, `ADMIN`; autorización con `@PreAuthorize` y pruebas por cada combinación.
2. **Control de propiedad (anti-IDOR):** un cliente solo ve/modifica sus propias órdenes y tickets; consultas siempre filtradas por `user_id` del token.
3. Validación de entrada con Bean Validation; límites de tamaño de *payload*; rechazo de campos desconocidos.
4. Cabeceras de seguridad (HSTS, `X-Content-Type-Options`, `Content-Security-Policy` para el front), CORS con lista blanca explícita.
5. Registro de **auditoría** (`audit_log`, DDL abajo, migración `V3__audit_log.sql`) para acciones de administración (quién, qué, cuándo, IP).
6. Checklist OWASP API Security Top 10 revisado y archivado en Confluence.
7. Versionado de API (B-39): los paths llevan `/api/v1`; los 404 de IDOR son deliberados y el contrato los documenta.

**Esquema (B-37):**

```sql
-- V3__audit_log.sql
CREATE TABLE audit_log (
    id          bigserial   PRIMARY KEY,
    actor_id    uuid        REFERENCES users(id) ON DELETE SET NULL,  -- NULL si el actor fue borrado
    action      text        NOT NULL,   -- 'order.refund', 'event.publish', 'user.ban', ...
    resource    text        NOT NULL,   -- 'order:8f3c-...'
    before      jsonb,
    after       jsonb,
    ip          inet,
    user_agent  text,
    correlation_id uuid,                              -- mismo ID que las trazas (HU 09.2)
    created_at  timestamptz NOT NULL DEFAULT now()
);

-- Consulta canonica: "que hizo este usuario", en orden cronologico.
CREATE INDEX ix_audit_log_actor_time ON audit_log (actor_id, created_at DESC);
-- Consulta canonica: "que le paso a este recurso".
CREATE INDEX ix_audit_log_resource    ON audit_log (resource, created_at DESC);
```

> **`append-only`:** `audit_log` no tiene `UPDATE` ni `DELETE` en el código de aplicación; el rol de la aplicación recibe solo `INSERT` y `SELECT`. La retención se aplica con `pg_cron` + `DROP PARTITION`, no con un `DELETE` que deje huecos en la secuencia.

**Criterios de Aceptación (CA):**
- Un usuario A solicitando `GET /api/v1/orders/{id}` de un usuario B recibe `404` (no `403`, para no confirmar la existencia).
- Un `CUSTOMER` accediendo a `/api/v1/admin/**` recibe `403`; sin token, `401`.
- Existe un test automatizado por cada endpoint que verifica matriz rol × recurso.
- Toda acción de administración deja una fila en `audit_log` con `actor_id`, `action`, `resource`, `ip` y `correlation_id` igual al de la traza OpenTelemetry de esa request.

**Casos de Uso:**
- **Happy Path:** Un organizador crea un evento y solo él (y los administradores) pueden modificarlo.
- **Failure Path:** Un cliente modifica el `orderId` en la URL para ver compras ajenas (IDOR); el servicio responde `404` y registra el intento en logs de seguridad.

**Tercera auditoría (coherencia transversal, v3.0):** no añade hallazgos nuevos; comprueba que los anteriores estén realmente resueltos y que no se contradigan entre documentos.
