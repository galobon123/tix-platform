## Épica 07: Event Streaming con Kafka

**Objetivo de aprendizaje:** operación de Kafka en KRaft, diseño de tópicos y claves, *Schema Registry*, patrón *Transactional Outbox*, consumidores idempotentes, DLQ y reprocesamiento.

> Kafka figuraba en el stack y en el `docker-compose`, pero sin HU (A-04). Esta épica define cómo logra el **desacoplamiento asíncrono y la consistencia eventual** del cuadro objetivo sin sacrificar la corrección transaccional.

### HU 07.1 - Cluster, Tópicos y Contratos de Eventos
`[NUEVA]`

**Descripción:** Como equipo de plataforma, quiero un cluster Kafka duradero con tópicos y esquemas gobernados como código, para que productores y consumidores evolucionen sin romperse.

**Tareas de Implementación:**
1. Desplegar Kafka con **Strimzi** sobre Kubernetes en modo **KRaft** (ADR-011), con **pools separados de *controllers* y *brokers* (B-24)**: 3 *controllers* dedicated y 3 *brokers*, almacenamiento persistente, `default.replication.factor=3`, `min.insync.replicas=2`.
   ```yaml
   apiVersion: kafka.strimzi.io/v1beta2
   kind: KafkaNodePool
   metadata: { name: controllers, labels: { strimzi.io/cluster: tickets } }
   spec:
     replicas: 3
     roles: [controller]
     storage: { type: jbod, volumes: [{ id: 0, type: persistent-claim, size: 100Gi, deleteClaim: false }] }
   ---
   apiVersion: kafka.strimzi.io/v1beta2
   kind: KafkaNodePool
   metadata: { name: brokers, labels: { strimzi.io/cluster: tickets } }
   spec:
     replicas: 3
     roles: [broker]
     storage: { type: jbod, volumes: [{ id: 0, type: persistent-claim, size: 500Gi, deleteClaim: false }] }
     jvmOptions: { -Xmx: 3Gi }          # los brokers necesitan memoria por page cache
   ---
   apiVersion: kafka.strimzi.io/v1beta2
   kind: Kafka
   metadata:
     name: tickets
     annotations: { strimzi.io/node-pools: enabled, strimzi.io/kraft: enabled }
   spec:
     kafka:
       listeners: [{ name: tls, port: 9093, type: internal, tls: true }]
       config:
         default.replication.factor: 3
         min.insync.replicas: 2
         offsets.topic.replication.factor: 3
         transaction.state.log.replication.factor: 3
         transaction.state.log.min.isr: 2
       # B-24: sin esto, un nodo podria vender y factores al mismo tiempo
       # B-24: sin esto, un nodo podria vender y ser factor al mismo tiempo
       # B-24: sin esto, un nodo podria vender y ser factor al mismo tiempo
       # y una falla de red lo dejaria aislado del quorum
       controller.quorum.voters: 0,1,2@tickets-controllers-0.tickets-controllers:9090
     entityOperator: { topicOperator: {}, userOperator: {} }
   ```
   **Por qué pools separados (B-24).** La v2.0 usaba `roles: [controller, broker]` en un único `KafkaNodePool` de 3 nodos. Eso funciona, pero es exactamente lo que Strimzi recomienda **no** hacer en producción: los *controllers* hacen consenso con quórum y necesitan CPU y disco estables; los *brokers* hacen I/O de datos y necesitan page cache. En un nodo dual-role, la presión de página del tráfico de datos introduce *delays* en el consenso, y un GC largo en un broker puede retrasar los heartbeats del quórum. Con 3 nodos, perder **dos** nodos simultáneos es un escenario de quorum lost: sin recursos dedicados, es más fácil de llegar ahí. Los pools separados también permiten dimensionar el disco de forma distinta (100 GiB de metadata contra 500 GiB de datos).
   *(Validar los campos contra la versión de Strimzi instalada: la API evoluciona, y `controller.quorum.voters` se reemplaza por `controller.quorum.bootstrap.servers` en versiones recientes.)*
2. Definir los tópicos como `KafkaTopic` en el repo GitOps:

   | Tópico | Clave de partición | Particiones | Retención | Notas |
   |---|---|---|---|---|
   | `orders.events` | `orderId` | 12 | 7 d | ciclo de vida de la orden |
   | `seats.events` | `seatId` (o `eventId:shard<K>`) | 24 | 3 d | ventas/liberaciones; alimenta proyecciones y SSE |
   | `payments.events` | `orderId` | 12 | 7 d | resultados de pago |
   | `notifications.commands` | `userId` | 12 | 3 d | emails/push |
   | `<tópico>.dlt` | igual que origen | = origen | 14 d | mensajes no procesables |
   | `<tópico>.archive` | igual que origen | = origen | 2 años | retención larga para reconstrucciones |

   > La **clave determina el orden**: Kafka solo garantiza orden dentro de una partición. Elegir una clave que agrupe lo que necesita orden (`orderId`) pero reparta la carga.
   >
   > **B-30: la clave de `seats.events` era `eventId:section`.** El propio texto de la v2.0 razonaba el riesgo de partición caliente solo para `eventId`, y después caía en él con `eventId:section`: en un estadio grande, **una** sección (una tribuna con 20 000 asientos) sigue concentrating en **una** partición, con toda su carga. Dos salidas, y `seats.events` **no necesita** orden por asiento más allá de la transacción que lo produjo:
   > - `seatId` como clave: reparto perfecto y orden por asiento irrelevante (cada asiento es independiente). Es la opción por defecto.
   > - `eventId:shard<K>` si de verdad hiciera falta agrupar por evento: reparto uniforme dentro del evento y, además, el `shard<K>` reparte la clave entre slots de Redis.
   >
   > Con `seatId`, además, **cada evento vive en todas las particiones**, lo que es lo que hace trivial el escalado del proyector y del SSE.
   >
   > **B-31: la retenión debe permitir reconstrucciones.** La v2.0 afirmaba que las proyecciones eran "reconstruibles reprocesando desde el *offset* 0", pero con `retention.ms = 7 d` (o 3 d) el *offset* 0 de un evento de hace un mes **ya no existe**: Kafka lo habría borrado, y el consumidor arranca en el *earliest* disponible, que es hace 7 días. La reconstrucción sale incompleta y silenciosamente. Dos salidas, y hay que elegir una explícitamente:
   > - **Tópico de archivo** (la fila `<tópico>.archive` de la tabla, 2 años): los topics de retenciones cortas publican una copia o los eventos se escriben directamente al topic de archivo con retención larga.
   > - **Alcance explícito:** las proyecciones se reconstruyen **desde el *offset* más temprano disponible** y la documentación dice que para eventos anteriores a la ventana hay que recargar desde PostgreSQL. Menos elegante, pero honesto.
   >
   > La v3.0 adopta la primera opción y añade un CA en HU 07.4 que reconstruye una proyección desde un evento de hace 30 días.
3. **Configuración de productor:** `acks=all`, `enable.idempotence=true`, `compression.type=zstd` (o `lz4`), `linger.ms=5`, `delivery.timeout.ms=120000`.
4. Desplegar un **Schema Registry** (compatible con Confluent: Apicurio o Karapace), formato Avro o Protobuf, compatibilidad `BACKWARD`; el CI **falla** ante un cambio de esquema incompatible.
5. Estandarizar el **sobre del evento**: `id` (UUID), `type`, `source`, `time`, `subject`, `dataVersion`, `traceparent` (W3C), `data`.
6. Documentar el catálogo de eventos con **AsyncAPI** en Confluence.
7. Para desarrollo local, agregar una UI de Kafka (p. ej. Kafka UI) al perfil `obs` del compose.

**Criterios de Aceptación (CA):**
- Con un broker caído, los productores con `acks=all` **no pierden mensajes** ni se detienen; con dos caídos, producir **falla de forma explícita** (`NotEnoughReplicas`) en lugar de perder datos silenciosamente.
- Un cambio de esquema incompatible no pasa el CI.
- Todos los tópicos y ACL existen como código; ninguno se crea manualmente.

**Casos de Uso:**
- **Happy Path:** Se publica `order.paid` con clave `orderId`; todos los eventos de esa orden llegan en orden a un mismo consumidor.
- **Failure Path:** Un productor intenta publicar con un esquema incompatible; el registro lo rechaza y el despliegue se bloquea antes de llegar a producción.

### HU 07.2 - Transactional Outbox (Consistencia entre PostgreSQL y Kafka)
`[NUEVA]`

**Descripción:** Como sistema, quiero publicar eventos si y solo si la transacción de negocio se confirma, para evitar la "doble escritura" que deja a la DB y a Kafka inconsistentes.

**Tareas de Implementación:**
1. Crear la tabla `outbox_events` y escribir en ella **dentro de la misma transacción** que el cambio de negocio:
   ```sql
   CREATE TABLE outbox_events (
     seq            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
     id             uuid NOT NULL UNIQUE,
     aggregate_type text NOT NULL,
     aggregate_id   text NOT NULL,
     type           text NOT NULL,
     payload        jsonb NOT NULL,
     headers        jsonb NOT NULL DEFAULT '{}',
     created_at     timestamptz NOT NULL DEFAULT now(),
     published_at   timestamptz
   );
   CREATE INDEX idx_outbox_pending ON outbox_events (seq) WHERE published_at IS NULL;
   ```
2. **Relay v1 (polling)** en el `worker`: lee un lote, publica y marca como publicado, todo en una transacción:
   ```sql
   SELECT seq, id, aggregate_type, aggregate_id, type, payload, headers
     FROM outbox_events
    WHERE published_at IS NULL
    ORDER BY seq
    LIMIT 200
      FOR UPDATE SKIP LOCKED;
   ```
   Para **preservar el orden por agregado**, usar una sola instancia activa del relay (ShedLock) o particionar el outbox por `hash(aggregate_id) % N` con un relay por partición.
3. Garantía resultante: **al menos una vez**. Un *crash* tras publicar y antes de marcar produce duplicados → los consumidores **deben ser idempotentes** (HU 07.3).
4. Limpieza: borrar eventos publicados con más de 7 días (borrado por lotes o particionado por fecha).
5. **Relay v2 (CDC con Debezium)**: `wal_level=logical`, publicación y *replication slot*, `KafkaConnect`/`KafkaConnector` con el SMT *Outbox Event Router*. La conexión de Debezium es **directa** a PostgreSQL (no vía PgBouncer). **Monitorear el retraso del *slot*** (`pg_replication_slots`): un slot atascado retiene WAL y puede llenar el disco.
6. Métricas: `outbox.pending` (filas sin publicar), `outbox.lag.seconds`, `outbox.publish.errors`.

**Criterios de Aceptación (CA):**
- Si la transacción de negocio falla, **no** existe el evento; si se confirma, **existe** (test que fuerza una excepción tras el `INSERT` en la tabla de negocio).
- Matar el relay en mitad de un lote no pierde eventos; los duplicados resultantes son absorbidos por los consumidores (test de caos).
- Retraso del *outbox* p99 **< 2 s** en carga nominal; alerta si `outbox.pending` crece de forma sostenida por > 1 min.
- El *relay* no compite con las transacciones de negocio: la consulta usa el índice parcial y no genera bloqueos de larga duración.

**Casos de Uso:**
- **Happy Path:** `confirmSale` actualiza los asientos y escribe `seat.sold` en el *outbox*; el relay lo publica en < 2 s.
- **Failure Path:** Kafka no está disponible 5 minutos; el *outbox* acumula eventos, `outbox.pending` dispara la alerta, y al recuperarse Kafka el relay vacía la cola en orden sin pérdida.

### HU 07.3 - Consumidores Idempotentes, Reintentos y Dead Letter Topics
`[NUEVA]`

**Descripción:** Como equipo de backend, quiero consumidores que toleren duplicados, reordenamientos y mensajes defectuosos, para que un evento "veneno" no detenga el procesamiento.

**Tareas de Implementación:**
1. **Idempotencia:** tabla `processed_events(consumer text, event_id uuid, processed_at timestamptz, PRIMARY KEY (consumer, event_id))`. Dentro de la misma transacción del efecto: `INSERT ... ON CONFLICT DO NOTHING`; si no se insertó nada, **saltar** el procesamiento.
2. Confirmar *offsets* **después** del procesamiento (`enable.auto.commit=false`, `AckMode` por registro o lote).
3. **Reintentos no bloqueantes** con tópicos de reintento y *backoff* exponencial; tras agotar intentos, enviar al **DLT**. En Spring Kafka: `@RetryableTopic(attempts = "4", backoff = @Backoff(delay = 1000, multiplier = 4))` + `@DltHandler`.
4. Clasificar excepciones: **no reintentables** (deserialización, validación) van directo al DLT; las transitorias se reintentan. Usar `ErrorHandlingDeserializer`.
5. Ajustes de consumidor: `max.poll.records` moderado, `max.poll.interval.ms` acorde al trabajo, `partition.assignment.strategy=CooperativeStickyAssignor`, `concurrency` ≤ número de particiones.
6. Procedimiento y herramienta de **reproceso desde el DLT** (runbook) con límite de tasa.
7. Aclarar semántica: *exactly-once* de Kafka aplica a flujos Kafka→Kafka; para Kafka→PostgreSQL se logra **efecto exactamente-una-vez** mediante *at-least-once* + idempotencia.
8. Métricas: `kafka.consumer.lag`, `consumer.processed{result}`, `dlt.messages`.

**Criterios de Aceptación (CA):**
- Entregar el mismo evento 100 veces produce **un único efecto** (1 ticket, 1 email).
- Un mensaje con *payload* corrupto termina en el DLT tras ≤ N intentos **sin bloquear** la partición ni a los mensajes posteriores.
- Tras reiniciar el `worker` con 100 000 mensajes pendientes, el *lag* converge a 0 sin duplicar efectos.
- Alerta cuando `dlt.messages` > 0 durante 5 min.

**Casos de Uso:**
- **Happy Path:** `order.paid` se procesa una vez, se emite el ticket y se confirma el *offset*.
- **Failure Path:** El servicio de email falla de forma intermitente; el mensaje pasa por 3 tópicos de reintento con *backoff* y finalmente se entrega; si el proveedor sigue caído, queda en el DLT con alerta, sin afectar al resto del flujo.

### HU 07.4 - Consumidores de Dominio y Proyecciones
`[NUEVA]`

**Descripción:** Como plataforma, quiero consumidores especializados que reaccionen a los eventos, para mantener lecturas rápidas y efectos secundarios desacoplados del camino crítico de compra.

**Tareas de Implementación:**
1. `ticket-issuer`: consume `order.paid` → emite tickets (HU 06.4) → publica `order.fulfilled`.
2. `notification-consumer`: consume `notifications.commands`/`order.fulfilled` → envía email con límites de tasa del proveedor; deduplicación por `notification_id`.
3. `availability-projector`: consume `seat.sold`/`seat.blocked`/`order.expired` → mantiene `unavailable:{evt:sec}` en `redis-locks` (**no** `sold:{evt:sec}`: `BLOCKED` también ocupa el asiento, ver **B-01** en `03.md`) y **publica el delta en Redis Pub/Sub** en el canal `seats:events:{evt}` (**B-14** / ADR-017), que es lo que alimenta el SSE de HU 04.6. Publicar en Redis, no reenviar por Kafka desde el proyector: el SSE es un camino de baja latencia y no debe esperar al *round trip* de un tópico más un consumidor.
4. `sales-analytics`: proyección de lectura (tabla agregada por evento/hora) para paneles de negocio; **reconstruible desde el tópico de archivo**, no desde el *offset* 0 del tópico de retenciones cortas (**B-31**). El procedimiento documentado es: `kafka-console-consumer.sh --topic sales-analytics.archive --from-beginning`, con el *Schema Registry* y el mismo *consumer group* logic para deduplicar.
5. Propagar el contexto de trazas en cabeceras de Kafka (`traceparent`) para trazas de extremo a extremo (HU 09.2).

**Criterios de Aceptación (CA):**
- Latencia evento→proyección (`seat.sold` → Redis actualizado y delta publicado en Pub/Sub) **p99 < 1 s**.
- **Una proyección reconstruida desde el tópico de archivo produce exactamente el mismo estado que la proyección viva**, sin duplicados y sin intervención manual (B-31). CA: se publica un `seat.sold` de hace 30 días (más allá de la retención de 3 d de `seats.events`), se purga la proyección, se reconstruye desde `<tópico>.archive` y el resultado coincide con el *snapshot* previo. **Este CA no puede pasar con `retention.ms = 3 d`** y es el que hace obligatoria la fila `<tópico>.archive` de la tabla de HU 07.1.
- Un `seat.blocked` (un asiento que un operador bloquea, no una venta) también aparece en `unavailable:{evt:sec}` y desaparece del SSE como no disponible (B-01).
- Un consumidor caído **no** degrada ni bloquea el camino de compra (el `hold` y el `checkout` siguen operando).

**Casos de Uso:**
- **Happy Path:** Una venta actualiza el mapa de todos los clientes conectados en menos de 2 s.
- **Failure Path:** El `availability-projector` está caído 10 min; al volver procesa el *backlog* y reconcilia; mientras tanto el *árbitro final* (la DB) siguió evitando ventas dobles.

### HU 08.1 - Contenerización de las Aplicaciones
`[NUEVA]`

**Descripción:** Como desarrollador, quiero imágenes pequeñas, seguras y reproducibles, para desplegar la misma artefacto en todos los entornos.

**Tareas de Implementación:**
1. `Dockerfile` multi-stage con capas de Spring Boot (mejor caché y *pulls* más rápidos):
   ```dockerfile
   # syntax=docker/dockerfile:1
   FROM eclipse-temurin:21-jre AS builder
   WORKDIR /builder
   COPY target/app.jar application.jar
   RUN java -Djarmode=tools -jar application.jar extract --layers --destination extracted

   FROM eclipse-temurin:21-jre
   RUN useradd --system --uid 10001 app
   WORKDIR /application
   COPY --from=builder /builder/extracted/dependencies/ ./
   COPY --from=builder /builder/extracted/spring-boot-loader/ ./
   COPY --from=builder /builder/extracted/snapshot-dependencies/ ./
   COPY --from=builder /builder/extracted/application/ ./
   USER 10001
   EXPOSE 8080 8081
   # B-27: los flags van en el ENTRYPOINT, no en JAVA_TOOL_OPTIONS.
   # Con JAVA_TOOL_OPTIONS la JVM imprime "Picked up JAVA_TOOL_OPTIONS: ..." en stderr
   # en cada arranque: una linea que NO es JSON y que rompe el CA de HU 10.1
   # ("el 100 % de las lineas son JSON valido") y las reglas de parseo de Alloy.
   ENTRYPOINT ["java", \
     "-XX:MaxRAMPercentage=75", \
     "-XX:+ExitOnOutOfMemoryError", \
     "-jar", "application.jar"]
   ```
   Alternativas: `./mvnw spring-boot:build-image` (Buildpacks), imagen *distroless*, o compilación nativa con GraalVM (menor arranque y memoria, mayor tiempo de build y restricciones de reflexión).
2. Ejecutar como **usuario no-root** con sistema de archivos de solo lectura (montar `/tmp` como `emptyDir`).
3. Habilitar `server.shutdown=graceful` y `spring.lifecycle.timeout-per-shutdown-phase=30s`.
4. Habilitar hilos virtuales (`spring.threads.virtual.enabled=true`) y revisar *pinning* (bloques `synchronized` que retienen el hilo portador) con eventos JFR `jdk.VirtualThreadPinned`.
5. Etiquetar con el SHA del commit y metadatos OCI (`org.opencontainers.image.*`).
6. Evaluar AppCDS/CRaC para reducir el tiempo de arranque.

**Criterios de Aceptación (CA):**
- La imagen pesa **< 300 MB**, corre como UID ≠ 0 y Trivy no reporta vulnerabilidades CRITICAL.
- El contenedor arranca (readiness OK) en **< 30 s** en el nodo objetivo.
- Con límite de memoria de 768 MiB el proceso **no** es terminado por OOM bajo la carga nominal (JVM dimensionada por porcentaje).
- Al recibir `SIGTERM`, la app termina las peticiones en curso (≤ 30 s) antes de salir.

**Casos de Uso:**
- **Happy Path:** El mismo digest de imagen se promueve de *staging* a *producción* sin reconstruir.
- **Failure Path:** La JVM excede el límite de memoria; `ExitOnOutOfMemoryError` provoca un reinicio limpio en lugar de un estado zombie y la alerta de reinicios dispara.

### HU 08.2 - Manifiestos, Sondas y Exposición con Gateway API
`[NUEVA]`

**Descripción:** Como SRE, quiero manifiestos declarativos con sondas, límites y políticas de seguridad, para que los despliegues sean seguros, repetibles y sin interrupciones.

**Tareas de Implementación:**
1. Organizar con **Kustomize** (`base/` + `overlays/{local,staging,prod}`) para las apps propias; **Helm** para componentes de terceros (todo reconciliado por ArgoCD). Los mismos manifiestos corren en `kind`/`k3d` (overlay `local`).
2. `Deployment` con estrategia, sondas, recursos y seguridad:
   ```yaml
   apiVersion: apps/v1
   kind: Deployment
   metadata: { name: api }
   spec:
     replicas: 3
     strategy: { type: RollingUpdate, rollingUpdate: { maxUnavailable: 0, maxSurge: 25% } }
     selector: { matchLabels: { app: api } }
     template:
       metadata: { labels: { app: api } }
       spec:
         terminationGracePeriodSeconds: 45          # ≥ preStop + shutdown graceful
         securityContext: { runAsNonRoot: true, seccompProfile: { type: RuntimeDefault } }
         topologySpreadConstraints:
           - maxSkew: 1
             topologyKey: topology.kubernetes.io/zone
             whenUnsatisfiable: ScheduleAnyway
             labelSelector: { matchLabels: { app: api } }
          containers:
            - name: api
              image: ghcr.io/ORG/tix/api:SHA
              ports:
                - { name: http,  containerPort: 8080 }
                - { name: mgmt,  containerPort: 8081 }   # management.server.port (HU 09.1)
              resources:
                requests: { cpu: 500m, memory: 768Mi }
                # B-26: con requests.memory = limits.memory pero SIN limits.cpu, el pod queda
                # en QoS Burstable, no Guaranteed. El comentario de la v2.0 decia lo contrario.
                # Guaranteed exige request = limit en AMBOS recursos.
                limits:   { memory: 768Mi }            # -> Burstable (documentado, aceptable)
                #   Si se quiere Guaranteed: limits: { cpu: 1, memory: 768Mi } y requests: { cpu: 1, ... }
              # B-19: las tres sondas van al puerto de GESTION (8081), no al de aplicacion (8080).
              # Con management.server.port=8081, una sonda contra 8080 falla con connection refused
              # (el puerto de aplicacion no expone /actuator/**) y el pod nunca llega a Ready.
              startupProbe:   { httpGet: { path: /actuator/health/liveness,  port: 8081 }, periodSeconds: 2, failureThreshold: 30 }
              readinessProbe: { httpGet: { path: /actuator/health/readiness, port: 8081 }, periodSeconds: 5 }
              livenessProbe:  { httpGet: { path: /actuator/health/liveness,  port: 8081 }, periodSeconds: 10 }
              lifecycle: { preStop: { exec: { command: ["sleep", "10"] } } }
              securityContext: { allowPrivilegeEscalation: false, readOnlyRootFilesystem: true, capabilities: { drop: [ALL] } }
              volumeMounts: [{ name: tmp, mountPath: /tmp }]
          volumes: [{ name: tmp, emptyDir: {} }]
    ```
    > **Sondas:** la *liveness* debe reflejar solo si el proceso está sano (**no** incluir DB/Redis: una caída de dependencia no debe reiniciar todos los pods). La *readiness* puede incluir dependencias críticas con cuidado de no sacar todos los pods del *Service* a la vez.
    >
    > **B-19 en detalle.** Es un error silencioso: el manifiesto se aplica sin error, los pods se crean y quedan `0/1` en *Ready*, y el rollout se detiene. Lo que delata el problema es que `/actuator/health/liveness` responde en 8081 y no en 8080. Con `named: mgmt` en el `containerPort`, las sondas pueden referenciar el nombre en vez del número, y un error de puerto se vuelve imposible por construcción.
    >
    > **B-26 en detalle.** Kubernetes clasifica el QoS en tres niveles y `Guaranteed` exige que **todos** los contenedores tengan `requests` y `limits` de CPU **y** memoria, y que sean iguales. Igualar solo la memoria deja el pod en `Burstable`, que es la opción por defecto en la mayoría de los ecosystems y evita el *throttling* de CPU que implica `Guaranteed` con límites duros. La v3.0 documenta la decisión real (`Burstable`) en vez de afirmar `Guaranteed`, y deja la alternativa como decisión consciente.
3. `PodDisruptionBudget` (`maxUnavailable: 1`), `Service`, `ServiceAccount` por app (IRSA para accesos AWS) y `ResourceQuota`/`LimitRange` por *namespace*.
4. Exposición con **Gateway API** (`Gateway` + `HTTPRoute`), no con `ingress-nginx` (retirado en marzo de 2026; ADR-007):
   ```yaml
   apiVersion: gateway.networking.k8s.io/v1
   kind: HTTPRoute
   metadata: { name: api }
   spec:
     parentRefs: [{ name: public-gw }]
     hostnames: ["api.example.com"]
     rules:
       - matches: [{ path: { type: PathPrefix, value: /api } }]
         backendRefs: [{ name: api, port: 80 }]
   ```
5. TLS automatizado con **cert-manager** (con soporte de Gateway API).
6. **NetworkPolicies** con *default deny* y permisos explícitos (api → pgbouncer, redis, kafka; worker → …); etiquetas de *Pod Security Admission* en nivel `restricted`.
7. Namespaces: `tix-staging`, `tix-prod`, `observability`, `kafka`, `argocd`, `gateway`.

**Criterios de Aceptación (CA):**
- Un *rolling update* bajo carga ligera produce **0 respuestas 5xx** y 0 conexiones cortadas (verificado con k6 durante el despliegue).
- `kubectl drain` de un nodo no baja de 2 réplicas disponibles (PDB respetado).
- Una `NetworkPolicy` impide que un pod no autorizado alcance PostgreSQL (probado con un pod efímero).
- Todos los pods cumplen el perfil `restricted` (sin privilegios, no-root, `readOnlyRootFilesystem`).
- **Todas las sondas responden en el puerto de gestión 8081 y el pod llega a `Ready` en < 90 s** (B-19). CA automático: un test de chart lee el manifiesto renderizado y falla si alguna sonda apunta a un puerto distinto de `management.server.port`.
- `kubectl describe pod` muestra la QoS **declarada en el comentario** (`Burstable`), verificada con un test que lee `status.qosClass` (B-26).

**Casos de Uso:**
- **Happy Path:** Se despliega una versión nueva; los pods nuevos pasan a *Ready*, los viejos dejan de recibir tráfico, drenan y terminan sin errores.
- **Failure Path:** La nueva versión no pasa la *readiness* (configuración errónea); el *rollout* se detiene con los pods viejos sirviendo y se revierte desde GitOps.

### HU 08.3 - Autoescalado y Preescalado para Picos Programados
`[NUEVA]`

**Descripción:** Como SRE, quiero escalar horizontalmente según carga y anticiparme a aperturas de venta programadas, para que el sistema esté dimensionado *antes* del pico.

**Tareas de Implementación:**
1. **HPA v2** para `api` y `waiting-room` (CPU ≈ 60 % y métrica de negocio, p. ej. peticiones en vuelo/RPS) con `behavior` (estabilización de bajada ≥ 5 min).
2. **KEDA para el `worker`: un `Deployment` y un `ScaledObject` por consumidor (B-16).** La v2.0 tenía un único `Deployment` `worker` con 4 consumidores sobre 5 tópicos, un solo `ScaledObject` gatillado por el *lag* de `orders.events` y `maxReplicaCount: 12` justificado como "≤ particiones del tópico". Eso tiene tres problemas:

   - **Escalar por un tópico no escala por los otros cuatro.** Si `payments.events` se acumula (que es lo que pasa cuando cae el proveedor de pagos), el *lag* de `orders.events` sigue en cero y el despliegue no crece. El retraso crece sin que ningún disparador reaccione.
   - **El límite de réplicas es por consumidor, no global.** Con 4 consumidores, `maxReplicaCount: 12` permitiría 48 pods, y un solo consumidor nunca podría usar más de 12 porque tiene 12 particiones asignadas como máximo. Los otros 36 estarían ociosos.
   - **Un consumidor que necesita 12 réplicas y otro que necesita 2 compiten por el mismo presupuesto**, y el escalado de uno roba capacidad al otro.

   La estructura correcta es **un `Deployment` por consumidor, cada uno con su `ScaledObject` y su `maxReplicaCount` atado al número de particiones de *su* tópico**:

   ```yaml
   # worker-orders, worker-payments, worker-seats, worker-notifications:
   # un Deployment + un ScaledObject cada uno
   apiVersion: keda.sh/v1alpha1
   kind: ScaledObject
   metadata: { name: worker-payments }          # <- un ScaledObject por consumidor
   spec:
     scaleTargetRef: { name: worker-payments }   # <- y un Deployment propio
     minReplicaCount: 2
     maxReplicaCount: 12                        # = particiones de payments.events (12)
     pollingInterval: 15                         # <- deteccion de lag, ver nota
     triggers:
       - type: kafka
         metadata:
           bootstrapServers: tickets-kafka-bootstrap.kafka:9092
           consumerGroup: worker-payments        # <- un consumer group por consumidor
           topic: payments.events                # <- SU topic
           lagThreshold: "500"
           activationLagThreshold: "1000"
   ```

   | Consumidor | Tópico | Particiones | `maxReplicaCount` | `lagThreshold` |
   |---|---|---|---|---|
   | `worker-orders` | `orders.events` | 12 | 12 | 500 |
   | `worker-payments` | `payments.events` | 12 | 12 | 500 |
   | `worker-seats` | `seats.events` | 24 | 24 | 2 000 |
   | `worker-notifications` | `notifications.commands` | 12 | 12 | 5 000 |

   `maxReplicaCount` **nunca supera el número de particiones**: más allá de eso, los réplicas extra se quedan ociosas. Y `seats.events` necesita un `lagThreshold` mayor en términos absolutos porque procesa muchos más mensajes por segundo (cada venta genera un delta).

   **El preescalado por `cron` se pone solo donde tiene sentido:** en `worker-seats` y `worker-orders` (los que mueven la experiencia de compra), no en los otros dos. Y se aplica con un `ScaledObject` adicional de tipo `cron` sobre el **mismo** `Deployment`, no sobre un escalado global.
3. **Escalado de nodos** con Karpenter o Cluster Autoscaler, más *pods de sobreaprovisionamiento* (*pause pods*) para absorber ráfagas mientras aparecen nodos nuevos (tardan minutos).
4. **Presupuesto de conexiones:** `maxReplicas × pool de Hikari ≤ cuota de PgBouncer` (HU 03.3); verificarlo en CI con un chequeo sobre los manifiestos.
5. *Warm-up*: peticiones de calentamiento en el arranque y *readiness* tardía hasta completar la carga de cachés críticas.
6. Procedimiento de **preescalado manual** para eventos masivos (runbook): escalar `api`, `waiting-room`, PgBouncer y nodos 30–60 min antes.

**Criterios de Aceptación (CA):**
- Un aumento de carga del 50 % escala `api` en **< 2 min** manteniendo p99 dentro del SLO.
- El preescalado por *cron* deja las réplicas objetivo en `Ready` **antes** de la hora de apertura.
- Con 100 000 mensajes de *lag*, el `worker` escala hasta el máximo configurado y el *lag* converge sin sobrepasar la cuota de conexiones de DB.
- **Cada consumidor tiene su propio `ScaledObject` y su propio `Deployment`, y su `maxReplicaCount` no supera las particiones de su tópico** (B-16). CA automático: un test de manifiestos falla si hay más de un `ScaledObject` apuntando al mismo `scaleTargetRef`, o si algún `maxReplicaCount` > particiones del tópico del trigger.
- **El retraso de `payments.events` escala `worker-payments` sin que el *lag* de los otros tópicos se mueva** (B-16). Test: se inyectan 100 000 mensajes en `payments.events` con `orders.events` en cero; los pods de `worker-payments` crecen y los de `worker-orders` no. Con el esquema de la v2.0 (un solo `ScaledObject` gatillado por `orders.events`) este CA falla.
- El `Deployment` de un consumidor que **no** tiene particiones asignadas no se escala: no hay pods ociosos por más allá de las particiones.

**Casos de Uso:**
- **Happy Path:** A las 19:55 el preescalado deja 8 réplicas listas; a las 20:00 abre la venta sin saturación.
- **Failure Path:** El escalado de nodos tarda más de lo previsto; los *pause pods* se desalojan para dar espacio inmediato y el pico se absorbe mientras llegan los nodos nuevos.
- **Failure Path (B-16):** la pasarela de pagos tarda 40 s en responder. Se acumulan 100 000 mensajes en `payments.events`; `worker-payments` escala a 12 réplicas y el *lag* converge en 3 min. `worker-orders`, `worker-seats` y `worker-notifications` mantienen su mínimo, porque su *lag* es cero. Con un único `ScaledObject` por `orders.events`, el retraso de pagos habría crecido de forma invisible hasta que los SLOs de la pasarela se rompieran.

> **Principio:** el autoescalado reactivo es demasiado lento para un pico viral súbito; se combina con **preescalado**, **cola de espera** (HU 04.3) y *load shedding* (HU 05.4).

### HU 08.4 - Entrega Progresiva (Canary) con Análisis Automático
`[NUEVA]`

**Descripción:** Como equipo de ingeniería, quiero liberar versiones gradualmente con validación automática, para limitar el impacto de un defecto.

**Tareas de Implementación:**
1. Adoptar **Argo Rollouts** (reemplaza al `Deployment` de `api`) con estrategia *canary* (10 % → 50 % → 100 %) y enrutamiento por réplicas o por **Gateway API** (plugin).
2. Definir un `AnalysisTemplate` contra Prometheus que consulte tasa de error y latencia p99; si falla, **abortar y revertir automáticamente**:
   ```yaml
   apiVersion: argoproj.io/v1alpha1
   kind: AnalysisTemplate
   metadata: { name: error-rate }
   spec:
     metrics:
       - name: error-rate
         interval: 1m
         failureLimit: 2
         successCondition: result[0] < 0.01
         provider:
           prometheus:
             address: http://prometheus.observability:9090
             query: |
               sum(rate(http_server_requests_seconds_count{app="api",status=~"5.."}[2m]))
               / sum(rate(http_server_requests_seconds_count{app="api"}[2m]))
   ```
3. Compatibilidad con **migraciones de base de datos** (*expand/contract*): la versión N y N+1 deben convivir con el mismo esquema.
4. *Feature flags* (OpenFeature/Unleash) para separar *despliegue* de *activación*.

**Criterios de Aceptación (CA):**
- Una versión que introduce errores 5xx > 1 % es **abortada automáticamente** antes de alcanzar el 50 % del tráfico.
- El *rollback* automático restaura la versión estable en **< 3 min**.
- Ninguna migración rompe la versión anterior en ejecución (verificado en CI con la versión N-1 contra el esquema N).

**Casos de Uso:**
- **Happy Path:** El *canary* supera los análisis y se promueve al 100 % sin intervención.
- **Failure Path:** El *canary* eleva el p99 de `hold` por una consulta lenta; el análisis falla y el *rollout* se revierte; el equipo recibe la alerta con enlace al *dashboard*.

### HU 08.5 - Servicios con Estado: PgBouncer, Kafka y Redis
`[NUEVA]`

**Descripción:** Como SRE, quiero una estrategia clara para los componentes con estado, para saber qué opero yo y qué delego en servicios gestionados.

**Tareas de Implementación:**

3. **PgBouncer** como `Deployment` (≥ 2 réplicas) con PDB y `preStop` para drenar conexiones.
4. Procedimientos de **actualización** (versiones menores y mayores) y de **escalado de almacenamiento** documentados y ensayados.
